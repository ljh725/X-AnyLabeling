# ViTPose 关键点飞框问题排查总结

> 背景:批量推理 s55.json 时,ViTPose 预测的 17 个关键点全部飞出 person 框
> (`in_box = 0/11`),但头部关键点置信度 0.9、身体关键点 0.005,模型像在
> "认真预测但全部预测错"。
>
> 本文档记录完整排查过程、真凶、以及反思。

---

## 现象

批量推理 `s55.json`,ViTPose 预测的 17 个关键点全部飞出 person 框:

```
gid   in_box/total  mean_score  worst_kpt
  1    0/11           0.387     r_knee
  0    0/8            0.683     r_hip
  2    0/9            0.412     r_ank
  3    0/8            0.657     l_hip
  4    0/7            0.646     l_hip
```

特征:**头部 score 高(0.9)、身体 score 极低(0.005)**,模型像在"认真预测但全部预测错"。

---

## 走过的弯路(按时间顺序)

| 阶段 | 怀疑的根因 | 实际情况 |
|------|-----------|---------|
| 1 | 采纳外部建议:坐标映射公式错(scale 是 /200 相对尺度) | ❌ 本项目 `bbox_xyxy2cs` 是纯像素,**没有 /200** |
| 2 | 线性公式 vs 逆仿射差异 | ❌ 几何验证证明两者对正常框**结果完全一致** |
| 3 | padding 不对称、人体偏到一边 | ❌ 数学验证:左右 padding 各 65.8,**完全对称**,人体居中 |
| 4 | GPU provider(CUDA/TensorRT)精度问题 | ❌ 三个 provider **全部 fallback 到 CPU**,结果都 0.829 |
| 5 | 两个环境 onnxruntime 版本差异(1.24 vs 1.23) | ❌ 不是版本问题 |
| 6 | `crop_and_align` 处理多 box 时互相污染 | ❌ blob diff 显示单 box 和多 box 的 blob[0] **完全一致** |
| 7 | 输入准备(RGB/BGR、归一化常数) | ❌ 两条代码路径的 blob **max diff = 0.000000** |

**每一层都被排除了。** 所有"看起来可疑"的地方都查了一遍,全是对的。

---

## 真凶

最后一个测试暴露了真相 —— **同一个 box,两条路径跑出的 score 不同(0.829 vs 0.266)**。进一步对比发现:`parse_annotation` 解析出的 person 框
`[x1, y1, x2, 330.89]` —— **y2 和 y1 相同,person 框高度塌成 0**。

根因是最朴素的**数据格式假设错误**:

- 标注 rectangle 存的是 **4 个角点**:`[[x1,y1],[x2,y1],[x2,y2],[x1,y2]]`
- 旧代码假设是 **2 个对角点**,只取 `pts[0]` 和 `pts[1]`
- 这两个点恰好是**顶边的两个角**(y 坐标相同),导致框高度=0
- crop 出来的图是扁条,模型自然预测飞

**修复**:遍历所有角点取 min/max(一行改动),问题消失,in_box 从 `0/17` 变 `17/17`。

```python
# 修复前(假设 2 对角点,取前 2 个点)
(x1, y1), (x2, y2) = pts[0], pts[1]

# 修复后(遍历所有角点,兼容 2 点和 4 点格式)
xs = [p[0] for p in pts]
ys = [p[1] for p in pts]
box = (min(xs), min(ys), max(xs), max(ys))
```

## 反思

### 1. 被"权威建议"带偏了节奏

转述的"scale 是 /200 相对尺度"这个诊断,**听起来非常专业且具体**,第一反应是
"这应该就是了",然后花了好几轮去验证坐标映射、逆仿射、padding。没有第一时间
去核对"这个假设在本项目代码里成不成立"。

**教训:外部建议再专业,也要先核对它依赖的事实前提。** 本应该开头就
`print(bbox_xyxy2cs 的返回值)`,5 秒钟就能发现 scale 是纯像素、假设不成立。

### 2. 应该更早对比"输入"而不是"输出"

一直在对比 score(模型输出),花了 6 轮排除各种可能性。但**真正的破局点是对比
box 本身(模型输入的源头)**。当两个路径 score 不同时,应该立刻去 print box 的
数值,而不是去查 ONNX、provider、blob。

**教训:输出不一致时,先确认输入是否一致。追到最上游,而不是在中游打转。** 这个
原则本来知道,但被复杂的中间环节(仿射、归一化、ONNX)分散了注意力。

### 3. "复杂的代码路径"本身就是干扰项

这次涉及仿射变换、归一化、ONNX 推理、多环境,每一层都"可能"出问题。但实际上
**故障在数据解析(最简单的字符串/数字处理)这一层**。越简单的地方越容易被忽略。

**教训:排查时不要被技术复杂度引导。按数据流从上游到下游逐段验证,而不是从
"最可疑的复杂环节"开始。**

### 4. diff 测试的基准必须来自独立可信源

后来写的 `diagnose_blob_diff`(对比两条路径的 blob)思路是对的,但**应该再往上走
一步** —— 对比 box 而不是 blob。如果当时对比的是 `parse_annotation 出来的 box`
vs `原始 JSON 的 points`,第一轮就能抓到。blob diff 显示 identical 反而误导
(让我以为输入没问题),其实 **blob 是基于错误的 box 算出来的,自然一致**。

**这暴露了一个盲区:diff 测试的"基准"必须来自独立、可信的源**(原始 JSON),不能
两个都来自同一条可疑的代码路径。

---

## 一句话总结

> 绕了 7 个弯,真凶是 rectangle 格式假设错误(4 角点被当 2 对角点)。
> 下次遇到"输出不一致"会直接从最上游的输入数值开始 print,
> 不被中间环节的复杂度带偏。
