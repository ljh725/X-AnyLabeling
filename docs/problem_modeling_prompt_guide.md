# 让大模型成为问题建模伙伴

当你使用大模型解决需求时，不要一开始就让它写代码。更有效的方式是先让它成为一个问题建模伙伴、方法论搜索器、认知边界扩展器。

核心目标不是让它补充你的实现，而是让它先做三件事：

1. 重表征问题
2. 寻找更高层抽象
3. 提出你可能不知道的解法族

## 完整提示词模板 
## 你可以把提示词改成这种结构

```text
我现在有一个需求/问题如下：

【问题描述】
...

请你不要直接给代码，也不要只在我现有思路内优化。

请先完成以下任务：

1. 问题重表征：
   - 用 3 到 5 种不同方式重新表述这个问题。
   - 每种表述要站在不同抽象层级，比如：
     - UI 交互问题
     - 数据结构问题
     - 状态同步问题
     - 约束求解问题
     - 人机协作流程问题
     - 可维护性/扩展性问题

2. 知识边界扩展：
   - 指出我当前描述里隐含的假设。
   - 哪些假设可能限制了解法？
   - 有没有更通用的计算机科学、软件工程、产品设计或认知科学概念可以映射到这个问题？

3. 解法族枚举：
   - 不要只给一个方案。
   - 请给出至少 5 类不同方案，例如：
     - 直接工程修补
     - 架构重构
     - 数据模型改造
     - 交互范式调整
     - 规则系统/状态机/约束系统
     - 工具化或自动化方案

4. 反直觉方案：
   - 给出 2 到 3 个我可能不会主动想到、但值得考虑的方案。
   - 说明它们为什么看起来绕远，但可能更根本。

5. 学习导向：
   - 请提炼这个问题背后的通用知识点。
   - 告诉我如果想变强，应该学习哪些概念。
   - 每个概念用一句话解释，并说明它如何帮助解决当前问题。

最后，再根据成本、风险、长期收益，推荐一个方案。
```

## 简短提示词模板

```text
请不要急着写代码。
先把这个问题当作一个“问题建模”任务来处理。

请你：
1. 找出我问题中的隐含假设；
2. 用更抽象的概念重表征它；
3. 提出我可能不知道的解法族；
4. 给出一个短期方案和一个长期方案；
5. 告诉我这个问题背后值得学习的通用知识。
```

## 高价值句式
#  还有一个很好用的句式

```text
请站在一个比我当前描述更高一层的抽象视角看这个问题。
如果我把它误认为是 A 类问题，但它其实更像 B 类问题，请直接指出。
```

## 你也可以要求它扮演不同角色，而不是只扮演程序员
'''

1. 资深架构师
2. 产品交互设计师
3. 编译器/状态机设计者
4. 数据建模专家
5. 维护这个项目两年后的工程师
'''


## 得最关键的一句话是
```text
不要被我的实现想法约束。请先判断我是否把问题表述错了。
```

## 这句话尤其重要。很多时候，我们以为自己在问：

```text
怎么把这个按钮挪到这里？
```

## 但真正的问题可能是：

```text
这个界面的信息架构不稳定。
```

```text
状态源没有统一。
```

```text
当前交互模型把用户的任务拆碎了。
```

```text
这个需求应该被建模成选择集、约束集、状态迁移，而不是 UI patch。
```

## 多角色分析模板

也可以要求大模型不要只扮演程序员，而是分别从不同角色分析：

```text
请分别从以下视角分析：
1. 资深架构师
2. 产品交互设计师
3. 编译器/状态机设计者
4. 数据建模专家
5. 维护这个项目两年后的工程师
```

这样可以帮助你看到同一个问题背后的不同结构，而不是停留在最表层的代码修改。

## 推荐工作流

把需求分成两轮问。

第一轮负责扩大认知边界：

```text
先不要实现。请帮我重新理解这个问题，尽量跳出我的原始表述。
```

第二轮负责工程落地：

```text
现在基于你刚才提出的更高层模型，选择最适合当前代码库的方案并实现。
```

这样可以把大模型从“代码补全器”切换成“问题重构器”，先提升问题质量，再提升实现质量。

## 更稳的做法是把它当成一个未经验证的高级假设，进入“验证阶段”
## 方案生成后 验证阶段
## 1 先让原模型自证
'''
请不要继续扩展方案。
现在请审查你刚才提出的方法：
1. 这个方法成立依赖哪些前提？
2. 哪些前提在当前项目中还没有被验证？
3. 最可能失败的地方是什么？
4. 如果这个方法是错的，会出现什么可观察症状？
5. 最小验证实验是什么？

'''

## 2 再让另一个模型做反方审查
'''
请你扮演严苛的技术审稿人。
下面是一个方案，请专门寻找它的问题：
- 哪些概念被误用了？
- 哪些工程假设不成立？
- 有没有更简单的替代方案？
- 这个方案在什么条件下会失败？
- 如果你要否决它，理由是什么？
'''

## 3 回到代码库做事实核查

'''text
大模型提出的抽象方法，必须落到项目事实里验证
'''
'''text
请检查当前代码库，验证这个方案依赖的关键前提是否成立。
不要修改代码，只输出：
1. 已确认成立的事实，附文件/函数位置；
2. 未找到证据的假设；
3. 与方案冲突的现有实现；
4. 需要进一步实验验证的点。
'''

## 4 做最小实验，而不是全量部署
'''text
请把这个方案拆成一个最小可验证实验。
要求：
- 不影响现有主流程；
- 可以独立回滚；
- 能验证最关键的风险；
- 给出通过/失败标准。

'''
## 我建议你形成一个固定四步

'''text
提出方案 -> 反方审查 -> 代码事实核查 -> 最小实验验证。

'''
