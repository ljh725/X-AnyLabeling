# 代码升维对话协议（Code Dimensional Lift Protocol）

> 让一段"低维代码"借助大模型真正升一次维，而不是换一种写法。
> 配套文档：`docs/llm_feature_development_playbook.md`（通用功能开发方法论）。
> 本协议是 playbook 在「纯代码升维」这个子场景的压缩特化版。

---

## 0. 这份协议要解决什么问题

「升维」不是「优化」，也不是「重构」，更不是「换个写法」。

- **优化**：同一个问题模型下，做得更快/更省。
- **重构**：同一个问题模型下，换个结构让代码更好读。
- **升维**：**换一类问题模型**。低维代码把本该独立的多个维度压成了一维来解；升维是把被压扁的维度重新展开，让代码能表达低维方案表达不了的情况。

三者的混淆是大模型升维失败的最大原因——你说「优化」，它做重构；你说「改进」，它打补丁。

## 1. 为什么直接让大模型「改进代码」必然失败

三个结构性原因，不是 prompt 写得不好：

1. **「改进/优化/重写」指向方法，不指向思维**。大模型听到这些词，默认走 patch 路径——找 if-else、加分支、换写法。它不会停下来问「这段代码的问题模型是什么、被压扁的是哪些维度」。
2. **升维在对比中才看得见，单份代码看不见**。只给大模型一份低维代码，它没法知道「高维长什么样」，只能就地打转。
3. **大模型最擅长「假升维」**——把 if-else 换成策略模式、把 for 循环换成 map、把函数拆成类。写法变了，维度没变。没有强制验证，它会交一份看起来更「高级」但同维的东西，你以为升维了。

本协议的每一步都针对克服这三点设计。

## 2. 核心原则

**禁止大模型跳步**。每一步必须停下等用户确认，尤其第 1、2 步没完成前，绝对不准进第 4 步写代码。这是协议的命门。

**禁止裸 jargon**（元约束，覆盖全程）：

> 对话全程，任何非日常词出现时，必须当场用一句具体例子或行为定义。不许裸用 jargon。如果你写出了一串读者需要查的词，那说明你在降维——把多维现实压成了不透明标签。

这条元约束的存在是因为协议 v1 的教训：把「命名问题模型」放在第一步（如「布尔命中集合上按隐式栈序做唯一选择」），对一个还没掌握原始素材的学习者来说就是一串不透明的标签——协议自己在做降维。

给学习者起一个抽象名字，本身就是一次低维动作（把多维现实压成一个字符串）。命名这个动作必须放在素材掌握之后，不能之前。

## 3. 五步协议

### Step 1：用大白话描述行为 + 说出代价（不命名）

**目的**：先让学习者掌握「这段代码到底在干什么、做不到什么」。素材优先，标签之后。

**Prompt 模板**：

```text
下面是一段代码（粘贴）。

请只做一件事：用大白话描述它「在干什么」，
然后说出它「做不到什么」。

要求：
1. 描述行为：把它想象成一叠实物或一个真人做事的过程。
   禁用词：「问题模型」「模式」「抽象」「架构」「范式」。
   只能用「它从……开始」「当……时，它……」这样的句子。
2. 说出代价：每个代价必须是具体场景，
   「如果遇到 X 情况，这段代码只能 Y，没法 Z」。
   至少 3 条。

禁止：评价好坏、提出改进、建议替代、写新代码、
      给它起任何抽象名字（命名留到后面）。
```

**验证标准**：

- 大模型的回答里如果出现「问题模型」「模式」「抽象」等禁用词——失败，让它重来。
- 大模型的回答里如果出现它自己起的抽象名字（如「这是一种隐式栈序」）——失败，让它删掉。
- 代价必须每条都是具体场景，不能是「不够优雅」这种空话。

**大模型常见跑偏**：它会忍不住说「这里有个 bug」「可以优化成…」。第一次跑偏就在回复里明确打断：「我说了不评价、不改进。只描述行为、说代价。」

### Step 2：盘点被压扁的维度（这一步是协议的灵魂）

**目的**：低维的本质是「把多维问题压成一维来解」。找出被压扁的维度，才知道往哪升。这一步结束后，那个抽象名字会自动变成可解的压缩。

**Prompt 模板**：

```text
基于刚才的大白话行为描述，回答：

这段代码把哪些「本该独立的维度」，压成了一维的判据？

对每个被压扁的维度，请说明：
1. 这个维度是什么（用大白话说，例如「鼠标离对象多近」
   「对象多大」「谁后被画出来」「用户想编辑顶点还是整个对象」）。
2. 在当前代码里，它被压成了什么
   （如「压成了碰到/没碰到二选一」「压成了列表顺序」
   「被完全忽略了」）。
3. 在「未被压扁」的理想形态下，它应该是什么数据形态
   （如「一个连续的距离值」「一个有序的候选列表」
   「一个枚举的意图类别」）。

禁止：写代码、提方案。这一步只做「维度盘点」。
```

**验证标准**：

- 大模型必须列出**至少 3 个**被压扁的维度。如果只列出 1-2 个，逼它再找——低维代码几乎一定压扁了不止两个维度。
- 每个维度的描述必须能用大白话解释，不许裸 jargon。

**大模型常见跑偏**：它会把「被压扁」和「实现得不好」混在一起。纠正它：我们要的是「维度被压扁」，不是「代码写得糙」。

**这一步结束后（可选）**：现在可以让大模型给这套维度起一个压缩名字了——因为压缩素材你都掌握了，名字变得可解。如果你不需要这个名字，跳过即可。

### Step 3：为每个维度找高维表征 + 决定组合方式

**目的**：把每个被压扁的维度展开成可比较的值，并决定它们如何组合成一个可比较的整体。这是从「诊断」过渡到「设计」的桥梁，也是升维的核心。

**Prompt 模板**：

```text
针对上一步列出的每个被压扁的维度，设计它的高维表征。

要求：
1. 每个维度用什么数据类型承载（数值？枚举？列表？）。
2. 这些维度之间「如何组合成一个可比较的整体」
   ——必须给出组合方式，例如：
   - 元组字典序（先按 A，同级按 B…）
   - 加权评分（w1*x1 + w2*x2…）
   - 分层规则（A 决定档位，档位内再按 B）
   选哪种、为什么选这种，要说清。
3. 这个组合方式是否可扩展（未来加一个维度会不会推翻重写）。

完成后停下来，输出「维度 → 表征 → 组合方式」的对照表，
等我确认。禁止直接写实现代码。
```

**验证标准**：

- 大模型必须显式给出「组合方式」并解释为什么选这种。如果它只列出「距离用 float、面积用 float」而不说怎么组合——失败。**组合方式才是升维的核心，不是数据类型。**
- 大模型如果在这里就开始写代码——打断，让它停下来。

**这一步的红利**：到这一步，学习者往往能看出高维方案的雏形长什么样。大模型很可能独立设计出某种评分/元组结构——**而用户全程没有告诉它目标方案长什么样**。这就是「自己发现升维」。

### Step 4：在新维度上重写（带硬约束）

**目的**：落地。但带一个硬约束，防止「假升维」。

**Prompt 模板**：

```text
按上一步确认的维度表征和组合方式重写代码。

硬约束：
1. 优先级、判据、分层必须活在「数据字段」里
   （元组位、字典 key、配置项），不准活在「控制流的物理顺序」里。
   即：交换两段代码的物理位置，行为应当不变。
2. 不准为新引入的特殊 case 写 if 分支。
   特殊 case 必须通过「给它一个数据值」来处理，
   而不是「给它一段独立代码」。
3. 查询函数只负责「收集 + 排序」，不准在里面做「选中」决策。
   决策权交给调用方。

写完后，自查：交换任意两段同级代码的物理顺序，
输出是否不变？如果变了，你违反了约束 1，重写。
```

**验证标准**：

- 让大模型自己跑「交换代码顺序」的自检。这是检测「假升维」最狠的一招——如果交换顺序行为变了，说明优先级还活在控制流里，没升维。
- 约束 3 是检测「决策是否外置」的关键。如果重写后的函数内部仍然直接 return 单个对象而不是候选列表，决策权没外置，升维不彻底。

### Step 5：验证升维（防假升维检查表，绝对不能省）

**目的**：确认是真升维。这一步是协议的保险。

**Prompt 模板**：

```text
现在用下面四个判据检查你的重写是否「真的升维了」，
还是只是换了个写法：

1. 新方案能否表达旧方案「无法表达」的情况？
   （举一个旧方案做不到、新方案能做到的具体 case）
2. 旧方案能否作为新方案的「退化特例」？
   （把新方案的某些维度设成常数，能否还原旧方案行为？）
3. 新方案是否减少了「跨入口的复制粘贴」？
   （低维代码的标志是多处入口各写一遍漂移副本）
4. 新方案是否把「决策权」从函数内部搬给了调用方？

四条里至少两条答「是」，才算真升维。
如果不到两条，你做的是「重构」不是「升维」，回到 Step 2
重新找被压扁的维度——你一定漏了。
```

**这是协议最重要的检查**。大模型会本能地想跳过这步说「已经更好了」。四个判据逼它给具体 case，给不出就是假升维。

## 4. 协议使用的两个原则

1. **先在第二个用例上跑通，再信这份协议**。本协议是 v2——v1 在「命名是否放在第一步」上翻车过。任何协议只在第一个用例上跑通，都不算成立；必须在第二个不相关的用例上跑通才算。
2. **Step 1 和 Step 2 是命门，宁可拖也不能跳**。Step 4 之前的每一句话都在影响升维的方向，跳过任何一个判断点都可能导致 Step 4 给出一份假升维的代码。

## 附录 A：完整案例——beta.4 对象选择 → beta.11 算法

这个案例全程**不需要给大模型看 beta.11**。它会自己长出 4 元组。这正是协议成立的关键证据。

### A.1 输入的低维代码（移植前的 beta.4 `select_shape_point` 节选）

```python
# 原版逻辑（~80 行，节选核心）
for shape in reversed(self.shapes):
    if not self.is_shape_interactive(shape):
        continue
    # 顶点命中
    index = shape.nearest_vertex(pos, self.epsilon / self.scale)
    if index is not None:
        # ... 选中并 return
        return
    # cuboid 正面命中
    if shape.shape_type == "cuboid" and len(shape.points) == 8:
        front_path = self.cuboid_face_path(shape, CUBOID_FACE_FRONT)
        if front_path is not None and front_path.contains(pos):
            # ... 选中并 return
            return
    # 整体命中
    shape_hit = False
    if shape.shape_type in ["point", "line", "linestrip"]:
        if shape.nearest_vertex(pos, self.epsilon * 3 / self.scale) is not None:
            shape_hit = True
    elif len(shape.points) > 1 and shape.contains_point(pos):
        shape_hit = True
    if shape_hit:
        # ... 选中并 return
        return
```

同样的 `reversed(self.shapes) + for + if shape_type 分支 + 首次命中即 return` 模式在 hover 和双击里各复制了一份，三份已经漂移（双击漏了 cuboid 正面分支、点击不识别边命中）。

### A.2 五步走完会产出什么

| Step | 产出 |
|---|---|
| 1 行为+代价 | 行为：对象像一叠卡片，后画的压在上面；鼠标点一下从最上面往下翻，碰到第一个就停。代价：①重叠时只看「谁后画」硬挑，不看距离/面积；②点击这套不识别顶点/边，hover 那套识别，两套对不上；③同点反复点永远选同一个。 |
| 2 被压扁的维度 | 距离（压成布尔）、面积（被忽略）、栈序（隐式，靠列表顺序）、交互意图（顶点/边/整体，写死在 if 顺序里）、候选集（压成单个返回值）——5 个维度 |
| 3 维度表征+组合 | 距离=float、面积=float、栈序=-index、意图=level 枚举、候选=List；组合=**元组字典序** `(level, distance, area, -stack_index)` |
| 4 重写 | `_shape_hit_candidates(point) -> List[Shape]`：收集每个 shape 的 4 元组分数，排序后返回列表；hover/点击/双击三处入口都 `for shape in self._shape_hit_candidates(point): ...` 消费 |
| 5 验证 | (1) 嵌套选小框——旧做不到新做得到 ✓ (2) level 全设 2 即还原旧方案 ✓ (3) hover/点击/双击三份副本合一 ✓ (4) 返回 List 而非单 Shape，决策外置 ✓ ——**四条全 yes** |

### A.3 大模型独立设计出的「高维」代码（与 beta.11 实际方案对照）

```python
def _shape_hit_candidates(self, point):
    """Return shapes under a point in interaction priority order."""
    candidates = []
    for stack_index, shape in enumerate(self.shapes):
        if not self.is_shape_interactive(shape):
            continue
        area = shape.bounding_rect.width() * shape.bounding_rect.height()
        # level 0: 顶点
        v_dist = shape.nearest_vertex_distance(point, self.epsilon)
        if v_dist is not None:
            candidates.append(((0, v_dist, area, -stack_index), shape))
            continue
        # level 1: 边 / 线性 shape
        e_dist = shape.nearest_edge_distance(point, self.epsilon)
        if e_dist is not None and shape.can_add_point():
            candidates.append(((1, e_dist, area, -stack_index), shape))
            continue
        # level 2: 整体命中
        if shape.contains_point(point):
            candidates.append(((2, area, 0.0, -stack_index), shape))
    candidates.sort(key=lambda item: item[0])
    return [shape for _, shape in candidates]
```

这个结构和 beta.11 原版的 `_shape_hit_candidates` 本质一致——而用户全程没给大模型看 beta.11。这就是协议的可复现性证据。

### A.4 升维的真正本质（一句话）

> 不是「更好的算法」，而是「换了一类问题」：从「鼠标点中了**哪一个** shape」变成「这个位置下**叠着哪些** shape、按交互优先级怎么**排**」。返回类型从 `Shape or None` 变成 `List[Shape]`，决策权从函数内部搬给了调用方。
