# 让大模型成为问题建模伙伴：结构化提示词流程

当你使用大模型解决需求时，不要一开始就让它写代码。更有效的方式是先让它成为问题建模伙伴、方法论搜索器、认知边界扩展器。

这个提示词的核心目标不是让模型补充你的实现细节，而是让模型先做三件事：

1. 重新表征问题；
2. 寻找更高层抽象；
3. 提出你可能不知道的解法族。

但要注意：模型提出的方案不是结论，而是一个未经验证的高级假设。正确用法是先扩展认知边界，再进入验证阶段，最后才工程落地。

## 总体流程

推荐把一次需求讨论拆成四轮：

```text
问题建模 -> 方案生成 -> 方案验证 -> 最小实验
```

也可以理解成：

```text
扩展认知边界 -> 审查方案假设 -> 回到代码事实 -> 小范围验证落地
```

## 第一轮：问题建模提示词

这一轮的目标是让模型跳出你当前的实现想法，重新理解问题。

```text
我现在有一个需求/问题如下：

【问题描述】
...

请你不要直接给代码，也不要只在我现有思路内优化。

请先完成以下任务：

1. 问题重表征：
   - 用 3 到 5 种不同方式重新表述这个问题。
   - 每种表述要站在不同抽象层级，比如：
     - UI 交互问题
     - 数据结构问题
     - 状态同步问题
     - 约束求解问题
     - 人机协作流程问题
     - 可维护性/扩展性问题

2. 知识边界扩展：
   - 指出我当前描述里隐含的假设。
   - 哪些假设可能限制了解法？
   - 有没有更通用的计算机科学、软件工程、产品设计或认知科学概念可以映射到这个问题？

3. 解法族枚举：
   - 不要只给一个方案。
   - 请给出至少 5 类不同方案，例如：
     - 直接工程修补
     - 架构重构
     - 数据模型改造
     - 交互范式调整
     - 规则系统/状态机/约束系统
     - 工具化或自动化方案

4. 反直觉方案：
   - 给出 2 到 3 个我可能不会主动想到、但值得考虑的方案。
   - 说明它们为什么看起来绕远，但可能更根本。

5. 学习导向：
   - 请提炼这个问题背后的通用知识点。
   - 告诉我如果想变强，应该学习哪些概念。
   - 每个概念用一句话解释，并说明它如何帮助解决当前问题。

最后，再根据成本、风险、长期收益，推荐一个方案。
```

这一轮完成后，如果你觉得模型推荐的方案有价值，不要马上让它实现。下一步应该进入验证阶段。

## 可选增强：简短模板

当问题比较小，或者你只是想快速打开思路，可以使用短模板。

```text
请不要急着写代码。
先把这个问题当作一个“问题建模”任务来处理。

请你：
1. 找出我问题中的隐含假设；
2. 用更抽象的概念重表征它；
3. 提出我可能不知道的解法族；
4. 给出一个短期方案和一个长期方案；
5. 告诉我这个问题背后值得学习的通用知识。
```

## 可选增强：高价值句式

下面这句话适合用在你怀疑自己把问题问窄了的时候：

```text
请站在一个比我当前描述更高一层的抽象视角看这个问题。
如果我把它误认为是 A 类问题，但它其实更像 B 类问题，请直接指出。
```

最关键的一句话是：

```text
不要被我的实现想法约束。请先判断我是否把问题表述错了。
```

很多时候，我们以为自己在问：

```text
怎么把这个按钮挪到这里？
```

但真正的问题可能是：

```text
这个界面的信息架构不稳定。
```

```text
状态源没有统一。
```

```text
当前交互模型把用户的任务拆碎了。
```

```text
这个需求应该被建模成选择集、约束集、状态迁移，而不是 UI patch。
```

## 可选增强：多角色分析

也可以要求大模型不要只扮演程序员，而是分别从不同角色分析：

```text
请分别从以下视角分析：
1. 资深架构师
2. 产品交互设计师
3. 编译器/状态机设计者
4. 数据建模专家
5. 维护这个项目两年后的工程师
```

这样可以帮助你看到同一个问题背后的不同结构，而不是停留在最表层的代码修改。

## 第二轮：方案验证提示词

如果第一轮模型给出了一个你想采纳的方案，先把它当成一个高级假设，而不是最终答案。

```text
请不要继续扩展方案。
现在请审查你刚才提出的方法：

1. 这个方法成立依赖哪些前提？
2. 哪些前提在当前项目中还没有被验证？
3. 最可能失败的地方是什么？
4. 如果这个方法是错的，会出现什么可观察症状？
5. 最小验证实验是什么？
```

这一轮的目的，是让模型从“提出方案”切换到“审查方案”。

## 第三轮：反方审查

如果方案比较重要，可以让另一个模型或同一个模型切换角色，做反方审查。

```text
请你扮演严苛的技术审稿人。
下面是一个方案，请专门寻找它的问题：

- 哪些概念被误用了？
- 哪些工程假设不成立？
- 有没有更简单的替代方案？
- 这个方案在什么条件下会失败？
- 如果你要否决它，理由是什么？
```

这一轮的价值是降低“模型说得很顺，所以听起来像对的”的风险。

## 第四轮：代码事实核查

大模型提出的抽象方法，必须回到项目事实里验证。尤其是在已有代码库中，方案是否成立取决于现有架构、数据流、状态管理和历史约束。

```text
请检查当前代码库，验证这个方案依赖的关键前提是否成立。
不要修改代码，只输出：

1. 已确认成立的事实，附文件/函数位置；
2. 未找到证据的假设；
3. 与方案冲突的现有实现；
4. 需要进一步实验验证的点。
```

这一轮不是让模型写代码，而是让它查证事实。

## 第五轮：最小实验验证

通过事实核查后，不建议直接全量部署。更稳的做法是把方案拆成一个最小可验证实验。

```text
请把这个方案拆成一个最小可验证实验。
要求：

- 不影响现有主流程；
- 可以独立回滚；
- 能验证最关键的风险；
- 给出通过/失败标准。
```

这一轮输出的应该不是完整实现，而是一个可以验证关键风险的小实验。

## 第六轮：工程落地

只有当方案通过前提审查、代码事实核查和最小实验设计之后，才进入实现阶段。

```text
现在基于已经验证过的方案，选择最适合当前代码库的落地方式并实现。

要求：
1. 遵循当前项目的代码结构和风格；
2. 保持改动范围尽可能小；
3. 不重构无关模块；
4. 给出必要的测试或验证方式；
5. 实现后说明改动点、风险和后续可迭代方向。
```

## 推荐工作流

把需求分成两轮是最低成本做法：

第一轮负责扩大认知边界：

```text
先不要实现。请帮我重新理解这个问题，尽量跳出我的原始表述。
```

第二轮负责工程落地：

```text
现在基于你刚才提出的更高层模型，选择最适合当前代码库的方案并实现。
```

更稳的四步流程是：

```text
提出方案 -> 反方审查 -> 代码事实核查 -> 最小实验验证
```

完整闭环是：

```text
问题建模
-> 解法族生成
-> 反方审查
-> 代码事实核查
-> 最小实验
-> 工程实现
-> 根据结果重新建模
```

## 如何用大模型迭代这个提示词

这个提示词模板本身也可以继续被大模型迭代。推荐让模型基于使用结果来改，而不是凭空改。

```text
下面是一个问题建模提示词模板，以及一次真实使用后的模型输出。

请你评估这个提示词：
1. 哪些部分有效扩大了认知边界？
2. 哪些部分导致输出空泛、重复或不可落地？
3. 哪些问题没有被模型追问出来？
4. 哪些验证步骤还不够强？
5. 请基于这些观察，重写一版更好的提示词模板。
```

如果你想让它更偏工程落地，可以追加：

```text
重写时请降低抽象口号，增加可验证标准、代码事实核查要求、最小实验要求。
```

如果你想让它更偏认知扩展，可以追加：

```text
重写时请增加跨学科视角、反直觉方案、类比迁移和问题重表征的强度。
```

## 使用原则

这个模板的价值，不是让模型一次性给出正确答案，而是让模型帮你走完一个更好的思考流程：

1. 先怀疑问题表述；
2. 再扩展解法空间；
3. 再审查方案假设；
4. 再回到代码事实；
5. 最后小步验证和实现。

认知边界之外的方法值得被看见，但不应该被直接采纳。它们应该先变成候选假设，再通过事实和实验筛选。
