# 版本与备份管理约定

入口：[中文版本与备份目录](../../版本与备份目录.md)。建立日期：2026-11-02。

先读[GitHub 操作说明（大白话版）](../../GitHub操作说明.md)，了解三类工作的流程；每次操作填入[操作记录](操作记录.md)。重复关系和精简候选见[核对说明](重复关系核对-2026-11-02.md)。

## 各种保存方式的用途

| 类型 | 用途 | 当前例子 |
| --- | --- | --- |
| 默认首页 `main` | 放统一目录，保留现有旧版代码 | 首页链接到中文目录 |
| 版本入口分支 | 指向该版本选定的已提交阶段；更新时应核对验证状态 | `versions/4.0.0-beta.4`、`versions/4.2.1` |
| 功能开发分支 | 完成一项明确修改 | 新工作建议 `feature/4.2.1/功能英文名`；工具要求 `codex/` 前缀时使用 `codex/4.2.1/功能英文名` |
| 固定备份标签 | 精确保留一次保存点，不移动已有标签 | 新工作建议 `backup/4.2.1-YYYYMMDD-用途英文名` |
| 官方版本标签 | 保存官方原始代码，供对照和迁移 | `v4.2.1`；不要把官方标签挪到个人修改代码 |
| 本地 `.bundle` | 保存 Git 对象和历史的离线备份文件 | `backups/pre-drag-fix-20261030.bundle` |

名称里的日期建议统一使用北京时间。旧分支、旧标签保持原名，不需要为了统一外观重写历史。

## 每次修改的记录顺序

1. 先确定修改属于哪个基础版本，从相应的已保存节点建立功能开发线。
2. 写清楚这次具体改什么；开发过程中及时保存提交。没有提交的文件不会因为建了分支或标签就自动进入备份。
3. 做较大修改前，把需要保留的代码提交为一个明确保存点，再创建固定备份标签；同时检查新文件是否已纳入、是否含不应公开的个人文件。
4. 把需要异地保存的分支或标签同步到 GitHub，并核对远端提交号。
5. 完成相应验证后，记录功能、验证范围和提交号，再决定是否推进 `versions/...` 版本入口。
6. 更新中文目录和对应功能记录，标清“方案 / 开发中 / 已提交待验证 / 已验证 / 已回退”。分支名、标签名和已有测试文件不能代替验证结果。

## 归档与清理

- 已有 `archive/feature/...` 标签继续作为旧功能索引。
- 分支名重复或指向同一提交，不足以直接决定删除。先核对独有提交、后续维护用途及固定恢复点。
- 本次整理保留所有旧分支和标签。将来确实需要删减时，列明每个待清理名称、完整提交号及替代恢复入口，再进行有针对性的清理。
- 恢复优先放进新目录；图片、标注 JSON、模型文件和运行环境另行备份。
