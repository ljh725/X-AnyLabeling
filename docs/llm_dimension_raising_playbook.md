# 使用大模型升维解决问题：无理论知识前提下的功能开发方法论

> 本文档是 `llm_feature_development_playbook.md` 的替代版（v2）。
>
> 它解决的问题：当你想做的功能超出自己的知识边界——你不知道组成它的概念
> 存在，因此既描述不了它，也判断不了任何关于它的方案——如何借助大模型
> 可靠地把它做出来，并且尽可能把"升维"（发现你不知道自己不知道的解法）
> 变成可重复的过程。

## 0. 诚实前置：本方法论能承诺什么、不能承诺什么

### 0.1 理论知识缺失不可规避

正确性总得有个担保方。穷举下来全世界只有四个来源：

| # | 担保方 | 失效模式 |
|---|--------|----------|
| 1 | 使用者自己的知识 | 本方法论的前提就是它缺位 |
| 2 | 大模型的知识 | 可能是错的；可能和你缺的是同一块 |
| 3 | 经验现实 | 现象、可运行的原型、真实使用的后果 |
| 4 | 第三方他者 | 领域专家、code review、社区已有实践 |

"如何在使用者没有理论知识的情况下保证流程正确"的答案是**不可能**，
就像"如何校对一门我不懂的语言"。任何声称解决了这个问题的方法论都
是在撒谎。旧版 playbook 的根本缺陷不是没解决它，而是**假装解决了**：
它把担保方悄悄设成了 1（让用户确认问题定义、确认规则模型），而 1
恰恰是缺位的——无法判断的人最容易在确认环节点头放过错误。

### 0.2 所以目标函数必须改写

本方法论的目标**不是**规避知识缺失，而是：

> **让流程的正确性不依赖使用者的理论知识，并让残余风险可检测、
> 可回滚、可定位。**

具体手段是把各环节的担保方从 1 换成 3（验证环节）和 2+4（框架生成
环节），并用机制而不是提示词请求来约束模型的行为。

### 0.3 使用前的最终决策

先想清楚你是哪种场景，流程裁剪方式完全不同：

- **A. 不懂理论也要可靠地交付功能** → 走完整前端 + 极简后端，
  接受"使用者可能永远不懂其中的概念"。
- **B. 通过做功能把理论学会** → 前端不变，验收之后必须接"学"的环节
  （第 7 节），这是慢功夫，任何流程仪式都替代不了。
- **C. 高 stakes、错了代价大** → 不要指望任何流程，在框架选定后、
  实现前，买一次真人专家评审（担保方 4）。

## 1. 第 0 阶段：分流门

旧方法最大的浪费是让"加个按钮"和"改状态机"走同一条六阶段流水线。
所有改动先进一个二维判断：**不确定性**（问题定义是否清楚）×
**不可逆性**（改错了代价多大）。

| | 低不确定性 | 高不确定性 |
|---|---|---|
| **低代价**（可回滚、局部） | 直接做：TDD + 验证即完成 | 轻量版：1 轮竞争框架 → 落盘 spec → 实现 |
| **高代价**（架构、数据、兼容性） | 标准版：spec + 测试先行 + 复盘 | 完整版：本文档全流程 |

规则：

- 分流由模型提议，**用户一票否决即可**，成本控制在 10 秒。
- 分流错了随时可以升级车道；只允许升级，不允许在车道内偷工减料。
- 本文档第 2~5 节是完整版流程；轻量版 = 只做 2.2（竞争框架）+
  2.4（假设登记处）+ 第 4 节（后端）。

## 2. 前端流程：从现象到框架（升维发生区）

前端流程只做一件事：**在用户无法描述、无法判断的前提下，从现象出发
找到正确的问题框架**。它建立在用户确实拥有的三样东西上：

1. **现象**：用户描述不了知识，但亲历过问题，能叙述具体事件。
2. **识别能力**：用户判断不了抽象定义，但能指认具体行为（"我要的是
   这个"）。
3. **对自身经验的事实回答能力**：用户不需要懂任何理论就能回答
   "从那个入口进来时，锁定状态丢没丢"。

### 2.1 事件叙述（替代需求描述）

不要求用户说想要什么，只要求按模板叙述**具体发生过的事**：

```text
我在做……（操作序列，越具体越好）
我以为会……
实际……
我卡在哪一步 / 哪一刻觉得不对
我目前想到的解决办法（可选，仅登记为候选）：
必须保留的现有行为：
```

要点：

- **不收术语**。"不知道状态机是什么"的人照样能说"我撤销之后它又
  变回去了"。叙述具体事件不需要任何概念储备。
- 用户的预设解法必须登记，但标注为**候选方案而非需求**。它是后面
  检验流程能否把用户从自己锚点上拔出来的对照物。
- 旧模板的"我希望发生什么变化"被降级为可选——回答不了就不答，
  那正是知识边界的信号，不是缺陷。

### 2.2 竞争框架（升维的核心动作）

让模型产出 **≥3 个问题结构不同**的候选框架，并强制横向迁移。
提示词模板见附录 A.2，关键约束：

1. **结构上不同**，不是同一方案的三个变体。例如对"选中被遮挡对象"：
   时序循环（加切换机制）、空间排序（改选择判据）、显式消歧 UI
   （点击弹出候选列表）是三个不同结构；"Tab 循环"和"方向键循环"
   不是。
2. **强制跨界提问**："图形编辑器 / CAD / 浏览器开发者工具 / 游戏
   拾取是如何解决同类问题的？"——训练分布里的跨域模式是模型最
   可能替你完成升维的地方。
3. 每个框架必须输出四样东西：
   - **命名与核心概念**：这就是替你揭示你不知道存在的 A 和 C
     （例如 hit-testing、selection-as-ranking、disambiguation）。
   - **最坏情况成本表**：用可计数的用户操作量表示（点击数、步数），
     不许用"更优雅""更通用"这类无法核实的词。
   - **失效条件**：什么场景下这个框架会出错。
   - **对用户场景的预测**：见 2.3。

**红线**：模型输出一个框架然后问"这个对吗"，视为流程违规。单一
假设 + 无法判断的裁判 = 旧方法的失败模式重演。

### 2.3 现象预测核对（替代定义确认）

这是把担保方从用户知识换成经验现实的核心机制：

> **命名之后禁止问用户"对吗"，必须问"你有没有观察到……"。**

每个候选框架必须生成**对用户自己场景的可检验预测**，例如：

> "如果问题真的是状态机问题，那么从另一个入口进入时你应该也观察
> 到锁定状态丢失。你观察到了吗？"

用户回答"是 / 否 / 没试过"**不需要知道状态机是什么**——他只是在
报告自己的观察。规则：

- 预测命中的框架存活，落空的淘汰或降级。
- 预测必须具体、可观察、有明确对错；"用户体验会更好"不算预测。
- "没试过"的预测转化为一次 5 分钟的现场实验，做完再回答。
- 成本表在这一步发挥防迎合作用：当"选第 3 层对象需要点 3 次且
  得知道叠了几层"和"零额外点击"并排摆着，用户不需要理论就能
  投票。数字替理论发言。

这一步同时解决了旧方法的另一个死结：**模型倾向于迎合用户预设的
方案**。要求每个框架（包括用户的预设方案）拿出成本表和预测，让
它们在同一标准下竞争，而不是让用户给自己的方案当裁判。

### 2.4 原型识别（文字走到头就换介质）

当场景叙述和预测核对仍无法决出框架时，不要继续要用户描述——
人对选项的**识别**能力远强于对需求的**描述**能力。让模型做出两个
候选行为的最小可运行原型（或直接在现有功能上演示两种行为），
用户指着说"要这个 / 不要这个"。

- 原型必须小到能在一次会话内做出来；超过半天工作量的"原型"是
  实现，不是原型。
- 指认结果连同理由写进 spec 的证据栏（见 3.1）。

### 2.5 假设登记处（硬门禁）

全流程共享一份假设登记表（落盘文件，不是聊天记录）：

```text
| 假设 | 风险等级 | 验证方法 | 状态 | 失效后回退到 |
```

规则：

- 每个阶段产出的未验证假设都必须登记，标高/低风险。
- **高风险假设未全部关闭前，不允许进入实现阶段。** 这是流程规则，
  不是提示词请求：实现任务开始时假设清单必须为空或全部为低风险。
- 实现阶段的验证命令失败时，**先更新登记处，再改代码**——"代码
  事实推翻假设时回退"不靠模型自觉。
- 验收时发现体验问题，回退目标不是笼统的"重新定义问题"，而是
  登记处里具体失效的那一条。

## 3. 后端流程：产物落盘与执行门禁

后端不解决知识问题，只解决**执行翻车**：模型撒谎、上下文漂移、
改了不该改的行为。知识问题只在前端解决一次；后端是目前已知对
执行问题最便宜的办法。

### 3.1 产物全部落盘，不靠对话记忆

每个阶段产出一个文件进仓库（建议放 `docs/specs/<功能名>/` 或随
项目惯例）：

```text
问题定义.md      —— 事实 / 推断 / 假设三栏 + 最终选定框架
规则表.md        —— 每条规则：触发条件、预期行为、例外、验证方式
验收清单.md      —— 自动化测试清单 + 人工体验任务清单
假设登记.md      —— 见 2.5
```

- 每个新阶段开始时，模型必须**先读回这些文件**再工作。长上下文
  漂移用文件系统解决，不靠提示词哀求模型记住假设。
- spec 的每条结论标注证据基础："本框架由预测 P1✓、P2✓、原型 B
  指认支持"。用户**不背书 spec 的正确性**——证据链替代判断。
- 这些文件随代码进 PR，评审者能核对"实现 vs 规则表"，后续维护者
  能查"当初为什么这么定"。死在聊天记录里的产物等于没有产物。

### 3.2 规则表 = 可执行测试（测试先行）

- 规则确认后先写测试，测试文件本身就是规则表的可执行形态，
  两者不分离（分离必然漂移）。
- 测试用例从场景枚举生成：正常 / 边界 / 冲突 / 回归。模型能生成
  用例不需要用户懂理论；用户只需核对一件事："**这个场景我在
  真实工作中遇到过吗**"——这又是用户不依赖知识就能回答的问题。

### 3.3 实现与验证

- 最小实现：不擅自增加未确认的行为；保持未修改的现有行为兼容。
- 验证必须**真实运行命令并贴出输出**；禁止"我认为能通过"。
- 完成后必须报告：修改了什么 / 为什么 / 验证了什么 / 未验证什么 /
  与 spec 的偏差 / 残余风险。偏差不可耻，隐瞒偏差才违规。

## 4. 体验有效性验收协议

旧方法承认"测试证明不了体验"但没给方案。以下是最小可用协议：

1. 定义 3~5 个真实任务，修改前后各做一次（最好让没参与开发的
   人做），记录：**完成时间、操作步数、卡壳点**。
2. 验收标准预先写成可观察指标："该操作从 4 步降到 2 步""嵌套
   对象选中零额外点击"。不接受"感觉更顺"。
3. 自动化测试只证明**实现正确性**（代码符合规则）；任务对照
   证明**体验有效性**；**模型正确性**（规则是否表达了真实意图）
   只能靠真实使用——暂时无法验证的进假设登记处，标复核期限
   （例如"实际上标 50 张图后复核"）。

## 5. 升维模式库（可迁移资产）

每次功能开发完成后，从过程中蒸馏至多 **1~2 条**模式追加到这里。
每条模式包含：模式名 / 升维前 → 升维后 / 识别信号（什么现象提示
该用这个模式）。

### 模式 1：search → ranking（搜索改排序）

- 升维前：遍历候选，第一个满足条件的胜出。
- 升维后：枚举**全部**候选，按多维判据排序后取第一。
- 识别信号：第一命中者经常不是想要的；用户在抱怨"总是选错"
  而不是"选不到"。

### 模式 2：时间成本 → 判定信息

- 升维前：为覆盖不了的情况加操作机制（循环、切换、撤销重选），
  用户付时间成本。
- 升维后：给判定函数更多维度的信息（距离、面积、意图），让
  特殊情况在排序里自行消失，机制不再需要。
- 识别信号：你正在设计"再按一次 X 就轮到下一个"之类的机制。

### 模式 3：视觉问题 → 几何翻译

- 升维前：用视觉概念描述问题（遮挡、盖住、看见）。
- 升维后：翻译成几何/数据概念（嵌套、包围盒面积、z-order），
  视觉难题变成可计算的判据。
- 识别信号：问题描述里全是"看到/看不到"。

### 模式 4：一处算法 → 多处一致消费

- 升维前：hover 高亮、单击、双击各写各的命中逻辑。
- 升维后：一个候选列表函数被多处消费，一致性免费获得。
- 识别信号：同一个判定散落在三个以上调用点，改一处忘两处。

> 模式库的价值在于：它把一次升维的**动作**（而非结论）沉淀下来。
> 下次遇到结构相似的问题，模型可以被提示"套用模式库逐条检查
> 是否适用"，升维从运气变成流程。

## 6. 完整案例研究：遮挡对象选择（beta.4 → beta.11）

本案例是方法论的实证样本，答案直接公开（教学目的）。

### 6.1 起点（升维前）

原版 labelme 式算法：遍历 `reversed(shapes)`（从视觉顶层向底层），
第一个 `contains_point` 命中即返回——纯 z-order，**永远选中最上层**。
被上层完全盖住的对象理论上永远选不到，只能去右侧标签列表里选。

使用者的直观反应（本案例用户的真实第一反应）是设计**循环切换**
机制：重复点击或快捷键在重叠对象间轮换。这是模式 2 识别信号的
教科书例子——在时间维度上加机制。

### 6.2 作者的升维解法

beta.11 的 `_shape_hit_candidates`
（上游仓库 `anylabeling/views/labeling/widgets/canvas.py:497`；
本仓库已回填至 `canvas.py:672`，注释 `[迁移自 beta.11 功能C]`）：

1. **search → ranking**（模式 1）：枚举全部可见 shape 计算优先级
   元组并排序，取第一个。信息量增加一个维度——旧算法对候选集
   一无所知，新算法拥有全集。
2. **单判据 → 多维排序键**（模式 2）：元组
   `(交互类型, 距离, 面积, -z_order)`。"顶点 > 边 > 内部"把用户
   接下来想干什么（抓点？加点？移动整体？）编码进选择函数——
   交互意图维度注入几何判定。
3. **视觉遮挡 → 几何嵌套**（模式 3）：重叠时**包围盒面积小者优先**。
   被小框盖住的大框本就有非重叠区可点；真正无解的是被大框盖住的
   小框——面积规则恰好让后者必胜。**循环切换机制根本不需要了，
   遮挡问题在排序里自行消失。**

附带红利（模式 4）：hover 高亮、单击、双击三处消费同一候选列表
（本仓库 `canvas.py:1256`、`canvas.py:1978`、`canvas.py:1920`），
行为一致性免费获得。

升维的实质一句话：用户在**时间维度**上加机制，作者在**判定信息
维度**上加判据，把时间成本消灭了。

### 6.3 升维后方案的已知局限（失效条件示范）

任何方案都要登记失效条件，这个方案也不例外：

- 面积用**包围盒**而非真实面积：细长的旋转框/多边形包围盒虚胖，
  重叠时会被误判为"大 shape"让位。
- **顶点劫持**：点击落在 shape A 内部、但距 shape B 某顶点 10
  屏幕像素以内时选中 B；密集关键点场景几乎总点中顶点。
- **边优先级压过内部**：点在小 shape 内部但距大 shape 的边 10px
  以内 → 选中大 shape。
- point/line/linestrip 有 3 倍磁吸半径（30 屏幕像素），密集标注
  里容易抢走属于其他 shape 的点击。
- 锁定的 shape 仍可被面点击选中，在重叠区挡住未锁定的 shape。
- 完全平局才看 z-order："看见的"不一定是"选中的"。

这些局限不是缺陷清单，而是**下一轮迭代的假设登记处条目**。

### 6.4 该案例在流程各阶段的样子

- **事件叙述**："两个框重叠，我点公共区域想选小框，永远选中大框
  （或相反，取决于场景），我只能去右边列表里找。我想到的解法：
  按个键循环切换重叠的框。"
- **竞争框架**（模型应产出）：
  A. 时序循环（用户的预设）——成本表：选第 N 层需 N 次操作且需
     预知层数；
  B. 空间排序（作者的方案）——成本表：嵌套场景零额外点击；预测：
     "点小框内部直接命中小框"可当场验证；
  C. 显式消歧 UI（点重叠区弹候选列表，Blender/PS 式）——成本表：
     任何场景都固定 2 次点击，但打断标注节奏。
- **预测核对**：用户只需回答"点小框内部该不该直接选中小框？
  你在标注里遇到嵌套多还是部分重叠多？"——不需要懂任何理论。
- **决策**：用成本表 + 用户自己数据的场景频率（嵌套多 → B；
  极密集多框叠放多 → C 保底）即可定，用户全程零理论判断。
- **测试先行**：嵌套、公共区、顶点劫持、边抢点击、缩放下
  epsilon 换算——每个用例用户核对"这场景我遇到过"。

## 7. 知识迁移（可选，仅场景 B）

模型完成了功能，不代表你的知识边界扩大了。但只有"想学"时才做
这一节，且**砍掉一切重仪式**：

1. 功能完成后花 5 分钟回答一个问题并记入个人知识文件："这次
   我新掌握的一个问题模型是什么？它的失效条件是什么？"
2. 想深入时，让模型针对概念追问你，而不是给你讲（"你猜猜如果
   面积换成真实面积，哪个局限会缓解、会引发什么新问题？"）。
3. 自检五问（能独立回答才算越过"听懂了"）：能否命名这个问题？
   能否解释方案为什么有效？能否比较两个方案的取舍？条件变了
   能否预测结果？换个功能能否认出相同结构？

## 8. 本方法论自身的验证协议与失效模式

### 8.1 验证的定位：冒烟测试，不是证明

"用流程复现一个已知的升维解法，成功了就说明流程有效"——这个
推理不成立，原因有四：

1. **训练数据污染**：已知答案可能就在模型训练语料里，"产出答案"
   可能只是背诵，与提示词无关。
2. **无对照组**：朴素提示词可能同样成功，无法归因于流程。
3. **评判者偏见**：看过答案的人判"是否收敛"必然被污染。
4. **用户角色污染**：已知答案的用户无法再扮演无知用户。

证据价值是**不对称的**：跑失败 = 强证据（流程有结构性问题）；
跑成功 = 弱证据（只说明模型有能力且流程没拦住它）。

### 8.2 可承受成本内的最硬验证设计

1. **预注册成功标准**：跑之前写下 3~5 条客观判据（"方案是否
   枚举全部候选并排序""嵌套选中是否零额外点击"），逐条打钩，
   禁止凭感觉。
2. **双跑对照**：同一模型，朴素提示词跑一次，完整流程跑一次，
   对照判据。差异才是流程的真实增量。
3. **污染声明**：跑前直接问模型是否知道该问题的已知解法，
   记录在案；更严格的做法是把问题改头换面（换场景包装），
   迫使迁移而非背诵。
4. **用户演员**：尽量让没看过答案的人扮演用户；做不到就把
   "用户已被污染"写入结论的限制条件。

### 8.3 失效模式与对策

| 失效模式 | 现象 | 对策 |
|---|---|---|
| 模型也不知道正确概念 | 竞争框架全员预测落空 | 引入担保方 4（专家/文献/社区）；承认此步值得花钱 |
| 现象覆盖过稀疏 | 错误框架靠少量预测存活 | 不追求一次选对，缩短到真实使用的证伪循环，让现实持续投票 |
| 模型迎合用户预设 | 用户方案总在框架对比中"胜出" | 强制成本表 + 预测，让用户方案在同一标准下竞争；用户忍住不拉票 |
| 用户给自己方案拉票 | 确认环节变形 | 把预设方案降级为候选之一写进流程规则；由成本数字替理论发言 |
| 流程形式主义 | 小改动也走全流程 | 分流门；只允许升级车道 |
| 产物不进仓库 | 决策依据随聊天记录消失 | 落盘是硬规则；PR 不含 spec 文件视为不完整 |

## 9. 与旧版 playbook 的关系

旧版（`llm_feature_development_playbook.md`）的六阶段骨架
（审计 → 建模 → 确认 → 落点 → 实现 → 复盘）在**高不确定性 ×
高代价**车道下仍然可用，但需做三处手术：

1. 认知边界审计的输出从"1 个改写后的问题定义"改为
   "≥3 个竞争框架 + 各自的可检验预测"（第 2.2、2.3 节）。
2. 所有"请用户确认"环节改为"请用户回答关于自身观察的事实题"
   或"请用户在原型间指认"（第 2.3、2.4 节）。
3. 全部中间产物落盘进仓库，假设登记处作为阶段间门禁
   （第 2.5、3.1 节）。
