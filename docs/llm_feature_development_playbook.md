# 使用大模型进行功能开发与知识边界扩展

本文档是一份可重复使用的功能开发范本，适用于以下情况：

- 只能描述功能哪里不好用，但不知道问题在工程上应该如何命名。
- 希望开发或扩展一个功能，但不确定自己的问题定义是否完整。
- 功能涉及超出当前知识边界的交互、算法、架构或规则设计。
- 不仅希望大模型完成代码，还希望自己能够理解、判断并迁移其中的知识。

这套方法的核心不是让大模型立即实现字面需求，而是先共同确认真正的问题，再建立可验证的规则，最后实现并复盘。

> 如果能够清楚画出功能长什么样，可以让模型协助实现。
>
> 如果只能说出哪里不舒服，应先让模型帮助命名、分类和抽象。

## 1. 总体流程

一次完整的功能开发由六个阶段组成：

```text
认知边界审计
    ↓
用户意图与规则建模
    ↓
规则确认
    ↓
代码落点与验收设计
    ↓
最小实现与验证
    ↓
功能复盘与知识迁移
```

不要一次性把所有提示词交给模型并让它自动完成。每当对话越过一个自己暂时无法独立判断的边界时，都应让模型停下来，将事实、推断和假设分开，再通过代码、用户观察或实验继续验证。

## 2. 开始前准备

在提问前，尽量提供以下信息。不知道的部分可以明确写“不确定”。

```text
功能名称：

我希望发生的变化：

当前观察到的现象或坏体验：

典型使用场景：

我目前想到的解决办法：

必须保留的现有行为：

已知限制：

我不确定的地方：
```

其中“我目前想到的解决办法”只是候选方案，不应当默认等同于真实需求。

## 3. 第一阶段：认知边界审计

### 3.1 目标

检查问题是否因为提问者当前的知识边界而被问窄、问浅或问偏，避免把熟悉的解决办法误当成需求。

### 3.2 提示词模板

```text
我要开发或扩展的功能是：
……

我观察到的现象是：
……

我目前想到的解决办法是：
……

已知约束是：
……

请先不要写代码，也不要直接接受我的解决方案。请进行一次认知边界审计：

1. 我字面上提出了什么问题？
2. 我真正观察到的现象是什么？
3. 我的描述中包含了哪些未经验证的默认假设？
4. 我是否把某个熟悉的解决方案误当成了需求？
5. 我可能遗漏了哪些用户、状态、操作顺序、异常情况和长期影响？
6. 哪些结论可以从现有代码确认？
7. 哪些结论只能通过用户观察、交互实验或实际使用确认？
8. 这个问题可能属于什么类型，例如状态机、优先级排序、规则系统、反馈机制、数据一致性、权限模型、命令系统或其他模型？
9. 请把原问题改写成一个更完整、中立、可验证的问题。

请按以下类别组织输出：

- 已知事实
- 根据事实做出的推断
- 尚未验证的假设
- 被过早指定的解决方案
- 需要进一步确认的问题
- 改写后的问题定义

不要假设我的问题定义一定正确，也不要假设你重新定义的问题一定正确。请为每个关键假设说明验证方法。
```

### 3.3 人工确认

阅读模型的审计结果后，不要立即进入实现。先回复：

```text
符合实际的判断：
……

不符合实际的判断：
……

我仍然不确定的部分：
……

请根据这些反馈更新问题定义，并继续保留尚未验证的假设标记。
```

认知边界审计的产物是“候选问题定义”，不是最终真理。

## 4. 第二阶段：用户意图与规则建模

### 4.1 六层分析模型

功能开发可以从以下六层展开：

1. **目标与现象层**：描述目标、使用场景、现象、坏体验、约束和期望变化。
2. **用户意图层**：推断用户真正想完成什么，以及不同意图之间的优先级。
3. **规则模型层**：建立规则、优先级、状态转换、数据约束或冲突处理模型。
4. **代码架构层**：寻找现有执行路径、代码落点和受影响的模块。
5. **测试验收层**：把规则转化为可执行测试和人工体验场景。
6. **最小实现层**：按照确认后的模型完成最小修改，并检查一致性。

实际对话时，应先完成第 1 至第 3 层并确认规则，再进入第 4 至第 6 层。

### 4.2 第 1 至第 3 层提示词

```text
基于刚才确认的问题定义，请继续完成功能建模，暂时不要阅读或修改代码。

第 1 层：整理功能目标、使用场景、现象、坏体验、约束和期望变化。
第 2 层：推断用户可能的真实意图，并说明意图发生冲突时的优先顺序。
第 3 层：将用户意图转化为可实现、可测试的规则、优先级、状态或数据模型。

请同时：

1. 给出典型场景、边界场景和反例。
2. 说明规则发生冲突时如何处理。
3. 标记仍然没有证据支持的假设。
4. 在存在实质性取舍时，提供至少两种候选模型。
5. 说明每种模型的优点、代价和失效条件。
6. 最后输出一份待我确认的规则清单。

完成后请停下来，不要继续实现。
```

### 4.3 规则确认

此时重点判断的不是“代码能否实现”，而是：

- 规则是否表达了用户真正想完成的事情。
- 优先级冲突是否符合实际操作习惯。
- 是否遗漏隐藏状态、锁定状态、撤销、失败反馈等情况。
- 条件变化时，规则是否仍然合理。

可以使用下面的回复模板：

```text
确认保留的规则：
……

需要修改的规则：
……

需要补充的场景：
……

暂时接受但仍需验证的假设：
……

请整理成最终规则表。每条规则包括触发条件、预期行为、优先级、例外情况和验证方式。
```

规则没有确认前，不进入代码实现。

## 5. 第三阶段：代码落点与验收设计

### 5.1 提示词模板

```text
现在请阅读现有项目代码，但暂时不要修改。

基于已经确认的规则：

1. 说明现有功能的完整执行过程。
2. 找出每条规则应该落在哪些模块、类或函数中。
3. 说明它会影响哪些现有行为和数据。
4. 检查它是否与现有架构、状态管理、交互规则或兼容性要求冲突。
5. 将规则转换成自动化测试和人工体验场景。
6. 覆盖正常情况、边界情况、冲突情况和回归情况。
7. 区分哪些结论可以由代码和测试证明，哪些必须经过实际使用确认。
8. 给出最小修改方案及其风险。

请输出：

- 当前执行路径
- 规则与代码落点的对应关系
- 受影响范围
- 测试与验收清单
- 最小修改方案
- 风险与未确认项

完成后请停下来，等待方案确认。
```

### 5.2 验收标准

验收需要区分三个不同问题：

1. **实现正确性**：代码是否正确实现了规则。
2. **模型正确性**：规则是否正确表达了用户意图。
3. **体验有效性**：用户实际使用时是否真的更顺畅。

自动化测试通过只能主要证明第一项，不能自动证明后两项。

## 6. 第四阶段：最小实现与验证

### 6.1 提示词模板

```text
按照已经确认的规则、代码落点和验收场景进行最小实现。

要求：

1. 不擅自增加未确认的行为。
2. 尽量保持现有架构和代码风格。
3. 保持未被明确修改的现有行为兼容。
4. 为核心规则增加或更新测试。
5. 运行与修改范围相匹配的验证。
6. 无法确认的地方不要自行假定，应明确标记。
7. 完成后说明实际实现与原设计是否存在偏差。

请在完成后报告：

- 修改了什么
- 为什么这样修改
- 验证了什么
- 哪些内容尚未验证
- 与确认方案的偏差
- 仍然存在的风险
```

实现过程中，如果代码事实推翻了前面的假设，应回到相应阶段更新问题模型，而不是为了维持原方案而强行实现。

## 7. 第五阶段：功能完成后的复盘

### 7.1 提示词模板

```text
功能已经完成一轮修改，请重新审查：

1. 实现解决的是原始现象，还是只完成了我们设计的方案？
2. 哪些用户意图已经覆盖，哪些仍然遗漏？
3. 测试证明的是代码符合规则，还是用户体验确实改善？
4. 有没有为了实现方便而改变原始需求？
5. 本轮使用中出现的新问题，属于哪一层的错误？
6. 下一轮应该重新分析全部问题，还是只回到其中一层？

请分别判断：

- 代码是否正确实现了规则
- 规则是否正确表达了用户意图
- 用户实际使用是否真的变得更好

不要把自动化测试通过等同于用户体验改善。请为不能确认的结论给出观察或实验方法。
```

### 7.2 功能仍然不好用时

不需要机械地重新执行全部流程。先定位问题属于哪一层：

```text
我们已经完成一轮修改，但我仍然觉得功能不好用。

新的现象是：
……

请先复盘：

1. 当前不好用的具体表现是什么？
2. 它属于问题定义错误、用户意图理解错误、规则优先级错误、状态反馈不清、操作路径复杂、边界场景遗漏，还是实现不一致？
3. 有什么证据支持这个判断？
4. 应该回到哪一阶段重新分析？
5. 下一轮最小的验证目标是什么？

暂时不要直接进行第二轮代码修改。
```

一般可以按照下面的方式回退：

| 发现的问题 | 建议返回的位置 |
| --- | --- |
| 原始问题被问窄或问偏 | 认知边界审计 |
| 用户真正想做的事情理解错误 | 用户意图层 |
| 冲突、状态或优先级不合理 | 规则模型层 |
| 修改位置导致职责混乱或行为不一致 | 代码架构层 |
| 测试通过但没有覆盖真实体验 | 测试验收层 |
| 规则正确但代码行为错误 | 最小实现层 |

## 8. 第六阶段：扩展个人知识边界

模型完成了功能，不代表开发者的知识边界已经扩大。只有开始能够解释、判断、预测和迁移，相关知识才真正成为自己的能力。

### 8.1 知识提取提示词

```text
请不要只总结这次修改了哪些代码，而是帮助我提取这次开发中超出我原有知识边界的内容。

1. 这次功能使用了哪些重要概念？
2. 每个概念解决的通用问题是什么？
3. 我以前为什么不容易想到这些概念？
4. 这些概念之间是什么关系？
5. 当前方案还有哪些常见替代方案？
6. 为什么这次选择当前方案？
7. 如果条件变化，方案应该怎样变化？
8. 最容易出现哪些错误？
9. 应该如何通过测试或观察发现这些错误？
10. 这些知识还能迁移到项目中的哪些功能？

请结合当前项目中的实际代码和场景解释，不要只给抽象定义。
```

### 8.2 用自己的话重新解释

```text
这是我对这个功能和相关概念的理解：
……

请检查：

1. 我理解正确的部分。
2. 我混淆的概念。
3. 我遗漏的关键关系。
4. 哪些地方只是记住了结论，还没有理解原因。
5. 请通过追问帮助我修正理解，不要立即给出完整答案。
```

### 8.3 使用变体检验理解

```text
请改变这个功能的三个关键条件，为我设计几个变体问题。

先不要给答案，让我判断：

1. 原来的规则是否还能成立？
2. 哪些优先级或状态需要变化？
3. 哪些测试需要增加？
4. 应该修改数据、规则、交互还是代码结构？

在我回答后，再检查我的推理过程。
```

### 8.4 迁移到其他功能

```text
请从项目中寻找一个表面上不同、但底层结构相似的功能。

不要直接告诉我完整答案。先让我判断：

1. 两个功能共享什么问题模型？
2. 原来的规则能否迁移？
3. 哪些差异会导致原模型失效？
4. 我需要增加哪些新概念？
```

### 8.5 知识是否真正掌握

可以通过以下五个问题进行自检：

1. 我能不能给这个问题正确命名？
2. 我能不能解释方案为什么有效？
3. 我能不能比较两种方案的取舍？
4. 条件变化时，我能不能预测结果？
5. 遇到另一个功能时，我能不能识别出相同结构？

能够独立回答这些问题，才说明知识开始越过“听懂了”进入“能够使用”。

## 9. 个人知识记录模板

每次功能开发后，可以保留一份简短记录：

```text
功能名称：

我最初看到的现象：

最初的问题定义：

审计后重新定义的问题：

我原来不知道的概念：

问题的通用模型：

最终采用的规则：

为什么选择这些规则：

其他候选方案：

当前方案的失效条件：

验证方法与结果：

可以迁移到哪些问题：

我现在仍然无法独立判断的部分：
```

一次功能真正掌握一两个可以迁移的问题模型，比记住大量术语更有价值。

## 10. 快速版对话范本

时间有限时，可以依次使用下面五段提示词。每段完成并确认后，再进入下一段。

### 10.1 审计问题

```text
我想开发或扩展一个功能，但我目前只能描述目标和现象。

功能与现象：
……

请不要只回答我的字面问题。先判断这个问题是否被我的知识边界问窄、问浅或问偏。请指出默认假设、遗漏角度和被过早指定的方案，并把问题重新命名、分类和抽象。请区分事实、推断和假设，不要写代码。
```

### 10.2 建立规则

```text
基于确认后的问题定义，请整理目标、用户意图和可测试的规则模型。说明优先级、冲突处理、边界场景、反例、替代方案和失效条件。完成后停下来等待确认。
```

### 10.3 阅读代码与设计测试

```text
请阅读现有代码，不要修改。找出当前执行路径、规则的代码落点、影响范围和风险，并先设计自动化测试与人工体验场景。区分代码可以证明的结论和必须实际使用才能确认的结论。
```

### 10.4 最小实现

```text
按照确认的规则、代码落点和验收场景完成最小实现。保持未被修改的现有行为兼容，增加必要测试，并报告实际实现与方案之间的偏差和未验证风险。
```

### 10.5 复盘与学习

```text
请检查实现是否解决了原始现象，并分别评价实现正确性、规则正确性和体验有效性。然后提取本次开发中的通用概念、替代方案、失效条件和可迁移场景，通过变体问题检验我是否真正理解。
```

## 11. 使用原则

1. 不知道问题叫什么时，直接告诉模型：“我不知道这个问题应该叫什么，请帮助我命名、分类和抽象。”
2. 不把自己的问题定义当成事实，也不把模型的重新定义当成事实。
3. 要求模型显式区分事实、推断、假设和待验证问题。
4. 先确认用户意图与规则，再讨论代码实现。
5. 先设计验收场景，再修改代码。
6. 自动化测试主要证明实现符合规则，不能单独证明体验改善。
7. 一轮修改后仍然不好用时，先定位错误层级，再进行最小回退。
8. 不只让模型交付功能，还要让它解释概念、设计变体并帮助完成知识迁移。

最终判断标准是：

> 先怀疑问题定义，再建立问题模型；先明确如何验收，再让模型实现；功能完成后，把模型替自己完成的部分转化为下一次能够参与判断的能力。
