# L1/L2 质检复核队列功能实现任务文档

本文档用于指导后续模型把阶段一 L1/L2 质检能力接入 Inspector，
形成“质检复核队列”。本文档是功能实现任务，不替代规则规格。

规则、阈值、输出字段仍以以下文档为准：

- `docs/阶段一L1_L2质检规则阈值与输出规格_v0.md`
- `docs/阶段一L1_L2质检实现任务文档.md`
- `docs/inspector-panel-reference.md`
- `docs/inspector-external-result-format.md`

## 1. 背景

阶段一已经把 L1/L2 质检定义为可复跑的文件闭环：

```text
标注 JSON
  -> L1/L2 规则扫描
  -> review.tsv + report.json
  -> review_feedback.tsv
  -> threshold_suggestion.json
```

当前问题是：当数据量达到数十万对象、十万级 issue 时，人工直接
编辑 `review_feedback.tsv` 的操作成本过高。需要把复核动作功能化，
让标注员在 Inspector 中完成查看、修改、确认、误报标记和备注，
由代码自动维护反馈文件和阈值建议输入。

## 2. 功能定位

“质检复核队列”不是自动判错系统，而是高风险 issue 的人工复核工作台。

核心原则：

```text
质检问题是任务，不是结论。
标注员在 UI 中复核，不手填 TSV。
阈值建议可以自动生成，但不能自动静默生效。
CLI 负责批量入口，Inspector 负责复核入口和增量入口。
```

## 3. 总体目标

在 Inspector 中新增 L1/L2 质检复核能力，使用户可以：

- 导入 CLI 生成的 `report.json` / `review.tsv`。
- 查看 L1/L2 issue 队列。
- 按规则、严重级别、复核状态筛选 issue。
- 点击 issue 跳转到对应图片和 shape。
- 对 issue 执行复核动作。
- 修改标注后复扫当前文件或当前范围。
- 自动写入或刷新 `review_feedback.tsv`。
- 基于 `report.json + review_feedback.tsv` 生成
  `threshold_suggestion.json`。

## 4. 非目标

本阶段不做以下事项：

- 不批量自动改写正式 JSON。
- 不让阈值建议自动覆盖 YAML profile。
- 不把 QA 临时关系写入正式 shape。
- 不要求 Inspector 直接承担首次超大规模全量扫描。
- 不改变 L1/L2 规则判断口径。
- 不删除现有 Inspector 的 8 条基础检查规则。

## 5. 入口设计

### 5.1 CLI 批量入口

CLI 是大规模初筛入口，适合首次全量扫描和离线批处理：

```text
数据集目录
  -> scripts/run_l1l2_qc.py
  -> report.json
  -> review.tsv
  -> Inspector 导入
```

要求：

- 保留现有 CLI。
- Inspector 能导入 CLI 产物。
- 导入后形成可复核队列。
- 导入不应重新计算规则结果。

### 5.2 Inspector 扫描入口

Inspector 扫描按钮用于交互式增量检查，不作为唯一入口。

支持范围：

- 扫描当前文件。
- 复扫当前文件。
- 扫描当前打开目录的小规模范围。
- 复扫已修改 issue 所在文件。

要求：

- Inspector 扫描与 CLI 必须调用同一套 L1/L2 质检核心。
- 扫描结果字段必须与 `report.json` 中 issue 结构兼容。
- 大规模扫描必须走后台线程，不阻塞 UI。

## 6. Inspector 功能结构

现有 Inspector 为 4 个 Tab：

```text
数据检查 | 数据表格 | 规则配置 | 导出
```

建议扩展为：

```text
质检队列 | 数据表格 | 规则配置 | 反馈统计 | 导出
```

也可以保守实现为：

```text
数据检查 | 质检复核 | 数据表格 | 规则配置 | 导出
```

第一版建议优先实现独立 `质检复核` Tab，避免破坏现有
`IssueListWidget` 的基础检查行为。

## 7. 模块拆分建议

建议新增或扩展以下模块：

| 模块 | 职责 |
|---|---|
| `quality_review_queue.py` | 纯 Python 队列模型，加载 report/review/feedback，维护 issue 状态 |
| `quality_review_widget.py` | PyQt 复核队列 UI，显示 issue、筛选、复核动作 |
| `quality_review_model.py` | Qt table/tree model，可选，用于承载大量 issue |
| `quality_scan_worker.py` | 后台扫描 worker，调用 L1/L2 质检核心 |
| `quality_feedback_writer.py` | UI 动作到 `review_feedback.tsv` 的写入适配，可复用 `feedback.py` |
| `quality_stats_widget.py` | 反馈统计 UI，可第一版简化为摘要栏 |
| `inspector_panel.py` | 接入新 Tab、信号、导入、导出和导航 |

可以不一次性创建全部文件，但职责必须清晰，避免把所有逻辑堆入
`inspector_panel.py`。

## 8. 核心数据模型

### 8.1 队列项

复核队列中的每个 issue 至少包含：

```text
issue_id
run_id
file_path
shape_index
rule_id
rule_name
severity
message
label
group_id
primary_metric_name
primary_metric_value
status
decision
final_action
reviewer
reviewed_at
note
```

其中：

- `issue_id` 是复核反馈的主键。
- `run_id` 用于区分质检批次。
- `status` 是 UI 队列状态。
- `decision` / `final_action` 必须使用 `feedback.py` 中定义的枚举。

### 8.2 状态定义

UI 状态建议：

```text
pending
viewed
fixed
confirmed_error
false_positive
acceptable
needs_discussion
```

状态映射：

| UI 状态 | feedback decision | feedback final_action |
|---|---|---|
| `pending` | 空 | 空或 `none` |
| `viewed` | 空 | 空或 `none` |
| `fixed` | `fixed` | 根据修改类型写入 |
| `confirmed_error` | `confirmed_error` | `none` |
| `false_positive` | `false_positive` | `ignored` |
| `acceptable` | `acceptable` | `ignored` |
| `needs_discussion` | `needs_discussion` | `escalated` |

### 8.3 关联对象

L2 issue 可能涉及多个对象，例如 `face -> head`、`head -> person`、
`keypoint -> person`。第一版必须至少支持主对象跳转：

```text
file_path + shape_index
```

后续增强可支持：

```text
primary_shape_index
related_shape_indices
qa_entity_id
highlight_mode
```

第一版不得因为缺少相关对象高亮而阻断复核流程。

## 9. UI 行为要求

### 9.1 队列显示

队列至少支持显示：

- 状态。
- 严重级别。
- 规则。
- 文件名。
- shape 下标。
- label。
- group_id。
- 指标名和指标值。
- 问题描述。

必须支持筛选：

- 按状态筛选。
- 按 severity 筛选。
- 按 rule_id / rule_name 筛选。
- 只看当前文件。

必须支持排序：

- severity 优先。
- 未复核优先。
- 指标值风险优先。
- 文件路径稳定排序。

### 9.2 导航

单击或双击 issue 时：

- 打开对应 JSON / 图片。
- 选中对应 shape。
- 若 `shape_index = -1`，只跳转文件，不选中特定 shape。
- 导航失败时给出非阻塞错误提示。

### 9.3 复核动作

每条 issue 至少提供这些动作：

- 标记已修复。
- 确认错误。
- 标记误报。
- 标记可接受。
- 标记需讨论。
- 添加备注。
- 跳到上一条未处理。
- 跳到下一条未处理。

动作发生后：

- 更新 UI 状态。
- 更新内存队列。
- 自动写入或刷新 `review_feedback.tsv`。
- 保留原始 issue，不改写 `report.json`。

### 9.4 修改后的复扫

当标注员修改当前文件后，支持：

```text
复扫当前文件
```

要求：

- 只重算当前文件相关 L1/L2 issue。
- 不清空其他文件复核状态。
- 已处理 issue 若不再出现，应保留反馈证据，可在 UI 中显示为
  `resolved_after_rescan` 或类似状态。

第一版可以先不做自动状态推断，但必须避免复扫后丢失已有反馈。

## 10. 文件读写要求

### 10.1 导入

支持导入：

- `report.json`
- `review.tsv`
- 现有 `review_feedback.tsv`

优先级：

```text
report.json 作为完整证据源。
review.tsv 作为轻量问题列表。
review_feedback.tsv 作为复核状态覆盖。
```

如果同时存在 `report.json` 和 `review.tsv`，以 `report.json` 为准。

### 10.2 反馈写入

`review_feedback.tsv` 应由代码维护。

要求：

- 保留已有人工反馈。
- 新 issue 追加为空状态。
- 已有 issue 按 `issue_id` 合并。
- 空 decision 不参与阈值统计。
- 非法 decision / final_action 必须提示错误，不应静默吞掉。

### 10.3 阈值建议

提供入口生成：

```text
threshold_suggestion.json
```

要求：

- 调用现有 threshold suggestion 能力。
- 输出 `approval.status = pending`。
- 不自动修改 YAML profile。
- UI 文案必须明确“建议未生效”。

## 11. 与现有 Inspector 的关系

现有基础检查仍然保留：

- `FlatIndex`
- `ValidationEngine`
- `IssueListWidget`
- `EditableTableWidget`
- `RuleConfigWidget`
- `ExportManager`

新增质检复核队列不应破坏现有 8 条基础规则。

推荐关系：

```text
InspectorPanel
  ├─ 基础数据检查 Tab
  │   └─ 现有 IssueListWidget + ValidationEngine
  ├─ L1/L2 质检复核 Tab
  │   └─ 新增 QualityReviewWidget + QualityReviewQueue
  ├─ 数据表格 Tab
  ├─ 规则配置 Tab
  ├─ 反馈统计 Tab
  └─ 导出 Tab
```

## 14. 实现顺序建议

建议按以下顺序实现，降低风险：

```text
1. 纯 Python 队列模型
2. feedback.tsv 合并和写回
3. 最小 QualityReviewWidget
4. Inspector 新 Tab 接入
5. 点击跳转和一键复核
6. 当前文件复扫
7. 阈值建议入口
8. 统计摘要
9. 大量 issue 性能优化
```

不要先做复杂 UI。第一版只要能稳定导入、跳转、复核、写反馈，
就已经能显著降低人工操作成本。

## 15. 审核重点

后续代码完成后，审核应重点检查：

- 是否把 `review_feedback.tsv` 变成代码维护，而不是继续要求手填。
- 是否保留 CLI 批量入口和 Inspector 增量入口的分工。
- 是否共用同一套 L1/L2 质检核心。
- 是否错误地把阈值建议自动应用到 YAML。
- 是否破坏现有 Inspector 基础检查。
- 是否在复扫或导入时丢失已有人工反馈。
- 是否把 PyQt 依赖引入 `quality/` 纯 Python模块。
- 是否能承受十万级 issue 的加载和筛选。
