我有一个标注工具，X AnyLabeling。它本身已经有完整的数据获取、处理结构和输出结构。但是它有一个限制，就是只能处理当前加载的图片和对应的标签。

我想给它增加一个缩略图类似的窗口，有点像文件管理器的缩略图。它可以将跨图片的标签一次性的加载到一个窗口里。或者说，它以标签为一个观察条件，将加载的数据集全部都做一个统一的管理。好吧，这个是我的描述。现在我的疑问是，这个功能在设计的时候，应该不再需要对数据的加载和处理。它只需要获取我对某个具体标签的处理结果，然后再调用主程序中的方式。直接作用到 JSON 上应该就可以了。这种设计的想法，你觉得有什么问题？

你的思路方向是对的——新窗口**不应该重复造一套数据处理的轮子**，应该复用主程序已有的逻辑。但“直接作用到 JSON 上”这一点，我认为是这个设计里最大的隐患。具体说几个问题：
## 1. 核心问题：JSON 文件 ≠ 程序的真实状态
X AnyLabeling 的架构是典型的“内存状态 + 落盘时写文件”模式：
- 画布上显示的标签来自**内存中的 shapes / label list**
- JSON 只在保存（Ctrl+S、自动保存、切换文件）时才写入
- 撤销/重做（undo/redo）操作作用在内存状态上
如果你让缩略图窗口**绕过内存状态直接改 JSON**，会出现：
- 当前打开的图片在画布上还显示旧标签，而磁盘上已经是新的 → 状态分裂
- 用户在画布上有未保存的修改，你的窗口直接写文件 → **覆盖/丢掉用户的修改**
- 你改了 JSON，但主程序的 undo 栈完全不知情，用户一个 Ctrl+Z 行为变得不可预测
所以正确的做法不是“作用到 JSON 上”，而是**作用到主程序的数据模型上**，由主程序原有的保存逻辑去写 JSON。
## 2. “不需要数据的加载和处理”——需要修正一下
你说新功能不需要数据加载，严格来说不成立，但它可以**完全委托**给已有逻辑：
- 缩略图窗口要展示**整个数据集**的标签，而主程序当前只加载了一张图。所以“把其他图片的标签读进来”这件事，本身就是要新增的加载工作——只是可以复用主程序已有的 label 文件解析函数，而不是自己写一遍
- 正确的心智模型是：**新窗口是一个 View + 命令派发器，不是数据的所有者**
## 3. 建议的结构
```
主程序已有的部分：
  数据模型（shapes、label 列表、文件列表、dirty 标记）
  加载/保存逻辑
  各类标签操作（改名、删除、改颜色…）
新增部分（缩略图窗口）：
  ├── View：以"标签"为维度聚合展示（只读地聚合、渲染）
  └── Controller：
      ├── 对当前已加载文件 → 通过 signal/slot 调用主程序的既有操作
      └── 对未加载文件 → 先调用主程序的加载逻辑，操作后按原有规则保存
```
几点具体建议：
1. **用信号槽解耦**，不要让缩略图窗口直接持有和修改主窗口的内部对象。它发出“把标签 A 改名为 B”这样的**命令**，由主程序执行。
2. **单一数据源**：聚合展示的数据（比如统计每个标签出现在哪些文件）通过订阅主程序的状态变化信号来刷新，而不是自己维护一份副本后去同步。
3. **批量操作要考虑事务性**：比如批量删除一个标签涉及几十个文件，中途某个文件解析失败怎么办？建议按文件粒度处理，失败的记录下来报告，而不是整体中断。
4. **注意 dirty 状态**：对未加载文件的操作，加载→修改→保存这条链路要和主程序的自动保存/切换保存行为协调好，避免“半加载”状态的文件污染后续操作。
5. **性能**：数据集大时不要一次性解析所有 JSON，考虑懒加载 + 只读元数据（比如先只扫每个文件的 label 集合，点开详情再解析完整 shape）。
## 总结
你的设计里“复用主程序的处理方式”这一半是对的，另一半“直接改 JSON”是错的。**JSON 是输出物，不是数据源**；数据源是主程序的内存状态。把新窗口定位成“视图 + 命令转发层”，所有修改都通过主程序既有的操作入口走，落盘交给既有的保存机制——这样画布、标签列表、undo/redo、缩略图窗口四者天然保持一致。


所以这是一个聚合状态下的数据操作。那么它的操作数据实际上也是提前绕过了主程序的内存加载的吧？因为主程序本身只加载一张图片。啊，不对，主程序会将所有的标签都加载到内存里。那是可以实现，但是修改之后写回的话也是到内存里，那什么时候才写回到 JSON 里呢？


你这里其实把两个概念混在一起了，先拆开：
## 主程序“加载所有标签”指的是什么
X AnyLabeling 加载到内存的是**当前这张图的全部 shapes**，不是整个数据集的所有标签。它的模式是：
```
切换文件 → 卸载当前 shapes → 加载新文件的 JSON → 等待编辑 → 
（保存触发）→ 从内存 shapes 序列化写回 JSON
```
所以**整个数据集的标签并不在主程序内存里**。你的聚合窗口如果想一次看全数据集，必然要引入一个“额外加载”的东西——这绕不开，只能选它以什么形式存在。
## 两种可选结构
**结构 A：聚合窗口只持有一个轻量索引（推荐起步）**
窗口自己扫描所有 JSON，但只缓存元数据（每个文件有哪些标签、数量），用于聚合展示。一旦你要**执行操作**，流程是：
```
对文件 F 执行修改 X：
  1. 若 F 是当前画布上的文件 → 发信号给主程序，走既有命令，改的是内存状态
     → 写回时机完全交给主程序原有规则（Ctrl+S / 自动保存 / 切换文件时）
  2. 若 F 不是当前文件 → 让主程序（或复用其解析/序列化模块）加载 F → 修改 → 立即保存
     → 写回时机 = 操作完成的那一刻，一次一文件
```
这就回答了你的问题：**对非当前文件，写回不应该是“等等再说”，而是当场完成**。原因很简单——这些文件没有画布、没有 undo 栈、没有 dirty 标记，主程序的“延迟保存”机制对它们没有任何意义，反而引入了风险（比如程序崩了、或用户中途打开那张图造成冲突）。逐文件“加载→改→写回”是一个小事务，天然是安全的。
**结构 B：把数据集级模型提升进主程序内存**
让主程序维护全数据集的标签缓存，画布只是它的一个视图。这是更彻底的架构升级，好处是聚合操作全在内存进行、写回可以统一调度；代价是你要自己解决：每文件的 dirty 追踪、内存占用（大数据集）、与现有 per-file 逻辑的一致性。除非你计划把整个工具往“数据集管理器”方向长期演化，否则不建议第一步就做这个。
## 几个必须想清楚的点
1. **当前文件是特例**。对正在画布上编辑的文件，绝不能走“直接加载改写”路径，必须走主程序内存状态，否则用户未保存的编辑会被你覆盖。判断依据很简单：文件路径 == 主程序当前加载的路径。
2. **批量操作 = 一串小事务，不是一个大事务**。批量删除标签 X：逐文件处理，某个文件解析失败就跳过并记录，最后汇总报告。不要先全部改内存最后一起写——中途任何失败都会留下不确定状态。
3. **不可撤销是要明确接受的**。X AnyLabeling 的 undo 是内存级的，一旦你对非当前文件“当场写回”，这个操作就不可 Ctrl+Z 了。建议在 UI 上明示（比如“此操作将立即保存，不可撤销”），或自己做一个简单的操作日志做补偿性回滚。这不是技术障碍，是产品设计上要诚实的地方。
4. **写回时要遵守主程序的保存细节**，比如输出格式（版本号、shape 字段、文件路径的相对/绝对写法、是否输出 imagePath/imageData）。最稳妥的做法是让序列化调用主程序同一个 `save_labels`/序列化函数，而不是自己拼 dict——否则格式细节分叉，将来主程序升级格式你这边就悄悄产生脏数据了。
一句话总结：对非当前文件，答案就是**操作时立刻写回 JSON，一文件一事务**；对当前文件，写回时机沿用主程序既有机制，你只负责发命令。


所以我前面两轮的需求描述，总结起来，这个缩略图到底是一个什么样的功能结构设计呢？

把前两轮的讨论收敛掉，这个功能可以定义成一句话：
> **它是一个“数据集级的标签聚合视图 + 命令派发器”，本身不拥有数据、不拥有保存职责，只做两件事：聚合展示、转发操作。**
## 结构总览
```
┌─────────────────────────────────────────┐
│           缩略图/聚合窗口（新增）           │
│                                         │
│  ┌─────────────┐    ┌────────────────┐  │
│  │ 聚合索引(只读) │    │  操作命令入口     │  │
│  │ 文件→标签→数量 │    │ (改名/删除/跳转…) │  │
│  └──────┬──────┘    └───────┬────────┘  │
│         │                   │           │
│         │ 订阅刷新            │ 发命令      │
└─────────┼───────────────────┼───────────┘
          ▼                   ▼
┌─────────────────────────────────────────┐
│        主程序（既有，改造最小）             │
│                                         │
│  加载/解析模块 ── 序列化/保存模块          │
│  画布内存状态 ── undo/redo ── dirty 标记   │
│  文件列表管理                             │
└─────────────────────────────────────────┘
          ▲
          ▼
     磁盘上的 JSON 文件集合（唯一持久层）
```
## 五个组成部分
**1. 聚合索引（窗口自己的，只读元数据）**
主程序内存里只有当前一张图的 shapes，所以窗口需要自己扫一遍数据集 JSON，建立轻量索引：`文件 → 标签集合 → 数量`。懒加载、按需解析详细 shape。它是**衍生物**，磁盘 JSON 变了它就失效重扫，绝不能反过来当数据源。
**2. 视图层（以标签为观察维度）**
和文件管理器缩略图的本质区别：文件管理器以“文件”为单元，你以“**标签**”为单元——点一个标签，看到的是它散布在哪些文件里。索引换一个聚合方向就能支撑。
**3. 命令派发层（核心设计决策所在）**
所有修改操作，窗口自己**一个都不执行**，只声明意图（“把标签 A 改名成 B，涉及这 40 个文件”），然后按目标文件分两条路：
- **当前画布上的文件** → 信号发给主程序，走既有编辑命令，改内存状态，undo 可用
- **其余文件** → 调用主程序的加载→修改→保存链路，**当场写回 JSON，一文件一事务**，失败跳过并记录
**4. 写回规则（不可混淆的两套时机）**
- 当前文件：沿用主程序原有时机（Ctrl+S / 自动保存 / 切换时）
- 非当前文件：操作完成即落盘，不进任何延迟队列
- 唯一约束：当前文件的路径必须实时判断，防止用户刚切图造成两条路径撞车
**5. 刷新机制**
主程序在“保存完成 / 文件加载 / 画布编辑”时发信号，窗口收到后只让索引的**对应文件条目**失效重扫，不整体重建。
## 这个设计里你原方案的“对与错”
| 你的想法 | 判定 | 修正后 |
|---|---|---|
| 不重复造数据处理的轮子 | ✅ 对 | 解析/序列化全部复用主程序函数 |
| 不需要数据的加载和处理 | ⚠️ 半对 | 只读索引仍要新写，但只是元数据扫描 |
| 直接作用到 JSON | ❌ 错 | 改为作用到“主程序内存状态 或 主程序加载-保存链路”，JSON 只能由主程序的保存逻辑写 |
## 一句话定位
对主程序而言，它是**一个订阅了状态、会发命令的外挂面板**——类似把左下角那个 label list 放大到一个数据集的尺度，但正因为它跨出了单文件，它必须遵守“不碰当前文件的落盘、非当前文件即时事务落盘”这两条纪律，其余全靠委托。


后面还有两个问题。
1. 数据集通过略缩图回写到内存之后，应该怎么给到 JSON？这个过程是不通过主画面进行的。
2. 通过主画面对数据集产生的修改，应该怎么在略缩图中进行体现？也就是版本控制问题。

这两个问题正好是这个设计的两处“接缝”，分开说。
## 问题 1：不经过主画面，怎么写回 JSON
先纠正一个概念：**绕过的应该是“画布界面”这条路径，而不是“保存模块”**。X AnyLabeling 的保存链路拆开看是三段：
```
画布编辑 → 内存 shapes → 序列化函数 → 写文件
```
主画面只是前两段的宿主。你要复用的是**第三段**（序列化 + 写文件），这才是保证格式一致性的关键。所以非当前文件的完整流水线是：
```
1. 判断目标文件 F 是否 == 当前画布文件
   是 → 改走主程序命令路径，退出本流程
2. 调用主程序的解析函数读取 F 的 JSON → 得到 shapes
3. 对 shapes 执行修改（改名/删除/…）
4. 调用主程序同一个序列化函数生成新 JSON
   —— 关键：字段版本、imagePath/imageData、shape 结构全部
      与主程序保存时一致，不许自己拼 dict
5. 原子写回：写临时文件 → 校验 → rename 覆盖原文件
   （防止写一半崩溃留下损坏的标注文件）
6. 发出"F 已变更"信号，通知索引层
```
注意第 3 步只改数据、不经过画布，所以没有 undo 栈参与——这就是前面说过的“即时事务、不可撤销”的根源，流程上必须一步完成，不留中间状态。
还有一个隐藏坑：**ImageData 字段**。有些 JSON 里嵌了 base64 图片数据，解析和序列化时不能丢也不能重复编码，这更是“必须用同一个序列化函数”的理由。
## 问题 2：主画面的修改如何反映到缩略图
先明确：这**不需要版本控制**。版本控制要解决的是“多个写入方各自持有副本、需要合并”的问题；而我们上一轮已经确立了纪律——**磁盘 JSON 是唯一持久层，索引只是衍生物**。衍生物不需要版本号，只需要**失效-重建**。
所以把这个问题降维成一个“索引同步”问题，规则是三条状态来源各管一段：
**来源一：主程序保存/加载事件（主要通道）**
主程序在既有代码里已经有这些时机，只需要在对应位置补一个信号发射（或在函数级别做薄封装/事件监听）：
| 时机 | 缩略图收到信号后做什么 |
|---|---|
| 保存完成（写盘后） | 重扫该文件的 JSON，更新索引条目 |
| 加载新文件 | 索引里给该文件打上“当前编辑中”标记 |
| 画布上标签增删改名（内存级，未保存） | 只更新该文件的“待保存”标记，**不动索引数据** |
**来源二：内存领先于磁盘的窗口期（最容易出 bug 的地方）**
用户在画布上改了标签但还没保存时，磁盘 JSON 是旧的。此时缩略图如果只认磁盘，显示的就是过期信息。两种处理策略：
- **简单版（推荐）**：对“当前编辑中且 dirty”的文件，缩略图展示时**实时向主程序内存查询**该文件的标签集合，而不是读索引。逻辑上等于：“当前文件的真相在内存，其他文件的真相在磁盘，索引只是磁盘的缓存”。一行判断路径，几乎没有同步复杂度。
- 复杂版：维护 per-file 修订计数器、做 diff——这就是真的在做版本控制了，收益极低，不建议。
**来源三：外部变更兜底**
用户用别的编辑器改了 JSON、或缩略图自己批量写回，索引层可以比对 `mtime` 或在每次窗口获得焦点时对差异文件重扫。这是兜底，不是主通道。
**整体数据流就变成：**
```
磁盘 JSON ◄──保存── 画布内存 ──信号──► 缩略图索引
    ▲                                    │
    └──── 批量操作直接写回（事务式） ────────┘
              │
              └── 发"已变更"信号 → 索引局部失效重扫
```
## 回答你的两个问题，各一句话
1. **写回 JSON**：绕过画布界面，但不绕过保存模块——解析、序列化、写盘全部调用主程序既有函数，逐文件“读→改→原子写”一次完成，写完发信号。
2. **版本同步**：不做版本控制，做**失效-重建**。索引永远从属于磁盘 JSON；唯一例外是“当前编辑中的文件”以内存为准；主程序在保存/加载/编辑三个时机发信号，索引按文件粒度局部刷新。
这样设计后你会发现，整个系统里没有任何一份需要“合并”的数据——每一时刻每个文件的真相都只有一处，冲突问题在结构上就被消掉了，而不是靠同步算法解决。


所以这个缩略图一旦修改，就直接写入 JSON，不可以进行撤回。

对，但要加上准确的限定，这个结论只覆盖一半场景：
## 准确的说法
| 操作目标 | 路径 | 可撤销性 |
|---|---|---|
| **当前画布上的文件** | 走主程序既有命令 → 改内存 → 按原时机保存 | ✅ 可撤销（主程序 undo 栈照常工作） |
| **非当前文件（绝大多数情况）** | 加载 → 改 → 立即原子写盘 | ❌ 写下即成事实 |
批量操作里通常几十个文件只有一个可能是当前文件，所以**从体感上你的总结成立：缩略图的批量修改基本是不可撤销的**。
## 为什么“做成可撤销”代价很高
想让非当前文件也支持 undo，你得自建一套跨文件的 undo 栈，意味着：
1. 每次操作前把被改文件的**完整 JSON 原文**快照留底（内存或临时目录）
2. Ctrl+Z 时恢复快照——但要处理“撤销前用户恰好打开了那个文件并做了新编辑”的冲突
3. 撤销本身又是一次磁盘写操作，理论上还需要 redo……
这本质上是在主程序单文件 undo 体系之外再造一个平行体系，且两者会互相干扰。为了缩略图的便利性付出这个复杂度，不划算。
## 务实的补偿方案（不叫 undo，但兜住风险）
既然结构上放弃 undo，建议在产品层面做这三件事，成本都很低：
**1. 操作前确认 + 影响范围预览**
批量删除标签 X 时，弹窗不只说“确定吗”，而是列出“将影响 37 个文件、共 142 个 shape”——让用户在写盘前就知道后果，把一半的“后悔”消灭在发生前。
**2. 软备份：改写前把原文件挪到回收目录**

## 缩略图数据：三个层级，两种处理策略
缩略图需要的数据是 `shape 的 bbox + ID + 标签`（来自 JSON）和**图像内容**（来自图片文件）。成本完全不同：
| 数据 | 体量 | 处理策略 |
|---|---|---|
| bbox/ID/标签元数据 | 每条几十字节 | 已在聚合索引里，内存常驻没问题 |
| 原始图像 | 每张几百 KB～几十 MB | **绝不常驻**，按需解码 |
| 生成后的缩略图 | 每张几 KB～几十 KB | 内存 LRU 缓存 + 可选磁盘缓存 |
所以答案是：**进内存的是“解码→裁剪→缩放”的产物，而不是原图**。原图是一个流式输入，处理完即释放。
## 真正的性能瓶颈和解法
瓶颈不在读 JSON（那个很快），而在**图像解码**：为了裁一个 100×100 的 bbox，你可能要解码一张 4000×3000 的原图。解一次几百毫秒，几百个缩略图就会卡死。对策按优先级：
**1. 只生成可见的（虚拟化）**
缩略图网格用虚拟滚动——视口里能看到多少个就生成多少个，滚动时按需请求、离开视口的从 LRU 里挤出去。这是最重要的一条，能把工作量从“全数据集”降到“一屏”。
**2. 解码在后台线程池**
生成请求扔进 `QThreadPool`，UI 先显示占位图（标签名 + bbox 尺寸文字），缩略图算好了再替换。解码用局部裁剪：`QImage.load → copy(bbox) → scaled(缩略图尺寸)`，原图对象出作用域即释放。
**3. 磁盘缓存生成结果**
```
.cache/thumbs/{图像文件hash}/{shape_id}_{bbox hash}.png
```
key 里带上 bbox 的哈希是为了处理“shape 被移动/调整过”——bbox 变了缓存自动失效，不需要额外逻辑。缓存命中时连解码都不用做，第二次打开几乎是零成本。以 PNG 存小图（比如最长边 128px）每张几 KB，16 万标签也就几百 MB 上限，实际远小于此（你通常只看某个标签的子集）。
**4. 缓存失效的判定源**
和上一轮的索引同步规则完全一致：**主程序保存信号 / 缩略图自己写回的信号**触发对应文件重扫时，顺带让该文件的缩略图缓存失效。不要用轮询 mtime 做主通道。
## 还有一个多 shape 共享解码的优化
同一个图像文件里往往有多个 shape。逐个 shape 解码同一张原图是浪费，应该**按图像文件聚合解码**：视口内需要某图像的 K 个 bbox 时，解码一次，裁 K 次，再逐个缩放落盘。任务调度的粒度是“图像文件”而不是“shape”。
## 总结流水线
```
视口可见的 shape 集合
  → 按图像文件分组，查磁盘缓存
  → 未命中：后台线程解码原图一次 → 裁剪多个 bbox → 缩放 → 写缓存
  → 命中/生成完成 → 通知 UI 替换占位图
  → 内存里只留 LRU 里的成品缩略图（上限比如 2000 张）
```
一句话：**元数据常驻内存，原图即用即弃，缩略图两级缓存、只按可见性生成**。这样 16 万标签的数据集也不会有感知延迟——因为你任何时刻实际处理的都只是视口里那一两百个。

可以，而且这个方案在你的规模下是合理的升级。但要先把定位说对，同步问题才有正确答案：
## SQLite 的定位：它是“索引层”的升级实现，不是第二个数据源
原来设计里的“内存聚合索引”换成 SQLite，数据流不变：
```
获取 = SQLite 查询（代替内存扫描）
处理 = 查询结果 + 选中集合（不变）
写回 = JSON 落盘 + SQLite 行更新（同一事务窗口内完成）
```
**JSON 仍然是唯一真相，SQLite 是它的衍生物**——这个原则不因为引入数据库而改变。一旦你把 SQLite 当成和 JSON 平级的数据源，才真正产生“双向同步”问题；定位摆对，就只有单向的“衍生物维护”。
## 它到底快在哪
诚实地说，16 万条记录的过滤聚合，纯内存 dict 也就毫秒级，SQL 不一定“更快”。SQLite 真正的收益是另外几点：
| 收益 | 说明 |
|---|---|
| **跨会话持久化** | 内存索引每次启动全量重扫 16 万 shape；SQLite 建好后启动即查，只有增量扫描 |
| **复杂查询** | 按标签过滤 + 分页 + 按文件分组 + 统计，都是现成 SQL，`LIMIT/OFFSET` 天然支撑你的 50~100 分批 |
| **内存占用** | 不用整个索引常驻内存，按查询结果取 |
| **调试性** | 数据集标签分布可以直接开 SQL 看，开发期很省事 |
对你最大的实惠是第一条和第二条。
## 同步问题：不做“定时同步”，做“写时同更”
不要设计任何周期性的 JSON↔SQLite 同步任务，那样迟早出现不一致。规则很简单：
**规则一：谁写 JSON，谁顺手更新 SQLite，同一操作窗口内完成**
你的写回事务扩成五步：
```
备份原 JSON → 写新 JSON → 更新 SQLite 中该文件对应的行 → 原子完成
```
改名操作在 SQLite 里就是一条 `UPDATE shapes SET label=? WHERE shape_id=?`，开销可以忽略。主画布路径也一样——主程序保存信号触发的“索引重扫”，在 SQLite 方案下换成“重扫该文件并更新对应行”，或者直接读新 JSON 重插该文件的行。
**规则二：数据库里存校验字段，用于发现漂移**
每条文件记录带上 JSON 的 `mtime`（或内容哈希）。这样：
- 启动时：`SELECT * FROM files WHERE mtime_matches=0`，只重扫有变化的文件 → 增量更新，秒级
- 任何你没想到的外部改动，都能被检测出来
**规则三：留一个“重建索引”命令兜底**
删库重扫，作为最后手段。有了规则二，这个按钮平时根本用不上，但出问题时能一键自愈。
## 一个不要越界的提醒
**SQLite 里只存索引字段**（shape ID、标签、bbox、所属文件、mtime），不要存完整 shape 数据，更不要让它承担写回时的 shape 修改。写回时“读完整 JSON → 改 → 写回”这条链路保持不变。
如果反过来把完整 shape 镜像进 SQLite、直接改库再导出 JSON，你就造出了两个写入口，JSON 和 SQLite 谁是真相说不清了——前面所有设计里辛苦维持的“单一真相”就崩了。数据结构的分叉也迟早出现（主程序给 shape 加字段，你的镜像没跟上）。
## 一句话
SQLite 替代的是原来的内存索引，**“更快”主要体现在启动免全量扫描和 SQL 查询便利上**；同步问题不需要发明新机制——写 JSON 的那个事务顺手更新对应的行，加上 mtime 校验做漂移检测和增量重建，整个系统仍然是单一真相 + 衍生缓存的结构，只是缓存从“内存中的 dict”升级成了“磁盘上的库”。

写回**是**闭环的一部分，不是闭环之后的事。真实顺序是：确认 → 写回 → 变更通知 → 索引/缓存刷新 → 视图更新 → 下一批。你描述的“先闭环、再写回”会让写回变成一个悬空的收尾动作——但那时数据已经变了，闭环其实早就该发生了。
**调整三：整个流程是 ③④⑤⑥ 的循环，不是一次性走完。**
你列的 1-6 像一条直线，但这个功能的核心价值恰恰在于批量循环：看一批 → 改一批 → 退场一批 → 下一批。一个标签下 800 个 shape，用户会循环 8-16 轮，中间还可能切换观察条件（改到一半换个标签看）。所以收口时心智模型应该是一条环形流水线，而不是六个步骤。
## 一句话总结使用体验
用户视角其实只有三个动作：**打开窗口、选标签、循环“选中→改名→自动流转到下一批”**。扫描是启动时的后台噪音，写回和刷新是每次确认后的自动收尾，SQLite 和 JSON 的同步藏在事务里不可见。你要做到的是：用户感知不到任何“同步”“扫描”“保存”这些词，但每一步底下都有刚才设计的那些纪律在兜底。
