# Canvas 扩展同步维护指南

这份文档用于维护基于 `canvas.py` 的自定义扩展，尤其适用于未来上游把 `canvas.py` 拆分成多个模块之后，继续同步版本、迁移扩展功能。

当前文件位置：

```text
anylabeling/views/labeling/widgets/canvas.py
```

## 1. 为什么 `canvas.py` 是关键节点

`canvas.py` 当前不是单纯的绘图组件，它更像一个集中式核心模块，包含：

- 画布渲染
- 鼠标事件
- 键盘事件
- 标注对象创建
- 标注对象选择
- 标注对象移动、缩放、旋转
- hover 高亮
- 自动标注交互
- mask 相关交互
- cuboid 相关交互
- 十字线显示
- 缩放和平移
- 对外信号分发

所以如果自定义功能直接改在 `canvas.py` 里，上游后期拆分文件时，最容易出现同步困难。

## 2. 维护原则

不要只记文件名和行号，要记“功能锚点”。

推荐记录：

- 功能流程
- 信号名
- 方法名
- 参数
- 返回值
- 状态字段
- 配置项
- 调用方
- 影响范围
- 验证步骤

不推荐只记录：

- 第几行代码
- 某个临时变量
- 某个未说明用途的代码片段

## 3. 当前值得关注的稳定锚点

`Canvas` 当前暴露了多个信号，这些信号比具体代码行更适合作为扩展锚点：

```text
zoom_request
scroll_request
mode_changed
new_shape
show_shape
selection_changed
shape_moved
shape_rotated
vertex_selected
auto_labeling_marks_updated
auto_decode_requested
auto_decode_finish_requested
shape_hover_changed
split_position_changed
edit_label_requested
```

如果上游拆分 `canvas.py`，同步时优先搜索这些锚点是否迁移到新文件、新类或新控制器中。

每个自定义功能都建议单独记录一份“扩展卡片”。

## 5. 示例：加载图片时避免全量扫描

```text
扩展功能名：加载图片时避免全量扫描

原始目标：
减少打开图片或加载标签时的卡顿。

影响的功能流程：
导入图片 / 切换图片 / 加载标签 / 自动任务触发。

依赖的文件：
anylabeling/views/labeling/widgets/canvas.py
anylabeling/views/labeling/label_widget.py

依赖的类：
Canvas

依赖的方法：
需要由 AI 根据当前代码实际搜索确认，不要只凭记忆填写。

依赖的信号：
auto_decode_requested

依赖的配置项：
auto / manual 相关配置项，需要由 AI 搜索确认具体名称。

新增或修改的参数：
需要由 AI 检查函数签名、默认值、调用方是否全部同步。

涉及的状态字段：
is_auto_labeling
is_loading

调用方：
需要由 AI 搜索所有 connect、emit、方法调用位置。

被调用方：
需要由 AI 搜索信号连接到哪里、回调函数在哪里。

预期行为：
打开图片时不自动触发全量扫描，只在用户手动触发时执行。

实际验证步骤：
1. 打开一个包含大量图片的目录
2. 观察首次加载是否卡顿
3. 切换到下一张图片
4. 确认没有自动扫描全量图片
5. 手动触发任务，确认功能仍然可用

可能副作用：
自动标注不再自动执行、标签状态不刷新、文件列表不更新、手动按钮失效。
```

## 6. 上游拆分后怎么同步

当上游把 `canvas.py` 拆分后，不要先问“原来的代码在哪一行”，而是按下面顺序迁移：

1. 搜索原来的信号名是否还存在
2. 搜索原来的方法名是否还存在
3. 搜索原来的配置项是否还存在
4. 搜索原来的状态字段是否还存在
5. 找到新的调用链
6. 找到新的文件职责划分
7. 把自定义扩展迁移到新的最小接入点
8. 按验证步骤重新测试

推荐让 AI 执行的搜索任务：

```text
请在当前项目中搜索以下锚点，确认它们是否还存在、是否迁移了位置、调用链是否变化：

- <信号名>
- <方法名>
- <配置项>
- <状态字段>

请输出：
1. 新文件位置
2. 新类名
3. 新方法签名
4. 调用方
5. 被调用方
6. 与旧版本的差异
```

## 7. 如何提示 AI 注意接口层细节

接口层最容易漏这些细节：

- 函数参数
- 参数默认值
- 参数类型
- 返回值
- 信号携带的数据
- signal / slot 连接关系
- 状态字段初始化位置
- 配置项默认值
- 配置项读取位置
- 调用方是否全部修改
- 测试或验证步骤是否覆盖旧行为

你可以直接用下面这段提示 AI：

```text
请特别注意接口层细节，不要只看功能是否能跑。

请逐项检查：
1. 所有相关函数的方法签名是否变化，包括参数名、参数顺序、默认值、类型、返回值
2. 所有调用方是否已经同步修改，不能只改定义不改调用
3. 所有信号的 emit 参数是否和 connect 的槽函数参数匹配
4. 所有配置项是否有默认值、读取位置、保存位置、运行时应用位置
5. 所有新增状态字段是否在初始化、重置、切图、清空、关闭窗口时处理
6. 是否存在旧逻辑仍然自动触发，导致手动模式失效
7. 是否存在功能被拆分到新文件后，只迁移了一半调用链

请输出一张“接口细节核对表”，不要只给结论。
```

## 9. 让 AI 帮你迁移扩展时的完整模板

```text
我在旧版本中基于 canvas.py 做了自定义扩展。现在上游可能已经拆分了 canvas.py，我需要把扩展同步到新版本。

请不要只按文件名查找，请按功能锚点迁移。

我的扩展功能：
<描述扩展功能>

旧版本依赖的锚点：
信号：<列出信号>
方法：<列出方法，如果不确定就写“不确定，请帮我搜索”>
配置项：<列出配置项>
状态字段：<列出状态字段>

请你执行以下任务：
1. 在新版本中搜索这些锚点是否还存在
2. 找出它们迁移到了哪些文件、类、方法中
3. 对比旧版本和新版本的接口差异
4. 特别检查参数、默认值、返回值、信号 emit 参数、slot 参数是否匹配
5. 找出所有调用方，确认是否需要同步修改
6. 给出最小迁移方案，不要大范围重构
7. 给出迁移后的验证步骤

请最后输出：
1. 功能迁移结论
2. 接口细节核对表
3. 最小修改方案
4. 验证清单
```

## 10. 版本同步建议

为了降低以后同步难度，建议：

- 自定义扩展尽量独立成小提交
- 每个提交只解决一个功能点
- 不要把格式化、重构、业务改动混在一起
- 能通过信号接入就不要直接改大段方法体
- 必须修改原方法时，在扩展卡片中记录原因
- 每次同步上游前先备份分支
- 同步后先跑最小验证流程，再继续开发新功能

## 11. 最重要的一句话

未来 `canvas.py` 拆分后，真正要追踪的不是“代码原来在哪个文件”，而是：

```text
这个功能在用户流程中发生在哪里，它依赖哪些信号、方法、配置项、状态字段，以及这些接口在新版本中迁移到了哪里。
```
