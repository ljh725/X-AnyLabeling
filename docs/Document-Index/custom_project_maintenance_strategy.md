# 二次开发项目长期维护策略

这份文档用于说明：当你基于 X-AnyLabeling 做了大量业务定制后，后续应该如何维护项目、是否继续同步上游、以及怎样降低未来迁移成本。

## 1. 总体原则

如果你的项目已经因为垂直业务需求，和原始版本产生了明显差异，那么维护策略就不应该再只以“完整跟随上游”为目标。

更合理的方式是：

- 保留上游作为参考源
- 自己的仓库作为主线
- 只选择性吸收上游有价值的改动
- 让业务逻辑和通用能力分层维护

## 2. 什么时候还值得继续同步上游

以下情况通常适合继续跟进上游：

- 你还大量复用上游的核心框架
- 上游仍在持续修复通用 bug
- 上游的性能优化对你也有价值
- 上游的新功能与你的业务流程高度相关
- 合并一次上游改动的成本还可接受

如果满足这些条件，继续同步上游通常是划算的。

## 3. 什么时候不必强求完整同步

以下情况说明你已经逐渐走向独立项目形态：

- 你的操作流程和原版差异很大
- 你的界面、任务流、数据结构已经明显不同
- 上游每次合并都要解决很多冲突
- 上游新增功能对你的业务帮助不大
- 你的功能是围绕特定业务深度定制的

如果已经是这种状态，就不要再以“完整同步原版”为目标。

## 4. 推荐的长期维护方式

### 4.1 保留上游远端

建议保留上游仓库为 `upstream`，只把它作为参考源：

- 用来查看 bugfix
- 用来参考通用优化
- 用来借鉴结构变化
- 用来在必要时挑选性合并

### 4.2 你的项目作为主线

你自己的仓库应该是主仓库，后续开发都围绕你的业务需求展开。

### 4.3 只同步有价值的改动

建议只吸收以下类型的上游改动：

- 通用 bug 修复
- 安全修复
- 性能优化
- 你业务也会用到的核心能力
- 不会破坏你现有流程的改动

### 4.4 业务层和通用层分离

建议把代码按职责拆开：

- 通用层：图片加载、画布、保存、快捷键、基础 UI、模型接口
- 业务层：你自己扩展的标注流程、特殊任务、私有规则、专用配置
- 适配层：把你的业务逻辑接入原项目或新架构的中间层

这样以后上游拆分核心文件时，你的迁移成本会低很多。

## 5. 当项目越来越像另一个项目时怎么办

如果你的改动已经让项目变成了另一个产品，那么维护方式要切换成“自有项目维护”模式：

- 你的仓库就是正式版本
- 原项目只是参考和补丁来源
- 不再追求原样同步全部目录结构
- 只维护你需要的功能和兼容性

这时最重要的是：

- 维持自己的主分支稳定
- 记录清楚每次业务改动
- 保留关键接口的兼容信息
- 给自己的扩展写文档

## 6. 建议的项目结构

如果你有长期维护需求，建议把项目逻辑分成几类：

- `core/`：通用能力
- `business/`：业务定制逻辑
- `adapters/`：对接原项目或新架构的适配层
- `docs/`：操作说明、节点说明、同步规则、AI 提示模板
- `tests/`：关键流程验证
- `changelog/`：版本变化记录

如果你现在还不能重构目录，至少也要在逻辑上区分这些职责。

## 7. 降低未来维护成本的方法

### 7.1 尽量通过锚点扩展

尽量不要把业务功能直接绑死在单个巨大脚本的内部细节上。

优先使用：

- 信号
- 配置项
- 独立回调
- 插件式入口
- 适配层

### 7.2 每个扩展单独记录

每个业务功能都建议记录下面这些内容：

- 功能目的
- 影响流程
- 依赖接口
- 参数变化
- 触发条件
- 验证步骤
- 可能副作用

### 7.3 每次同步上游前先分离业务改动

如果你的业务改动比较多，建议先把业务提交整理清楚，再做上游同步。

这样更容易判断：

- 哪些冲突是上游造成的
- 哪些冲突是你自己的业务改动造成的
- 哪些改动应该保留
- 哪些改动可以丢弃

## 8. 推荐的版本策略

### 8.1 前期

- 尽量跟随上游
- 逐步做业务定制
- 先保持兼容

### 8.2 中期

- 选择性同步上游
- 业务层开始分离
- 关键扩展写文档

### 8.3 后期

- 自己的项目独立维护
- 上游只作为参考
- 只挑必要的修复和优化吸收

## 9. 判断标准

你可以用下面几个问题判断是否还要继续完整同步上游：

1. 上游的改动对我还有没有实际价值？
2. 合并一次上游是否会引入很多冲突？
3. 我的业务流程是否已经和原版完全不同？
4. 继续同步的成本是否高于收益？
5. 我是不是已经在维护一个新的项目，而不是简单 fork？

如果大多数答案偏向“否”，说明你应该开始按独立项目来维护。

## 10. 最终建议

不要把“继续同步原始版本”当成唯一目标。

更实际的策略是：

- 保留上游参考价值
- 以自己的业务需求为主
- 只吸收真正有用的上游改动
- 让项目结构逐步适应你的业务
- 把长期维护重点放在稳定性、可迁移性和文档化上
