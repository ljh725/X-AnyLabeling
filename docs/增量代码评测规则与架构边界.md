# 增量代码评测规则与架构边界

## 背景

当前项目代码可分为三类：

1. 项目自身未改动代码：作为原始基线和已有能力参考。
2. 项目自身经过改动的代码：作为增量改动重点评测对象。
3. 完全新增项目代码：作为新增扩展、子系统或旁路能力重点评测对象。

本评测不以“代码是否写得漂亮”为唯一目标，而是判断第 2 类和第 3 类代码是否能以低成本、低风险、可维护的方式长期和原项目共存。

## 核心目标

- 找出重复造轮子的地方。
- 找出不合理的项目间依赖。
- 找出依赖启动顺序、全局状态或 UI 状态的隐式耦合。
- 判断新增项目之间的层级逻辑关系是否清晰。
- 判断对原项目代码的修改是否必要、克制、可维护。

## 十二条评测规则

### 1. 原项目最小侵入

大白话：

> 能不改原项目核心代码，就不要改。必须改时，要说明为什么必须改。

检查口径：

- 是否修改了启动入口、主窗口、核心标注组件、配置系统、数据读写等关键文件。
- 是否只是为了新增项目方便而修改原项目核心逻辑。
- 是否可以通过已有扩展点、信号、配置、服务层或新增模块接入。
- 修改是否会影响原有功能行为。
- 后续原项目升级时，这些改动是否容易合并。

可接受情况：

- 修复原项目真实缺陷。
- 增加稳定扩展点。
- 少量必要注册或接线代码。

高风险情况：

- 为某个新增项目临时改核心流程。
- 在核心大文件中散落多个无统一边界的补丁。
- 原项目核心逻辑开始感知某个新增项目的具体实现。

### 2. 依赖必须显式

大白话：

> 可以有依赖，但不能靠启动顺序、全局变量或某个界面刚好打开过来碰运气。

检查口径：

- 新增项目是否依赖另一个新增项目先启动。
- 是否依赖某个 UI 页面、dock、tab、缓存或全局变量已经初始化。
- 是否存在“导入模块即产生副作用”的隐式依赖。
- 依赖关系是否在配置、注册表、文档或入口处明确表达。
- 依赖缺失时是否有清晰错误提示，而不是直接崩溃。

可接受情况：

- 依赖关系清晰声明。
- 启动顺序由统一入口管理。
- 被依赖能力不存在时能降级或给出明确错误。

高风险情况：

- 项目 A 必须等项目 B 打开过才能运行。
- 项目 A 依赖项目 B 的全局变量副作用。
- 新增项目之间互相 import，形成循环依赖或启动顺序依赖。

### 3. 层级只能向下

大白话：

> 上层可以调用下层，下层不要反过来知道上层。核心项目不要反过来依赖扩展项目。

建议层级：

```text
UI 层
  ↓
应用服务 / 业务编排层
  ↓
领域逻辑 / 纯 Python 规则层
  ↓
基础设施 / 工具层
```

检查口径：

- 工具层、质量规则层、数据处理层是否 import 了 PyQt UI。
- 原项目核心代码是否 import 了新增项目。
- 业务逻辑是否被写死在按钮点击、表格事件、窗口状态里。
- 新增项目之间是否存在横向互相依赖。
- 纯逻辑模块是否能脱离 UI 单独测试。

可接受情况：

- UI 调用服务层。
- 服务层调用纯逻辑层。
- 新增项目依赖原项目公开能力。

高风险情况：

- 纯 Python 质量规则依赖 QWidget。
- 原项目核心模块依赖新增扩展模块。
- 底层工具函数读取 UI 控件状态。

### 4. 公共能力优先复用

大白话：

> 项目里已经有稳定轮子时，优先用已有轮子；如果不用，要说明原因。

检查口径：

- 是否重复实现配置读取、JSON 读写、路径匹配、几何计算、后台线程、导入导出、错误处理等已有能力。
- 是否已有基类、工具函数、服务模块或扩展点可以复用。
- 重复代码是直接复制、结构相似，还是语义相同但实现不同。
- 新增实现是否绕过了原项目已有异常处理、日志、配置和兼容逻辑。

可接受情况：

- 为了隔离风险保留少量重复。
- 原有能力不是稳定公共 API。
- 新增场景确实有不同约束，并且原因已说明。

高风险情况：

- 已有成熟实现不用，重新写一套不完整版本。
- 多个新增项目各写一套相似工具。
- 重复实现导致行为不一致或数据兼容问题。

### 5. 新增项目可独立开关

大白话：

> 一个新增项目应该能单独开启、关闭、失败，不应该拖垮主项目或其他新增项目。

检查口径：

- 新增项目关闭后，原项目是否仍可正常运行。
- 新增项目失败时，是否影响主流程启动。
- 新增项目 A 关闭后，新增项目 B 是否仍可运行。
- 新增项目是否有清晰入口、退出和错误处理。
- 新增项目是否把状态污染到全局，导致关闭后仍影响其他功能。

可接受情况：

- 新增项目作为明确插件、模块或功能开关存在。
- 失败时只影响自身功能。
- 与其他新增项目共享公共能力，而不是互相依赖运行状态。

高风险情况：

- 关闭新增项目后主项目无法启动。
- 新增项目异常导致核心标注流程不可用。
- 新增项目之间形成必须同时开启的隐式组合。

### 6. 数据契约必须稳定

大白话：

> 代码可以改，但数据格式、字段含义、输入输出契约不能随便变。

检查口径：

- 是否改变了已有 JSON 字段、配置字段、导入导出字段的含义。
- 新增字段是否影响旧数据读取。
- 新增项目是否假设某些字段一定存在。
- 是否偷偷写回正式标注文件，导致数据污染。
- 是否缺少版本兼容、默认值或迁移逻辑。

可接受情况：

- 新增字段向后兼容。
- 数据格式变化有版本说明和兼容逻辑。
- 只读分析逻辑不写回正式数据。

高风险情况：

- 改变已有字段含义。
- 新功能运行后旧数据无法打开。
- 质检、扫描、分析类功能把临时字段写入正式标注文件。

### 7. 业务逻辑不要塞进 UI

大白话：

> 按钮、表格、窗口只负责交互，真正的判断逻辑要能单独拿出来测试。

检查口径：

- 规则判断、数据处理、核心算法是否写在 QWidget、按钮回调或表格事件里。
- 核心逻辑是否依赖当前界面状态才能运行。
- 不打开界面时，逻辑是否可以单独调用。
- 是否可以用纯 Python 单测覆盖主要行为。

可接受情况：

- UI 层只负责收集输入、展示结果、转发信号。
- 复杂逻辑下沉到服务层、规则层或纯 Python 模块。
- UI 和纯逻辑之间有清晰数据对象或接口。

高风险情况：

- 批处理、质检、数据转换逻辑写死在点击事件里。
- 业务逻辑直接读取多个控件状态。
- 想测试核心行为时必须启动完整界面。

### 8. 错误必须可诊断、可恢复

大白话：

> 出错不可怕，怕的是静默失败、报错看不懂，或者失败后项目状态坏掉。

检查口径：

- 是否吞异常或只返回空结果。
- 是否只使用 print，而没有日志、状态提示或错误传播。
- 后台线程失败是否能通知主界面。
- 文件写入失败时是否会留下半成品。
- 用户是否能从错误信息判断下一步怎么处理。

可接受情况：

- 错误有明确日志、提示和上下文。
- 批处理失败时能保留已完成结果，并报告失败项。
- 写文件有临时文件、覆盖策略或失败回滚。

高风险情况：

- except 后直接 pass。
- 扫描失败但界面显示成功。
- 异常后全局状态、缓存或文件处于不一致状态。

### 9. 变更必须可测试

大白话：

> 新增或修改的核心逻辑，不能只能靠人工点界面验证。

检查口径：

- 新增纯逻辑是否有单元测试。
- 修改原项目核心逻辑时是否有回归测试。
- 边界条件、异常输入、空数据是否覆盖。
- 新增项目是否有最小可运行测试或验收清单。
- UI 相关行为是否至少有集成测试或明确手工验证步骤。

可接受情况：

- 核心逻辑可以脱离 UI 测试。
- 高风险改动有回归用例。
- 难以自动化的 UI 交互有清晰手工测试矩阵。

高风险情况：

- 只能通过完整人工流程验证。
- 修改关键路径但没有任何回归测试。
- 新增项目没有最小输入样例和预期输出。

### 10. 配置、开关、入口必须集中

大白话：

> 新功能从哪里开、怎么关、谁负责初始化，要有统一入口，不能散落在各处。

检查口径：

- 是否到处写硬编码路径、阈值、开关或模式名。
- 是否多个地方重复初始化同一能力。
- 新增项目入口是否清晰。
- 功能启用、禁用、默认值是否集中管理。
- 是否需要修改很多不相关文件才能接入或关闭一个新增项目。

可接受情况：

- 新功能有统一配置、注册入口或功能开关。
- 默认值集中定义。
- 初始化顺序清晰。

高风险情况：

- 开关散落在多个 UI 文件、脚本和配置里。
- 某个功能是否启用取决于隐式变量或运行顺序。
- 新增项目入口不清楚，只能从代码副作用推断。

### 11. 性能和资源边界要明确

大白话：

> 新增功能不能为了自己方便，把主项目拖慢、卡死或占满内存。

检查口径：

- 是否在 UI 线程执行重任务。
- 是否一次性加载大量图片、JSON 或模型。
- 后台任务是否可取消、可反馈进度。
- 是否重复扫描同一批数据。
- 是否有缓存策略和缓存失效逻辑。
- 大数据集、空目录、损坏文件时表现是否可控。

可接受情况：

- 重任务放到后台线程或批处理流程。
- 有进度、取消和错误反馈。
- 大批量数据有分批、缓存或增量处理。

高风险情况：

- 打开界面时直接全量扫描大目录。
- UI 长时间无响应。
- 后台任务无法取消，失败后仍占用资源。

### 12. 公共能力要沉淀到正确位置

大白话：

> 如果多个新增项目都需要同一个能力，就不要各写一份，也不要随便塞进某个具体项目内部。

检查口径：

- 多个新增项目是否出现相似工具函数、数据模型或处理流程。
- 公共逻辑是否被放在某个具体 UI、tab、脚本或新增项目内部。
- 是否应该抽到 service、utils、quality、converter 或独立公共层。
- 抽出的公共能力是否仍保持低层级，不反向依赖 UI 或具体扩展。

可接受情况：

- 公共能力沉淀到稳定公共层。
- 抽象边界清楚，调用方向符合层级规则。
- 复用后不牺牲新增项目独立性。

高风险情况：

- 项目 A 的内部工具被项目 B 直接 import。
- 公共逻辑藏在 UI 文件里。
- 多个新增项目重复维护相似实现，行为逐渐分叉。

## 规则如何使用

评测时先不直接判断“这段代码好不好”，而是拿规则当尺子：

```text
这段代码违反了哪条规则？
违反的证据是什么？
影响是什么？
有没有合理例外？
建议怎么整改？
```

推荐输出格式：

```text
问题等级：P0 / P1 / P2 / P3
违反规则：十二条评测规则之一
问题位置：文件、类、函数或项目模块
证据说明：为什么认为它违反规则
影响范围：启动、维护、升级、测试、数据兼容或功能稳定性
建议处理：复用、抽公共能力、声明依赖、反转依赖、隔离开关或保留例外
```

## 如何让大模型执行检查

不要直接把全部代码丢给大模型并问“哪里不好”。更稳妥的方式是把评测拆成多个阶段。

### 第 1 步：给大模型明确身份和边界

推荐说明：

```text
你是代码架构评测助手。你的任务不是修改代码，而是基于规则检查第 2 类和第 3 类代码的风险。
第 1 类原始未改动代码只作为基线和已有能力参考。
请优先报告有证据的问题，不要泛泛评价代码风格。
```

### 第 2 步：提供必要输入

至少提供：

- 原项目基线版本或基线分支。
- 当前待评测版本。
- 第 2 类代码清单：修改过的原项目文件、diff、相关函数。
- 第 3 类代码清单：新增项目、入口、目录、主要功能。
- 本文档中的十二条评测规则。
- 希望输出的报告格式和问题等级。

### 第 3 步：先让大模型做归类，不急着下结论

推荐任务：

```text
请先把代码分成三类：
1. 原始未改动代码
2. 修改过的原项目代码
3. 完全新增项目代码

然后列出每个新增项目的入口、职责、依赖对象和可能影响的原项目节点。
此阶段只做归类和依赖梳理，不输出整改建议。
```

### 第 4 步：让大模型建立已有能力地图

推荐任务：

```text
请基于原项目代码整理已有能力地图，包括配置、文件读写、几何计算、UI 组件、后台任务、导入导出、错误处理、质检规则等能力。
后续检查重复造轮子时，只能引用这张能力地图或代码证据。
```

### 第 5 步：逐条规则检查，而不是一次性泛评

推荐任务：

```text
请按十二条评测规则逐条检查第 2 类和第 3 类代码。
每个问题必须包含：
- 违反规则
- 问题位置
- 代码证据
- 影响
- 是否存在合理例外
- 建议处理方式

如果没有发现问题，请明确写“未发现有证据的问题”，不要为了凑数量编造问题。
```

### 第 6 步：单独做依赖图和启动矩阵

推荐任务：

```text
请画出新增项目之间、新增项目与原项目之间的依赖关系。
重点检查：
- 是否存在循环依赖
- 是否存在启动顺序依赖
- 是否存在核心项目反向依赖新增项目
- 是否存在 UI 状态或全局状态隐式依赖

并输出一个开启 / 关闭矩阵，判断每个新增项目能否独立开启、关闭和失败隔离。
```

### 第 7 步：最后做优先级排序

推荐任务：

```text
请把所有问题按 P0 / P1 / P2 / P3 排序。
P0：会导致主项目不可启动、数据污染、核心功能不可用。
P1：会导致明显架构反向依赖、隐式启动依赖、升级成本极高。
P2：重复造轮子、测试缺口、错误处理不足、性能风险。
P3：命名、局部结构、轻微重复、文档不足。
```

### 第 8 步：要求大模型给出可复查报告

最终报告应该避免只给结论，要能被开发者复查：

```text
问题编号：
问题等级：
违反规则：
问题位置：
证据：
影响：
建议：
是否需要人工确认：
```

## 推荐的大模型检查方式

对话中可以分三轮进行：

```text
第一轮：归类 + 能力地图 + 依赖图
第二轮：按十二条规则逐条检查
第三轮：整理成 P0/P1/P2/P3 报告和整改优先级
```

这样做的好处是：

- 大模型先理解项目结构，再判断问题。
- 重复造轮子的判断有基线，不靠印象。
- 依赖问题可以通过图和矩阵暴露。
- 报告更适合复查和整改。

## 后续可扩展检查表

后续可以基于这十二条规则继续展开检查表：

- 第 2 类代码改动必要性检查表。
- 第 3 类新增项目独立性检查表。
- 重复造轮子检查表。
- 显式 / 隐式依赖检查表。
- 层级关系检查表。
- 重点代码节点检查表。
- 原项目升级成本检查表。
- 数据契约稳定性检查表。
- 错误恢复检查表。
- 性能和资源边界检查表。
