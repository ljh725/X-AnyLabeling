# 增量代码评测规则与架构边界

## 背景

当前项目代码可分为三类：

1. 项目自身未改动代码：作为原始基线和已有能力参考。
2. 项目自身经过改动的代码：作为增量改动重点评测对象。
3. 完全新增项目代码：作为新增扩展、子系统或旁路能力重点评测对象。

本评测不以“代码是否写得漂亮”为唯一目标，而是判断第 2 类和第 3 类代码是否能以低成本、低风险、可维护的方式长期和原项目共存。

## 核心目标

- 找出重复造轮子的地方。
- 找出不合理的项目间依赖。
- 找出依赖启动顺序、全局状态或 UI 状态的隐式耦合。
- 判断新增项目之间的层级逻辑关系是否清晰。
- 判断对原项目代码的修改是否必要、克制、可维护。

## 五条核心规则

### 1. 原项目最小侵入

大白话：

> 能不改原项目核心代码，就不要改。必须改时，要说明为什么必须改。

检查口径：

- 是否修改了启动入口、主窗口、核心标注组件、配置系统、数据读写等关键文件。
- 是否只是为了新增项目方便而修改原项目核心逻辑。
- 是否可以通过已有扩展点、信号、配置、服务层或新增模块接入。
- 修改是否会影响原有功能行为。
- 后续原项目升级时，这些改动是否容易合并。

可接受情况：

- 修复原项目真实缺陷。
- 增加稳定扩展点。
- 少量必要注册或接线代码。

高风险情况：

- 为某个新增项目临时改核心流程。
- 在核心大文件中散落多个无统一边界的补丁。
- 原项目核心逻辑开始感知某个新增项目的具体实现。

### 2. 依赖必须显式

大白话：

> 可以有依赖，但不能靠启动顺序、全局变量或某个界面刚好打开过来碰运气。

检查口径：

- 新增项目是否依赖另一个新增项目先启动。
- 是否依赖某个 UI 页面、dock、tab、缓存或全局变量已经初始化。
- 是否存在“导入模块即产生副作用”的隐式依赖。
- 依赖关系是否在配置、注册表、文档或入口处明确表达。
- 依赖缺失时是否有清晰错误提示，而不是直接崩溃。

可接受情况：

- 依赖关系清晰声明。
- 启动顺序由统一入口管理。
- 被依赖能力不存在时能降级或给出明确错误。

高风险情况：

- 项目 A 必须等项目 B 打开过才能运行。
- 项目 A 依赖项目 B 的全局变量副作用。
- 新增项目之间互相 import，形成循环依赖或启动顺序依赖。

### 3. 层级只能向下

大白话：

> 上层可以调用下层，下层不要反过来知道上层。核心项目不要反过来依赖扩展项目。

建议层级：

```text
UI 层
  ↓
应用服务 / 业务编排层
  ↓
领域逻辑 / 纯 Python 规则层
  ↓
基础设施 / 工具层
```

检查口径：

- 工具层、质量规则层、数据处理层是否 import 了 PyQt UI。
- 原项目核心代码是否 import 了新增项目。
- 业务逻辑是否被写死在按钮点击、表格事件、窗口状态里。
- 新增项目之间是否存在横向互相依赖。
- 纯逻辑模块是否能脱离 UI 单独测试。

可接受情况：

- UI 调用服务层。
- 服务层调用纯逻辑层。
- 新增项目依赖原项目公开能力。

高风险情况：

- 纯 Python 质量规则依赖 QWidget。
- 原项目核心模块依赖新增扩展模块。
- 底层工具函数读取 UI 控件状态。

### 4. 公共能力优先复用

大白话：

> 项目里已经有稳定轮子时，优先用已有轮子；如果不用，要说明原因。

检查口径：

- 是否重复实现配置读取、JSON 读写、路径匹配、几何计算、后台线程、导入导出、错误处理等已有能力。
- 是否已有基类、工具函数、服务模块或扩展点可以复用。
- 重复代码是直接复制、结构相似，还是语义相同但实现不同。
- 新增实现是否绕过了原项目已有异常处理、日志、配置和兼容逻辑。

可接受情况：

- 为了隔离风险保留少量重复。
- 原有能力不是稳定公共 API。
- 新增场景确实有不同约束，并且原因已说明。

高风险情况：

- 已有成熟实现不用，重新写一套不完整版本。
- 多个新增项目各写一套相似工具。
- 重复实现导致行为不一致或数据兼容问题。

### 5. 新增项目可独立开关

大白话：

> 一个新增项目应该能单独开启、关闭、失败，不应该拖垮主项目或其他新增项目。

检查口径：

- 新增项目关闭后，原项目是否仍可正常运行。
- 新增项目失败时，是否影响主流程启动。
- 新增项目 A 关闭后，新增项目 B 是否仍可运行。
- 新增项目是否有清晰入口、退出和错误处理。
- 新增项目是否把状态污染到全局，导致关闭后仍影响其他功能。

可接受情况：

- 新增项目作为明确插件、模块或功能开关存在。
- 失败时只影响自身功能。
- 与其他新增项目共享公共能力，而不是互相依赖运行状态。

高风险情况：

- 关闭新增项目后主项目无法启动。
- 新增项目异常导致核心标注流程不可用。
- 新增项目之间形成必须同时开启的隐式组合。

## 规则如何使用

评测时先不直接判断“这段代码好不好”，而是拿规则当尺子：

```text
这段代码违反了哪条规则？
违反的证据是什么？
影响是什么？
有没有合理例外？
建议怎么整改？
```

推荐输出格式：

```text
问题等级：P0 / P1 / P2 / P3
违反规则：原项目最小侵入 / 依赖必须显式 / 层级只能向下 / 公共能力优先复用 / 新增项目可独立开关
问题位置：文件、类、函数或项目模块
证据说明：为什么认为它违反规则
影响范围：启动、维护、升级、测试、数据兼容或功能稳定性
建议处理：复用、抽公共能力、声明依赖、反转依赖、隔离开关或保留例外
```
