# 优先级排序拾取模式（Priority-Based Picking Pattern）

> 一套可复用的交互对象选择设计模式：**把"该选中谁"的决策问题，转化为对所有候选项打分后排序的问题**。
>
> 适用于任何"在一个点上可能有多个候选、需要决定选谁"的交互场景：图像/地图标注、CAD 拾取、游戏对象选择、SVG/Canvas 编辑器、数据可视化 tooltip 命中等。

## 0. TL;DR

> **一句话**：不要用 `if-elif-else` 写"如果命中顶点就选顶点，否则如果嵌套就选小框……"，而是给每个候选打一个**统一的优先级元组** `priority = (维度1, 维度2, ...)`，然后 `candidates.sort()`。
>
> **核心收益**：决策问题降维为排序问题 → 规则解耦、可组合、可扩展、可单测、行为可向后兼容。

---

## 1. 适用场景

当你的系统满足以下特征时，本模式适用：

- **一触发点 → 多候选**：用户的一次交互（点击/悬停/拖拽落点）落在某个位置，该位置可能命中**多个对象**（重叠、嵌套、近邻）。
- **需确定唯一胜出者**：交互语义要求选出一个（或按优先级排序的有序列表）。
- **判定维度多元**：选谁取决于多个**互相独立的规则**（几何类型、距离、面积、创建顺序、选中状态……），且这些规则**可能冲突**。

典型场景：

| 领域 | 场景 | 候选冲突来源 |
|------|------|------------|
| 图像标注 | 重叠框/嵌套多边形/密集关键点 | 栈序、面积、顶点 |
| 地图编辑 | 重叠行政区/POI/路径 | 层级、面积、距离 |
| CAD | 线段交点附近的端点/线段/面 | 类型（点/线/面）、距离 |
| 游戏 | 点击落在多个碰撞体重叠区 | 层级、距离、阵营 |
| SVG/Canvas 编辑器 | 分组内的子元素 vs 分组本身 | 层级、距离 |
| 数据可视化 | tooltip 命中多个数据点 | 距离、数据值 |

**不适用**：候选唯一确定、或规则单一无冲突的场景（直接 if 即可，本模式是过度设计）。

## 2. 问题：朴素 if-else 方案的痛点

面对"重叠时选谁"，直觉写法是过程式规则链：

```python
# ❌ 朴素方案：耦合的规则链
def pick(point):
    for shape in reversed(shapes):            # 栈序遍历
        if hits_vertex(shape, point):
            return shape                        # 规则1: 顶点
    for shape in reversed(shapes):
        if hits_edge(shape, point) and can_add_point(shape):
            return shape                        # 规则2: 可编辑边
    # 规则3: 整体命中, 但多个重叠怎么办?
    nested = [s for s in shapes if contains(s, point)]
    if nested:
        return min(nested, key=area)            # 面积最小? 但没考虑栈序/距离...
    return None
```

**痛点**：

| 痛点 | 后果 |
|------|------|
| **规则耦合** | 改一条规则（如"顶点优先级"）可能连锁影响其他规则，因为它们写在同一个控制流里 |
| **优先级隐式** | "顶点 > 边 > 整体" 的优先关系藏在嵌套 if 的先后顺序里，不直观，易错 |
| **不可组合** | 每加一个判定维度，if-else 分支数翻倍（组合爆炸） |
| **语义不一致** | 悬停高亮和点击选中常各自实现一套规则，导致"悬停亮 A 但点击选 B" |
| **难单测** | 决策逻辑和控制流耦合，难以脱离 UI 框架测试 |
| **难以向后兼容** | 改进歧义判定时，容易破坏原有"栈序优先"的默认行为 |

## 3. 模式结构

本模式由 4 个角色组成：

```
┌─────────────────────────────────────────────────────────────┐
│                      Picker（拾取器）                         │
│  ┌───────────────────────────────────────────────────────┐  │
│  │  ① Candidates Generator（候选生成器）                   │  │
│  │     输入: point, shapes                                │  │
│  │     输出: [shape, ...]  (所有可能命中的对象)             │  │
│  └────────────────────────┬──────────────────────────────┘  │
│                           ▼                                  │
│  ┌───────────────────────────────────────────────────────┐  │
│  │  ② Priority Calculator（优先级计算器）★ 核心           │  │
│  │     输入: shape, point, context                        │  │
│  │     输出: priority tuple = (维度1, 维度2, ..., 维度n)   │  │
│  └────────────────────────┬──────────────────────────────┘  │
│                           ▼                                  │
│  ┌───────────────────────────────────────────────────────┐  │
│  │  ③ Sorter（排序器）                                    │  │
│  │     candidates.sort(key=lambda c: c.priority)          │  │
│  │     输出: 按优先级排好序的 [shape, ...]                 │  │
│  └────────────────────────┬──────────────────────────────┘  │
│                           ▼                                  │
│  ┌───────────────────────────────────────────────────────┐  │
│  │  ④ Consumer（消费者）                                  │  │
│  │     悬停 / 点击 / 双击 / 拖拽落点 ...                   │  │
│  │     都遍历排好序的列表，取首个或前 N 个                  │  │
│  │     → 悬停/点击/双击的选择结果天然一致                   │  │
│  │  └─→ 取首个：select / hover                            │  │
│  │  └─→ 取前 N：多选 / tooltip 命中多个数据点               │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

### 3.1 候选生成器（可选优化）

- 朴素实现：遍历所有 shape，命中则入列。
- 空间索引优化：用 R-tree / Quad-tree / BVH 先粗筛，再做精确几何判定（适合海量对象）。

### 3.2 优先级计算器（核心）

**职责**：给单个候选打一个**统一格式的分数**（tuple）。

**关键约束**：所有候选项的 priority tuple **必须维度相同、可比**（否则 sort 会报错或语义错乱）。

### 3.3 排序器

一行 `sort(key=lambda c: c.priority)`。**全升序**（小者优先）。

### 3.4 消费者

复用同一份排好序的列表。这是保证"各种交互语义一致"的关键。

## 4. 设计准则：维度怎么选、顺序怎么定

这是本模式最微妙、也最值得设计的部分。下面给出**4 条可操作准则**，并标注 X-AnyLabeling 案例（简记 **XAL**）的对应。

### 准则 1：按"语义层级"从高到低排列维度（不要按"计算成本"）

维度的先后顺序决定了优先级，**第一位是最优先的决胜维度**。

**排列原则**：
```
质的差异（离散、语义性强）  →  放前面
    例：交互类型(顶点/边/整体)、对象层级(分组/子元素)、阵营
量的差异（连续、几何性强）  →  放中间
    例：距离、面积
兜底语义（保留旧行为）      →  放最后
    例：栈序
```

> **XAL**：`priority = (级别, 距离, 面积, -栈序)`
> - 级别(离散)在最前 → 交互意图优先
> - 距离/面积(连续)在中 → 同意图下按几何细节细分
> - -栈序(兜底)在最后 → 保证默认行为不变

**反面教材**：如果把"距离"放在"级别"前，则"距离近的整体命中"会压过"距离稍远的顶点"——用户明明想抓顶点却被选中整体，违反直觉。

### 准则 2：让冲突维度"语义失效"，而非显式处理

当某维度在特定场景下**不该起作用**时，不要写 if 去绕过它，而是**给它填一个让 sort 自动跳过的值**。

经典手法：**对该场景填 0（或常量）**，让 sort 在这一位全员平手，自动用下一位决胜。

> **XAL**：级别2（整体命中）时，"距离"维度填 `0`（而非真实距离）。
> - 因为点已经在对象内部，"距离"无意义；
> - 全员距离都填 0 → sort 在距离位全员平手 → 决胜权自然交给第3位"面积"。
> - 这就实现了"整体命中时不看距离、看面积"的语义，**零 if**。

### 准则 3：用"代理变量"表达主观语义

用户的真实心智常是主观的（"选更具体的那个"、"选更重要的那个"），代码无法直接表达。解法：找一个**客观、可算、单调**的量作代理。

> **XAL**：用户心智"选更具体的小对象" → 用 `bounding_rect` 面积做代理（面积小≈更具体）。
> 代理变量是启发式（heuristic），不完美但务实。

常见代理变量：

| 主观语义 | 代理变量 | 适用场景 |
|---------|---------|---------|
| "更具体" | 包围盒面积（小者优先） | 嵌套选择 |
| "更重要" | 自定义权重 / z-order | 分组 vs 子元素 |
| "更可能命中" | 距离（近者优先） | 近邻点选择 |
| "更易交互" | 类型优先级 | 端点 vs 线段 |

### 准则 4：最后一维放"兜底语义"，保证向后兼容

把"保留旧行为"的维度放在**最后一位**，并设计成"在前所有维度都平手时才生效"。

> **XAL**：最后一维 `-stack_index`（创建顺序的负值）。
> - 前3维都分不出胜负时，后创建的（栈顶）优先；
> - 这与旧逻辑 `reversed(shapes)` **完全等价** → 新机制默认行为 = 旧行为，只在歧义场景才改进。

**收益**：这是一个**"行为收敛的升级"**——安全、可回退、易回归测试（默认行为不变，只验证歧义场景的改进）。

## 4 节小结：4 维度设计的对照表

| 准则 | XAL 维度 | 性质 | 起作用的场景 |
|------|---------|------|------------|
| 准则1 语义层级 | 级别(0/1/2) | 离散/质 | 区分交互意图（顶点/边/整体） |
| 准则3 代理变量 | 面积 | 连续/量 | 嵌套时小对象优先 |
| 准则2 语义失效 | 距离(整体填0) | 连续/量 | 近邻时近者优先；整体命中时让位给面积 |
| 准则4 兜底兼容 | -栈序 | 离散/兜底 | 同条件时保留旧栈序语义 |

## 5. 参考实现（伪代码模板）

```python
class Picker:
    def pick(self, point):
        candidates = self._generate_candidates(point)   # ① 候选生成
        scored = [(self._priority(s, point), s) for s in candidates]  # ② 打分
        scored.sort(key=lambda c: c[0])                 # ③ 排序
        return [s for _, s in scored]                   # ④ 排好序的列表

    def _generate_candidates(self, point):
        # 可选: 空间索引粗筛 → 精确几何判定
        return [s for s in self.shapes if self._hits(s, point)]

    def _priority(self, shape, point):
        # ★ 核心设计区：返回统一格式的 tuple
        # 遵循 4 条准则: 语义层级 > 冲突失效 > 代理变量 > 兜底兼容
        level = self._interaction_level(shape, point)   # 离散, 质的优先
        dist  = self._distance(shape, point)            # 连续, 量
        area  = self._area(shape)                       # 连续, 量(代理变量)
        stack = -self._stack_index(shape)               # 兜底
        return (level, dist, area, stack)
```

### 消费侧（保证一致性的关键）

```python
# 悬停、点击、双击 —— 全部复用同一份排序结果
def on_hover(point):
    for s in picker.pick(point):   # 取首个
        highlight(s); break

def on_click(point):
    ranked = picker.pick(point)
    if ranked:
        select(ranked[0])          # 取首个
    else:
        deselect()

def on_double_click(point):
    for s in picker.pick(point):
        edit_label(s); return      # 取首个
```

> 因为三者共用 `picker.pick()`，"悬停高亮谁"与"点击选中谁"**永远一致**，杜绝割裂感。

## 6. X-AnyLabeling 完整案例

### 6.1 背景

beta.4 旧逻辑：`reversed(shapes) + 首次 contains_point 命中即 return`，仅靠栈序。在重叠/嵌套/近邻场景误选难选。

beta.11 引入 `_shape_hit_candidates`，采用本模式。

### 6.2 4 维优先级设计

```python
priority = (级别, 距离, 面积, -stack_index)
              │     │     │       │
              │     │     │       └─ 准则4 兜底: 后创建(栈顶)优先, ≡ 旧 reversed 行为
              │     │     └───────── 准则3 代理: 嵌套时小面积优先
              │     └─────────────── 准则2 失效: 整体命中填0, 让位给面积
              └───────────────────── 准则1 层级: 顶点0 < 可编辑边1 < 整体2
```

### 6.3 演算：嵌套场景

```
大框 BIG(0,0)-(100,100) 面积10000, stack=0
小框 SMALL(40,40)-(60,60) 面积400,   stack=1
点击点 (50,50) 落在小框中心

→ BIG   整体命中:   priority = (2, 0, 10000, 0)
→ SMALL 整体命中:   priority = (2, 0, 400,   -1)
                            平 平   400<10000 → SMALL 胜
排序后: [SMALL, BIG] → 选中 SMALL ✅
```

### 6.4 演算：顶点优先场景

```
A 小框(10,10)-(30,30) stack=0, 顶点(10,10) 离点(11,11)≈1.41
B 大框(0,0)-(80,80)   stack=1, 包含(11,11)

→ A 顶点命中: priority = (0, 1.41, 400, 0)
→ B 整体命中: priority = (2, 0, 6400, -1)
              0<2 → 第1位即分胜负 → A 胜
排序后: [A, B] → 选中 A ✅
```

> 更详细的演算见 `SELECTION_MIGRATION_PLAN.md` 与 `tests/test_shape_hit_candidates.py`。

## 7. 何时不用 / 何时该用

### 该用

- 多候选、多规则、规则会冲突的场景。
- 希望悬停/点击/双击等交互语义统一。
- 希望改进旧行为但保持向后兼容。
- 需要脱离 UI 框架单测选择逻辑。

### 不该用（过度设计）

- 候选唯一或规则单一 → 直接 if。
- 对象极少（< 几十个）且无重叠 → 朴素遍历足够。
- 性能极端敏感的 hot path（每次 sort 有开销）。

### 性能考量

- sort 复杂度 O(n log n)，n 为候选数（通常远小于总对象数）。
- 海量对象时，在候选生成阶段加空间索引（R-tree/Quad-tree）把 n 降到候选规模即可。
- 打分函数应纯计算、无副作用、可内联，避免 I/O。

## 8. 扩展指南

本模式的**可扩展性**是它最大的工程价值。下面给出常见扩展，均**无需改动结构**。

### 扩展1：增加新规则 → tuple 加一维

```python
# 需求: "已选中的对象优先"
priority = (级别, 距离, 面积, 已选中?0:1, -栈序)   # 加一维
#                                                       ↑ 新维度插在兜底之前
```

插入位置遵循**准则1**：按语义层级决定插在哪。

### 扩展2：锁定/只读对象降级 → 用高级别维度压制

```python
# 需求: "锁定对象不能被编辑, 但仍可选"
priority = (锁定?-1:0, 级别, 距离, 面积, -栈序)
#          ↑ 锁定的填负数 → sort 升序时排到最后 → 仍可选但优先级最低
```

> XAL 即用此手法：`locked` 默认 False（守卫 no-op），未来要支持锁定只需让 locked=True 的对象级别降级。

### 扩展3：分组语义 → 生成阶段处理，不进 priority

```python
# 需求: "点在分组边界上 → 选整个分组"
def _generate_candidates(self, point):
    group = self._group_at_point(point)       # 生成阶段判定分组
    if group:
        return group.shapes                    # 把整组作为候选返回
    return super()._generate_candidates(point)
```

分组逻辑放在候选生成阶段，不污染 priority（分组是"选什么"的问题，不是"哪个优先"的问题）。

### 扩展4：2D → 3D 拾取

距离维度换成"射线-对象最近距离"，面积维度换成"包围球体积"，其余结构不变。

## 9. 测试策略

本模式的核心优势之一：**决策逻辑是纯函数，可脱离 UI 框架单测**。

```python
def test_nested_small_beats_big():
    big = Shape([(0,0),(100,0),(100,100),(0,100)])
    small = Shape([(40,40),(60,40),(60,60),(40,60)])
    picker = Picker([small, big])
    assert picker.pick(P(50,50))[0] is small    # 小框胜
```

**测试矩阵建议**（参考 `tests/test_shape_hit_candidates.py`）：

| 测试场景 | 验证维度 | 断言要点 |
|---------|---------|---------|
| 嵌套（大套小） | 面积 | 小对象胜，且**不依赖栈序** |
| 顶点 vs 整体 | 级别 | 顶点胜，即使另一对象是栈顶 |
| 近邻顶点 | 距离 | 更近的胜 |
| 同对象多候选 | 内部一致性 | 取最高级别而非第一个入列的 |
| 空白点击 | 边界 | 返回空列表 |
| 元组排序 | 字典序 | 多维平手时按后续维度决胜 |

## 10. 常见陷阱与反模式

### 反模式 1：维度顺序按"计算成本"而非"语义层级"

```python
# ❌ 把便宜计算的维度放前面
priority = (is_cached, level, distance)   # is_cached 只为省计算放最前
# 后果: 缓存的低优先级对象会压过非缓存的高优先级对象
```

**正解**：维度顺序只服从语义优先级，与计算成本无关。成本用空间索引/缓存解决。

### 反模式 2：不同候选项 priority 维度数不一致

```python
# ❌ 顶点命中返回3维, 整体命中返回2维
if hit_vertex: return (0, dist, area)
else:          return (1, area)        # 维度不同 → sort 比较时 TypeError/语义错乱
```

**正解**：所有候选项必须返回**相同维度数**的 tuple。语义失效的位填 0/常量（准则2）。

### 反模式 3：在 priority 里塞副作用

```python
# ❌ priority 计算时修改状态
def _priority(self, s, pt):
    self._last_hit = s                  # 副作用!
    return (level, dist, area, stack)
```

**正解**：priority 必须是**纯函数**（无副作用、确定输入得确定输出）。副作用放消费侧。

### 反模式 4：忽视浮点精度

```python
# ❌ 直接用浮点距离比较, 可能因 1e-16 级误差导致不确定排序
priority = (level, dist, area, stack)   # dist 是浮点
```

**正解**：若业务对边界敏感，对距离做**量化/容差归一**（如 `round(dist, 6)` 或 `dist // epsilon`），保证同一逻辑位置得到稳定排序。

## 11. 与其他模式/算法的关系

| 关系 | 说明 |
|------|------|
| vs **稳定排序** | Python `sort` 是稳定排序：priority 完全相同时，保留入列顺序（即栈序）。所以"最后一维兜底"在稳定排序下甚至可省略——但显式写 `-stack` 更清晰、不依赖语言特性。 |
| vs **复合键索引** | 数据库的复合索引 `(col1, col2, col3)` 思想一致：先按 col1 排，相同再按 col2……本模式是同一思想在交互选择上的应用。 |
| vs **AHP 层次分析法** | AHP 给各维度赋权重后加权求和成单一分数。本模式用**字典序**而非加权，更简单且能表达"绝对优先"（高级别维度压倒一切）。 |
| vs **z-index** | z-index 是单一维度（栈序）的特例。本模式是 z-index 的多维推广。 |

```
┌──────────────────────────────────────────────────────────────┐
│  优先级排序拾取模式 (Priority-Based Picking Pattern)           │
│                                                              │
│  问题: 一个点命中多个对象, 该选谁?                              │
│                                                              │
│  解法: 不写 if-else 规则链, 改为:                              │
│        ① 生成候选 → ② 每个打 priority tuple → ③ sort → ④ 消费  │
│                                                              │
│  核心: priority = (语义层级, 代理变量..., 兜底维度)             │
│        全升序排序, 小者优先                                     │
│                                                              │
│  4 条设计准则:                                                │
│    1. 维度按"语义层级"排列(质的差异 > 量的差异 > 兜底)           │
│    2. 冲突维度用"填0"让其语义失效(零 if)                        │
│    3. 用"代理变量"表达主观语义(面积≈具体性)                     │
│    4. 最后一维放兜底语义, 保证向后兼容                          │
│                                                              │
│  收益: 规则解耦 / 可组合 / 可扩展 / 可单测 / 行为可向后兼容       │
│                                                              │
│  案例: X-AnyLabeling _shape_hit_candidates                    │
│        priority = (级别, 距离, 面积, -栈序)                     │
└──────────────────────────────────────────────────────────────┘
```

## 附录 A：术语表

| 术语 | 定义 |
|------|------|
| 候选（Candidate） | 在某交互点上可能被命中的对象 |
| 优先级元组（Priority Tuple） | 给候选项打的可比较分数，维度间按字典序比较 |

| 语义失效（Semantic Invalidation） | 让某维度在特定场景不起作用的技巧（填0/常量） |
