## 0. 为何需要这份文档

此前的文档用 `(级别, 距离, 面积, -栈序)` 来概括 priority 元组。这对**顶点/边命中**成立，但在**整体命中**时失真——那里第二位装的是面积、第三位装的是 0。

```
顶点命中:    (0, vertex_distance, area, -stack)   # 第2位=距离
整体命中:    (2, area, 0.0, -stack)               # 第2位=面积,第3位=0  ← 与"距离/面积"概括矛盾
```

根源：同一个 tuple 位置，在不同级别下**承载的语义会变**。固定字面命名（"距离/面积"）掩盖了这种"语义浮动"，对维护/复用者会造成误导。本文给出一个**对全部 case 都成立**的统一表征，并讲清命名选择背后的权衡。

---

## 1. 统一规范表征（Canonical Representation）

```
priority = (LEVEL, K1, K2, NEG_STACK)
              │    │   │      │
              │    │   │      └─ NEG_STACK: 负栈序(创建顺序的负值),兜底维度
              │    │   └──────── K2: 次关键字(级别内的二级区分)
              │    └──────────── K1: 主关键字(级别内的一级区分)
              └───────────────── LEVEL: 交互意图级别(离散,质的优先)
```

**排序规则**：全部升序，小者优先。从左到右逐位字典序比较，第一位分出胜负即定结果。

### 四个位置的角色语义（与具体量解耦）

| 位置 | 角色名 | 性质 | 语义（对所有 case 成立） |
|------|--------|------|------------------------|
| 第1位 | `LEVEL` | 离散/质 | 交互意图的等级：顶点 < 边/点线 < 整体命中 |
| 第2位 | `K1` | 连续/量 | **该级别下最该用来分胜负的主关键字** |
| 第3位 | `K2` | 连续/量 | 该级别下次要的区分量；无意义时填占位值 |
| 第4位 | `NEG_STACK` | 离散/兜底 | 前三位全平手时，后创建者（栈顶）优先 |

> 关键认知：**K1 / K2 是"位置角色"，不是"某个固定量"。** 同一个位置在不同 LEVEL 下装的是不同的具体量（见 §2）。这是本机制最微妙、也最容易被文档误述之处。

## 2. 逐 case 取值表（逐行对齐代码）

> 下表每一行都与 `canvas.py` 的具体行号一一对应，是本文唯一的真相来源。

| LEVEL | 命中类型 | K1（主关键字） | K2（次关键字） | 对应代码 | priority 实例 |
|:-----:|---------|---------------|---------------|---------|--------------|
| 0 | 顶点命中 | 顶点距离 `vertex_distance` | 面积 `area` | `canvas.py:544` | `(0, vertex_distance, area, -stack)` |
| 1 | 可编辑边命中 | 边距离 `edge_distance` | 面积 `area` | `canvas.py:561` | `(1, edge_distance, area, -stack)` |
| 1 | point/line/linestrip 近邻 | 顶点距离 `distance` | 面积 `area` | `canvas.py:570` | `(1, distance, area, -stack)` |
| 2 | 整体命中（contains） | **面积 `area`** | **`0.0`（占位）** | `canvas.py:582` | `(2, area, 0.0, -stack)` |

### 关键观察：K1 的语义随 LEVEL 浮动

```
LEVEL=0(顶点)  →  K1 = vertex_distance   (几何远近)
LEVEL=1(边/点) →  K1 = edge/distance     (几何远近)
LEVEL=2(整体)  →  K1 = area              (对象大小)  ← 浮动发生处
```

- 在 LEVEL 0/1，K1 承载"距离"（用户离可编辑点/边有多近）；
- 在 LEVEL 2，点已经在对象内部、距离无意义，**K1 改为承载"面积"**（嵌套场景下小对象优先），同时 K2 填 `0.0` 占位（保持 tuple 形状一致、可比）。

这正是"位置角色固定、具体量浮动"的体现。

## 3. 决策流（逐 case 演算）

### 演算 A：嵌套场景（大框套小框）

```
大框 BIG (0,0)-(100,100) 面积10000, stack=0
小框 SMALL (40,40)-(60,60) 面积400, stack=1
点击点 (50,50) 落在小框中心 → 两者都整体命中(LEVEL=2)

→ BIG   priority = (2, 10000, 0.0, 0)     # K1=area=10000
→ SMALL priority = (2, 400,   0.0, -1)    # K1=area=400
逐位比:
  LEVEL:   2 == 2        平手
  K1:      10000 > 400   → SMALL 的 K1 更小 → SMALL 胜
结果: 选中 SMALL ✅
```

### 演算 B：顶点优先（跨级别）

```
A 小框(10,10)-(30,30) stack=0, 顶点(10,10) 离点(11,11)≈1.41
B 大框(0,0)-(80,80) stack=1, 包含(11,11)

→ A 顶点命中:    priority = (0, 1.41, 400, 0)      # K1=vertex_distance
→ B 整体命中:    priority = (2, 6400, 0.0, -1)     # K1=area
逐位比:
  LEVEL:   0 < 2  → 第1位即分胜负 → A 胜
结果: 选中 A ✅
```

### 演算 C：同级别同 K1，比 K2（罕见，验证 K2 存在意义）

```
构造: 两个矩形, 面积不同, 但点到各自最近顶点的距离恰好相等(都=2.0)
A 面积=400, stack=0, 顶点离点2.0
B 面积=6400, stack=1, 顶点离点2.0
点击命中两者顶点(LEVEL=0)

→ A priority = (0, 2.0, 400, 0)
→ B priority = (0, 2.0, 6400, -1)
逐位比:
  LEVEL: 0==0 平手
  K1:    2.0==2.0 平手
  K2:    400 < 6400 → A 胜  (面积小者优先,与嵌套语义一致)
结果: 选中 A ✅
```

> 演算 C 说明：K2 不是摆设。当 LEVEL 和 K1 都平手时，K2（面积）接棒决胜——这与 LEVEL=2 时 K1 直接用面积，形成**一致的"小面积优先"语义**。

## 4. 命名选择说明（Naming Choice）

> 这一节专门回答："为什么文档里用 `LEVEL/K1/K2/NEG_STACK`，而不是直接写 `级别/距离/面积/栈序`？"

### 4.1 三种候选命名层级对比

同一个元组，可以被命名成三种层级。各有适用场景，也各有失真。

#### 层级 A：字面命名（Literal）

```
priority = (级别, 距离, 面积, -栈序)
```
- **依据**：直接用顶点/边命中时的具体量来命名（`canvas.py:544/561`）。
- **优点**：直观、具体、对入门读者友好。
- **失真点**：在 LEVEL=2（整体命中）时**错误**——那里第2位是面积、第3位是 0，不是"距离/面积"。
- **适用**：纯入门、只讲顶点/边场景的简述。

#### 层级 B：角色命名（Role）—— **本文采用**

```
priority = (LEVEL, K1, K2, NEG_STACK)
```
- **依据**：用"这个位置在排序中扮演什么角色"来命名，**与具体量解耦**。
- **优点**：**对全部 4 种 case 都成立**，无失真；适合维护者/复用者理解机制全貌。
- **代价**：丢了"K1 具体是哪个量"的信息（需配合 §2 取值表才能知道）。
- **适用**：权威规范、跨 case 的统一描述、设计模式复用。

#### 层级 C：结构命名（Structural）

```
priority = (4维排序键)
```
- **依据**：只描述"这是一个 4 维可比较的排序键"，不展开各位置。
- **优点**：最通用、最抽象。
- **失真点**：几乎丢了所有细节。
- **适用**：一句话概括、设计模式文档的 TL;DR。

### 4.2 本文档为何选层级 B（角色命名）

**核心理由：它是唯一能同时满足"严谨 + 跨 case 统一"的命名。**

层级 A（字面）在 LEVEL=2 处失真，对一个"要逐 case 核对、要据此复用/扩展"的规范文档而言是**不可接受的硬伤**——读者会据"第2位=距离"去扩展，结果在整体命中分支里写出 bug。

层级 B 用 `K1/K2` 这种**位置角色**命名，配合 §2 取值表，做到：
- 表头（§1）描述的是"不随 case 变化的角色语义"——**永远成立**；
- 取值表（§2）描述的是"随 case 浮动的具体量"——**逐 case 精确**。

两者配合 = 既严谨又完整。这正是"权威规范文档"该有的形态。

### 4.3 给读者的速记建议

| 你是谁 | 建议记哪套命名 |
|--------|--------------|
| 初学/想快速理解 | 层级 A `(级别,距离,面积,-栈序)`，但**只当它是顶点/边场景的近似** |
| 维护者/复用者 | 层级 B `(LEVEL,K1,K2,NEG_STACK)` + §2 取值表 |
| 设计模式学习者 | 层级 C `4维排序键` + §1 角色语义 |

> **一句话**：字面命名好记但有破绽，角色命名严谨但需配表，按你的目的选。

## 附录：命名选择的方法论（可迁移）

这次"字面命名 vs 角色命名"的差异，本质是一个**通用的文档写作决策**，可提炼为一条方法：

> **当一个数据结构的同一位置，在不同状态下承载不同语义时，文档应优先用"角色命名"（描述位置的功能）而非"字面命名"（描述某个状态下的具体值）。**
> - 字面命名：易读，但在非默认状态下失真。
> - 角色命名：严谨，但需配"状态-取值表"才完整。
> - 标准做法：**表头用角色命名保证通用性，正文用取值表保证精确性。**

适用场景：状态机的状态字段、协议帧的变长字段、联合体（union）的成员、配置项的多模式参数……任何"位置共享、语义浮动"的场合。
