【已确认事实】

- 项目正式数据语义已确定：
  - `person + pose关键点` 使用正式 `group_id` 关联。
  - `head` 是独立检测类别，有自己的 `group_id`。
  - `face` 是独立检测类别，有自己的 `group_id`。
- `group_id` 解耦的含义是：`head/face` 不强制与 `person` 共用 id，不是允许 `group_id = null`。
- 一个真实人物目标可以只标注 `head`、只标注 `face`，或只标注 `head + face`，不要求三类框同时存在。
- 因此，完整性不能再定义为“person 组必须有 head/face”。

【核心问题表述】

在 `person/head/face` 正式 `group_id` 解耦后，如何设计阶段一目标框质量校验方案，使系统既能检查 `person + pose` 的正式组内一致性，又能通过 QA 临时几何关系检查 `face/head/person` 的空间合理性，同时不破坏正式训练/检测数据语义。

【不要带入实现的探索性假设】

- 不假设 `person/head/face` 必须共用同一个 `group_id`。
- 不假设 `head/face` 可以没有 `group_id`。
- 不假设每个 `person` 都必须配套 `head/face`。
- 不假设 `face/head/person` 的几何匹配结果是真值。
- 不假设第一阶段要写回 `qa_entity_id` 到正式 JSON。
- 不假设只输出 TSV 就足够承载质检证据。
- 不进入模型二检、半自动修正、UI 改造或代码实现。

【待验证假设】

- L2 几何匹配规则在真实数据上的稳定性：
  - `face -> head`
  - `head -> person`
  - 头部关键点 -> 候选 `face/head`
- `face_without_matched_head`、`head_without_matched_person` 在实际数据中分别有多少是真问题、多少是合法单类标注。
- L1/L2 规则的默认阈值是否合适，例如：
  - face 超出 head 比例
  - face/head 面积比
  - head/person 面积比
  - 关键点落框容差
  - 同类重复框 IoU 阈值
- `review.tsv + report.json` 双输出是否满足 Inspector 复核和后续统计复盘。
- 是否在后续阶段把稳定的 QA 关系写入 `attributes.qa_entity_id`。

【当前决定采用的方案】

- 阶段一采用 L1/L2 规则体系：
  - L1：硬规则，检查 JSON 字段、label、shape_type、points、group_id、基础几何合法性。
  - L2：几何/视觉关系规则，通过同图 QA 临时匹配检查空间合理性。
- 正式 `group_id` 只用于正式任务语义：
  - `person + pose` 按 group_id 检查。
  - `head/face` 作为独立检测目标检查自身 group_id 合法性。
- 跨类关系不写回正式 group_id，只作为 QA 临时关系：
  - `face -> 候选 head`
  - `head -> 候选 person`
  - `nose/eye/ear -> 候选 face/head`
- 第一阶段不把 `qa_entity_id` 写入正式 JSON。
- 输出采用双文件：
  - `review.tsv`：给 Inspector 导入、点击跳转复核。
  - `report.json`：保存完整 QA 证据、匹配关系、阈值、统计信息。
- 几何匹配采用：
  - 硬过滤
  - 打分排序
  - 低置信或无候选则输出 issue，不强行绑定。
- 阶段一定位是“高风险样本发现器”，不是自动判官。

【下一步只允许围绕什么展开】

- 围绕阶段一 L1/L2 规则规格继续收敛。
- 重点只讨论：
  - 每条 L2 规则的默认阈值。
  - `face -> head`、`head -> person` 的硬过滤条件和打分因子。
  - `review.tsv` 与 `report.json` 的字段细化。
  - 人工复核结果如何回流到规则阈值调整。
- 暂不展开：
  - 模型二检。
  - 半自动修正。
  - UI 改造。
  - 批量改写 JSON。
  - 代码实现。
