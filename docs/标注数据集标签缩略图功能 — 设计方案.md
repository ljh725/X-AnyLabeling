# 标注数据集标签缩略图功能 — 设计方案
> 版本：v1.0
> 日期：2026-09-03
> 宿主程序：X AnyLabeling（或兼容其 JSON 格式的标注软件）
---
## 1. 功能定位
一句话定义：
> **一个“数据集级的标签聚合视图 + 命令派发器”——本身不拥有数据、不拥有保存职责，只做两件事：聚合展示、转发操作。**
核心价值：让用户以**标签**为观察维度（而非文件维度）浏览整个数据集，通过缩略图批量审视同标签的标注质量，并批量执行改名/删除等操作。
典型使用场景：某标签下 800 个 shape，用户分批查看、每批圈选一部分、批量改成新标签名，直到该标签清空或处理完毕。
---
## 2. 架构总览
### 2.1 四层结构
| 层 | 内容 | 职责 |
|---|---|---|
| **持久层** | 磁盘上的 JSON 文件 + 图片文件 | **唯一真相**，所有修改最终落在这里 |
| **索引层** | SQLite 数据库 | JSON 的衍生缓存，只存元数据，加速查询 |
| **处理层** | 缩略图窗口 | 聚合展示、选中、形成修改意图 |
| **命令层** | 主程序既有代码 | 解析/序列化/保存/undo，所有写操作必须经过它 |
### 2.2 三条公理（整个设计的纪律基础）
1. **JSON 是唯一真相**。SQLite 和缩略图缓存都是衍生物，失效即可重建，不存在双向同步问题。
2. **所有写操作走主程序同一套序列化函数**，不允许自己拼 JSON dict（保证字段版本、imagePath/imageData、shape 结构一致）。
3. **写回是逐文件小事务**：要么完整完成，要么完全不动；失败跳过并记录，不中断整批。
### 2.3 数据流全景
```
磁盘 JSON ◄────保存──── 画布内存 ──信号──► 缩略图窗口
    ▲                                        │
    └──── 批量操作直接写回（事务式）◄──────────┘
              │
              └── 发"已变更"信号 → 索引局部失效重扫
SQLite 索引：写 JSON 的事务内顺手更新对应行（写时同更，无定时同步）
```
### 2.4 与主画面的关系
主程序原流程是“加载单文件 → 画布编辑内存状态 → 按时机保存”。缩略图功能与它**并存而不冲突**：两套流程共享磁盘这个唯一真相，各自在内存里只持有自己需要的那部分。

## 3. 数据设计
### 3.1 shape 唯一性
- 图片与 JSON 一一对应（宿主已保证，一图一文件）。
- 每个 shape 携带**自生成唯一 ID**：32 位十六进制数（128 bit）。16 万量级下生日碰撞概率约 10⁻²⁴，可忽略。
- ⚠️ 此 ID 为自定义字段，非 X AnyLabeling 原生格式字段。序列化必须复用主程序函数，确保该字段不因格式校验/版本迁移被丢弃。
### 3.2 SQLite 表结构（索引层）
```
shapes 表
  shape_id     TEXT PRIMARY KEY   -- 32 位十六进制唯一 ID
  label        TEXT               -- 标签名
  bbox_x       REAL               -- 框坐标与尺寸
  bbox_y       REAL
  bbox_w       REAL
  bbox_h       REAL
  file_path    TEXT               -- 所属 JSON 文件路径
  image_path   TEXT               -- 对应图片路径
files 表
  file_path    TEXT PRIMARY KEY
  mtime        REAL               -- 磁盘 JSON 的修改时间（漂移检测用）
  shape_count  INTEGER
```
**边界约束：库中只存元数据。** 不存完整 shape（points、group_id、自定义字段等），那些仅在写回时从 JSON 原文读取。绝不把 SQLite 做成第二个数据源或写入口。
### 3.3 磁盘缓存目录
```
.cache/thumbs/{图像文件hash}/{shape_id}_{label哈希}_{bbox哈希}.png
```
- key 含 **label 哈希**：改名后缓存自动失效。
- key 含 **bbox 哈希**：shape 移动/调整后缓存自动失效。
- 单张缩略图最长边 128px，PNG 存储。

## 4. 功能流程详述
### 4.1 阶段〇：启动（用户无感知）
1. 检查 SQLite 是否存在：
   - 不存在 → 后台**全量扫描**（首次可能耗时几十秒，不阻塞界面）
   - 存在 → 后台**增量扫描**
2. 增量扫描：遍历数据集 JSON，比对磁盘 mtime 与库中记录，仅对不匹配的文件“重扫 → 删旧行 → 插新行”；新增文件插入，已删文件清行。
3. 扫描在后台线程执行，期间主界面正常可用。
**不做手动触发**。手动“重建全量索引”仅作为菜单兜底按钮。
### 4.2 阶段一：打开缩略图窗口
1. 查询标签分布渲染左侧列表：
```sql
SELECT label, COUNT(*) AS cnt FROM shapes GROUP BY label ORDER BY cnt DESC
```
2. 向主程序查询当前画布文件路径，记录为 `current_file`，并订阅三个信号：
   - 文件加载
   - 保存完成
   - 画布编辑（dirty 状态变化）
### 4.3 阶段二：选择观察条件（循环起点）
1. 查询条件命中总数：
```sql
SELECT COUNT(*) FROM shapes WHERE label = ?
```
2. 初始化分页（每页 50~100 个），查询第一页：
```sql
SELECT shape_id, bbox_x, bbox_y, bbox_w, bbox_h, file_path, image_path
FROM shapes WHERE label = ?
ORDER BY file_path
LIMIT 100 OFFSET 0
```
`ORDER BY file_path` 使同图像文件的 shape 相邻，供解码聚合使用。
### 4.4 阶段三：缩略图渲染流水线
对查询结果的 100 个 shape：
**分桶**：按 `image_path` 分组（100 个 shape 可能仅来自 20~30 张图）。
**逐桶处理**：
1. 逐 shape 生成缓存 key，批量检查磁盘缓存，命中标记“就绪”。
2. 未命中的组成后台任务投入 `QThreadPool`：
```
任务（后台线程）：
  a. 解码整张原图（一次）
  b. 对桶内每个未命中 shape：crop(bbox) → scaled(128px)
  c. 逐个写入磁盘缓存
  d. 发信号通知 UI：这批 key 已就绪
  e. 原图对象释放
```
**UI 填充**：初始显示占位图（标签名 + bbox 尺寸 + 文件名缩写），就绪信号逐个替换为真图；成品同时放入内存 LRU（上限约 2000 张）。
**性能特征**：
- 元数据常驻，原图即用即弃，成品两级缓存（磁盘 + LRU）。
- 只按可见性生成：任何时刻实际解码的仅视口涉及的 20~30 张原图，与数据集总量无关。
- 首次滚动有数百毫秒占位→替换延迟；二次打开命中磁盘缓存，近零成本。
### 4.5 阶段四：选中与确认（处理层）
1. 网格上点选/框选/全选，维护选中集合（一组 `shape_id`，可跨页累加）。
2. 触发操作（重命名/删除等），弹出确认对话框：
   - 新标签名输入（或从已有标签选择）
   - **影响范围预览**：涉及 N 个文件、M 个 shape
   - 明示文案：“此操作立即写入 JSON 文件，不可通过 Ctrl+Z 撤销（已自动备份）”
3. 用户确认后形成**修改意图对象**，此时磁盘无任何改动：
```
OperationIntent:
  type: rename
  new_label: "pedestrian"
  shape_ids: [...170 个 ID...]
  target_files: [...去重后的文件列表...]
```
### 4.6 阶段五：写回执行（命令层，单批事务）
对 `target_files` 逐个处理，**双路径分流**：
```
对每个文件 F：
  ┌─ F == current_file（写回时刻的实时判断）？
  │
  ├─ 是：画布路径
  │    发信号给主程序 → 在内存 shapes 中按 shape_id 定位并修改
  │    → undo 栈正常记录 → dirty 置位
  │    → 不写盘！保存时机由用户 Ctrl+S / 自动保存决定
  │    → SQLite 对应行暂不更新，等"保存完成"信号到来再同步
  │
  └─ 否：直接路径（五步小事务）
       a. 备份：复制 F 到 .backup/{时间戳批次}/
       b. 读入 F 完整 JSON（含全部 shape 字段）
       c. 按 shape_id 集合定位目标 shape，修改 label，其余不动
       d. 主程序同一序列化函数生成新 JSON
          → 写临时文件 → rename 原子覆盖
       e. 更新 SQLite：
          UPDATE shapes SET label=? WHERE shape_id IN (...)
          并刷新该文件的 mtime 记录
```
**事务纪律**：
- 单文件失败（解析错误/写权限）→ 跳过并记录，继续下一个，不回滚已完成项。
- 全部完成 → 写操作日志（时间、操作类型、文件清单、成功/失败统计）。
- 汇总弹窗：“170 个 shape 已更新，2 个文件跳过（原因见日志）”。
- 批量涉及多文件时显示进度条，全程后台线程。
### 4.7 阶段六：刷新闭环（回到循环）
**触发**：直接路径的写回完成信号 + 主程序保存完成信号（画布路径）。
1. 已改 shape 的缩略图缓存失效（缓存 key 含 label 哈希，天然失效）。
2. 已改 shape 不再匹配当前过滤条件，**从视图中退场**。
3. 当前页重渲染：剩余 shape 上移，从 SQLite 拉后续 shape 补足本页。
4. 分页总数更新（该标签 -170）。
5. 用户回到阶段四继续选下一批——循环持续至标签清空或切换观察条件。
### 4.8 阶段七：退出与长期保障
- **窗口关闭**：无特殊动作。SQLite 已实时同步，磁盘缓存供下次秒开。
- **.backup 策略**：保留最近 N 个批次（建议 10），超出自动删旧；用户可手工恢复。
- **重建索引按钮**：删库全量重扫，不可解释不一致状态的一键自愈。

## 5. 同步与一致性规则
不做定时同步，做**写时同更 + 漂移检测**：
| 规则 | 内容 |
|---|---|
| 写时同更 | 谁（哪条路径）写 JSON，谁在同一操作窗口内更新 SQLite 对应行 |
| 漂移检测 | files 表存 mtime，启动增量扫描比对，外部改动可被发现 |
| 当前文件例外 | “当前编辑中且 dirty”的文件以主程序内存为真相，SQLite 行延迟至保存信号后同步 |
| 兜底 | 重建索引命令，正常用不到 |
两条 SQLite 更新路径的代码**分开写清楚，不图统一**：
- 直接路径：写盘事务内即时更新
- 画布路径：等主程序“保存完成”信号后重扫更新
---
## 6. 可撤销性（明确放弃 undo，用三层薄保护兜底）
| 操作目标 | 路径 | 可撤销性 |
|---|---|---|
| 当前画布文件 | 主程序命令 → 改内存 → 原时机保存 | ✅ 主程序 undo 可用 |
| 非当前文件 | 读 → 改 → 立即原子写盘 | ❌ 写下即成事实 |
**不为非当前文件自建跨文件 undo 栈**（快照冲突、平行体系互相干扰，复杂度不值）。补偿三层：
1. **操作前确认 + 影响范围预览**（N 文件 / M shape 明示）
2. **软备份**：改写前原文件挪入 `.backup/{时间戳}/`，保留最近 N 批
3. **操作日志**：配合备份目录定位和恢复

## 7. 用户视角流程（收口）
```
① 打开标注软件          —— 后台自动增量扫描（无感知）
② 打开缩略图窗口         —— 左侧标签分布列表，即开即用
③ 选择某个标签           —— 分批显示 50~100 个缩略图
④ 循环：选中 → 确认 → 自动流转下一批
⑤ 关闭窗口
```
用户感知不到“同步”“扫描”“保存”这些词——但每一步底下都有第 2、5、6 节的纪律在兜底。
```
获取 ────► 处理 ────► 写回
 ▲                      │
 └────── 变更通知 ◄──────┘
获取/写回发生在 JSON 磁盘边界；处理发生在 SQLite 索引上。
```

## 8. 实现要点与易踩坑清单
1. **`current_file` 必须取写回那一刻的实时值**——用户可能在选图过程中切换了画布，用窗口打开时的缓存值会出错（可能导致覆盖未保存编辑）。
2. **画布路径与直接路径的 SQLite 更新时机不同**（延迟 vs 即时），分开实现。
3. **缩略图缓存 key 必须包含 label 哈希**，否则改名后旧缓存被继续命中。
4. **imageData 字段**：部分 JSON 内嵌 base64 图片数据，解析/序列化必须复用主程序函数，防止丢失或重复编码。
5. **解码按图像文件聚合**：同一原图解码一次裁多次，任务调度粒度是图像而非 shape。
6. **shape 自定义 ID 字段**在格式迁移中的存活，依赖复用主序列化函数。
7. **原子写**：临时文件 + rename，防写半崩溃损坏标注。

## 9. 开发分期建议
| 阶段 | 内容 | 交付时可用性 |
|---|---|---|
| P1 | 扫描 + SQLite 建库 + 标签列表查询 | 只读浏览（无图） |
| P2 | 缩略图渲染流水线（缓存/线程池/占位） | 只读浏览（完整） |
| P3 | 写回事务（直接路径：备份/原子写/库同更/日志） | 批量修改可用 |
| P4 | 画布路径分叉 + 三信号订阅 + 刷新闭环 | 完整功能 |
风险最高的写回放最后，前两步完成时功能已产生价值；P3/P4 重点测试双路径分叉与 `current_file` 实时判断。
---
## 10. 一句话总结
> 缩略图功能是一个订阅了主程序状态、会派发命令的外挂面板：元数据走 SQLite 索引、图像按需两级缓存、修改意图经双路径分流（画布走命令、其余走事务式落盘）、JSON 是唯一真相——单文件尺度上它服从主程序的编辑体系，数据集尺度上它用“失效-重建”代替版本控制，用“预览+备份+日志”补偿放弃的 undo。
