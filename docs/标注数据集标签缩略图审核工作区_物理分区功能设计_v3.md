# 标注数据集标签缩略图审核工作区——物理分区功能设计 v3

> 版本：v3.0  
> 日期：2026-09-03  
> 宿主：X-AnyLabeling 4.x  
> 核心前提：标签通过剪切分区，单人独占处理，完成后再剪切汇总

---

## 1. 一句话定义

> **这是一个只处理“当前独立文件夹”的标签缩略图审核工具：按固定标签顺序浏览、在当前文件夹内改标和删除、独立保存进度与备份，不读取、不修改、也不调度其他标注员的文件夹。**

该设计不解决“多人同时修改同一份数据”的问题，因为实际生产流程已经从源头消除了这种情况。

---

## 2. 已确认的业务规则

### 2.1 标签规则

1. 标签具有固定且唯一的顺序，例如 `1～5000`。
2. 开始标注前，通过操作系统的“剪切”把标签数据分到三个独立文件夹。
3. 三个文件夹中的标签集合互不重复。
4. 每个文件夹拥有独立的数据存储路径。
5. 一个文件夹只由一个标注人员处理。
6. 审核期间不允许把标签从一个文件夹调整到另一个文件夹。
7. 软件不提供任何“跨文件夹移动、改派或重新平衡标签”的功能。
8. 三个文件夹全部处理完成后，再通过“剪切”汇总到最终目录。

### 2.2 示例分区

如果按连续范围平均拆分 5000 个标签，可以是：

```text
标注员 A：标签 0001～1667
标注员 B：标签 1668～3334
标注员 C：标签 3335～5000
```

实际边界可以不同，但一旦剪切完成并开始审核，分区归属即固定，不在软件内动态调整。

### 2.3 数据所有权

```text
一个标签 → 只属于一个分区文件夹
一个分区文件夹 → 只属于一个标注员
一个标注员 → 只在自己的文件夹内读写
```

因此，安全边界不是“整个 5000 标签的数据集”，而是“标注员当前打开的独立文件夹”。

---

## 3. 功能真正要解决的问题

在物理分区已经避免多人冲突后，缩略图工作区只需要解决五件事：

1. 怎样按固定顺序快速浏览当前文件夹内的标签。
2. 怎样从大量 Shape 中生成并缓存缩略图。
3. 怎样确保批量操作修改的是正确 Shape。
4. 怎样避免后台写盘覆盖当前画布的未保存内容。
5. 怎样在程序崩溃或写入失败时恢复当前文件夹的数据。

不再需要解决：

- 不同标注员之间的实时同步；
- 同一标签的多人抢占；
- 跨文件夹事务；
- 跨文件夹锁；
- 跨文件夹冲突合并；
- 标签任务的动态重新分配。

---

## 4. 文件夹就是工作区

### 4.1 工作区边界

用户从 X-AnyLabeling 中选择一个分区文件夹后，该文件夹成为当前审核工作区：

```text
当前工作区根目录
  ├─ 标签数据或图片目录
  ├─ JSON 标注文件
  └─ .xanylabeling/
      └─ thumbnail_review/
          ├─ index.sqlite
          ├─ review_progress.sqlite
          ├─ cache/
          ├─ backups/
          └─ operations/
```

所有索引、缓存、审核进度、备份和操作日志都跟随当前工作区保存，不引用另外两个分区的路径。

### 4.2 路径约束

工作区打开后：

- 只扫描根目录以内的 JSON 和图片；
- 只允许修改根目录以内的 JSON；
- 缩略图窗口不能添加第二个工作区；
- 批量操作不能传入工作区以外的文件；
- 真实路径解析后越过工作区边界时直接拒绝操作。

这条路径边界是软件层面的主要防误操作措施。

### 4.3 不做跨文件夹功能

软件中不出现以下入口：

- “移动到标注员 B”；
- “把标签调整到另一个分区”；
- “重新平衡三个文件夹”；
- “跨文件夹搜索并修改”；
- “把其他文件夹挂载到当前审核窗口”。

分区和最终汇总都由用户在文件系统中通过剪切完成，缩略图审核功能不参与搬运。

## 5. 标签范围与顺序

### 5.1 分区配置

每个工作区保存一份只读归属配置：

```yaml
schema_version: 1
partition_id: A
label_order:
  type: numeric_range
  start: 1
  end: 1667
```

如果标签不是纯数字，也可以保存显式顺序表：

```yaml
label_order:
  type: explicit
  values: [label_0001, label_0002, label_0003]
```

配置只定义当前文件夹允许出现的标签及显示顺序，不负责移动数据。

### 5.2 打开工作区时检查

首次扫描输出：

- 配置内应有但目录中没有的标签；
- 目录中存在但不属于本分区的标签；
- 重复标签；
- 无法识别顺序的标签；
- 缺少 JSON 或图片的数据项。

其中“标签不属于本分区”是硬错误：允许只读查看和导出诊断，但禁止把它作为正常审核对象继续处理。

### 5.3 UI 顺序

左侧标签列表严格按固定顺序显示，不再按 Shape 数量从多到少排序：

```text
0001  已完成   120/120
0002  处理中    60/95
0003  未开始     0/81
...
```

数量只用于展示工作量，不改变标签顺序。

## 6. 总体架构

### 6.1 五个模块

| 模块 | 职责 |
|---|---|
| 工作区扫描器 | 扫描当前文件夹、验证标签归属、建立本地索引 |
| 缩略图加载器 | 按原图聚合解码、裁剪、缩放和缓存 |
| 审核进度库 | 保存当前分区的标签进度、选择和待提交决定 |
| 写入协调器 | 区分当前画布文件和普通磁盘文件 |
| JSON 事务引擎 | 暂存、校验、备份、原子替换、日志和恢复 |

### 6.2 数据流

```text
当前分区文件夹
      │
      ├──扫描──► 本地索引 ──查询──► 缩略图工作区
      │                              │
      │                              ▼
      │                         待提交审核决定
      │                              │
      │                         用户确认提交
      │                              │
      ├──当前文件◄──画布命令─────────┤
      │                              │
      └──其他文件◄──本地 JSON 事务───┘
```

整个流程没有跨分区通信。

## 7. 本地索引设计

### 7.1 索引性质

`index.sqlite` 只是当前工作区 JSON 的查询缓存：

- 删除后可以重新扫描；
- 不保存完整 Shape；
- 不作为标注写入口；
- 不复制其他分区的数据；
- 不在最终汇总时继续使用。

### 7.2 建议数据

```text
files
  annotation_path
  image_path
  size
  mtime_ns
  shape_count

shapes
  annotation_path
  image_path
  shape_id
  label
  shape_type
  bbox_x/y/w/h

labels
  label
  order_no
  total_shapes
```

路径保存为工作区根目录下的相对路径。

### 7.3 安全刷新

索引刷新仍采用临时构建后发布，但目的只是避免扫描中断破坏当前页面，不是解决多人并发：

1. 后台建立 staging 索引。
2. 扫描当前文件夹全部目标文件。
3. 检查行数、标签归属和 Shape ID。
4. 全部完成后切换为 active 索引。
5. 扫描取消或失败时继续使用旧索引。

外部剪切、增加或删除文件后，用户重新打开工作区或点击“刷新当前文件夹”即可重建。

## 8. 分页与标签流转

### 8.1 标签级工作流

用户不是在三个文件夹之间切换，而是在当前文件夹内依次处理标签：

```text
当前标签 0001
  → 查看全部缩略图
  → 完成审核
  → 标记标签 0001 已完成
  → 自动进入标签 0002
```

标签顺序由分区配置决定，不能被 Shape 数量、最近使用时间或搜索结果永久改变。

### 8.2 Shape 分页

单个标签下 Shape 较多时，每页默认显示 100 个。采用稳定游标：

```text
ORDER BY annotation_path, shape_id
```

下一页从上一页最后一个 `(annotation_path, shape_id)` 后继续，不使用越来越慢的深 OFFSET。

### 8.3 标签完成条件

一个标签可以标记为“已完成”的默认条件：

- 没有未提交的审核决定；
- 没有写入失败项；
- 当前标签没有待保存的画布修改；
- 所有需要审核的 Shape 都已有审核结果；
- 没有被隔离的身份异常对象。

如果允许用户强制完成，必须记录原因和未完成数量，不能伪装成完整完成。

## 9. 缩略图加载与缓存

### 9.1 加载方式

1. 查询当前标签的一页 Shape。
2. 先显示文件名、标签和框尺寸占位卡片。
3. 按原图路径分组，同一原图只解码一次。
4. 对图中多个 Shape 分别裁剪并缩放到最长边 128px。
5. 结果写入磁盘缓存，并放入内存 LRU。
6. UI 收到结果后替换占位图。

### 9.2 缓存 key

```text
原图相对路径
+ 原图大小和修改时间
+ Shape ID
+ bbox 哈希
+ 标签哈希
+ 渲染版本
```

这样原图、框位置或标签变化后都会生成新缩略图。

### 9.3 任务取消

切换标签、关闭窗口或重新扫描时：

- 停止继续投递旧任务；
- 已在线程中运行的任务可以完成计算；
- 结果携带页面 token；
- token 不匹配当前页面时丢弃结果，不更新 UI。

## 10. 审核交互

### 10.1 默认布局

```text
┌ 当前分区标签列表 ┬ 当前标签缩略图网格              ┐
│ 0001  已完成     │                                 │
│ 0002  处理中     │                                 │
│ 0003  未开始     │                                 │
├──────────────────┴─────────────────────────────────┤
│ 已选 N  待改标 M  待删除 K  [撤销决定] [确认提交] │
└────────────────────────────────────────────────────┘
```

### 10.2 两阶段操作

1. 用户选择一个或多个缩略图。
2. 数字键或按钮只产生“待改标、待删除、保留”等决定。
3. 尚未提交的决定可以撤销。
4. 点击“确认提交”时显示 Shape 数和涉及文件数。
5. 用户确认后才修改画布或磁盘。

误按数字键不会立即写 JSON。

### 10.3 改标范围

目标标签必须属于当前分区配置。

例如当前分区允许 `1～1667`：

- `100 → 105`：允许；
- `100 → 2000`：拒绝；
- “移动到分区 B”：不存在这个功能。

这项校验只限制审核操作的合法范围，不负责在磁盘上搬运标签。

### 10.4 跨页选择

选择集保存永久 Shape ID 和所属 JSON 相对路径，不保存“第几页第几个”。翻页不会丢失选择，刷新后找不到的对象会明确标记为失效。

## 11. Shape 定位安全

即使没有多人修改，同一个人也可能在主画布中删除、复制或重新排列 Shape。因此写回不能依赖 JSON 数组下标。

### 11.1 对象定位

每个 Shape 使用现有字段：

```text
xanylabeling_shape_id
```

写入时使用：

```text
(当前工作区, JSON 相对路径, xanylabeling_shape_id)
```

数组位置只用于显示和导航，不用于写回。

### 11.2 异常身份

- ID 缺失：禁止批量写该 Shape；
- ID 非法：禁止批量写该 Shape；
- 同一 JSON 内 ID 重复：禁止批量写整个冲突集合；
- 对象已被删除：报告已失效并跳过。

身份修复使用现有独立项目工具，不在缩略图窗口中静默完成。

---

## 12. 当前画布与磁盘文件

### 12.1 当前画布文件

当前画布可能有未保存内容，因此规则是：

> **当前画布对应的 JSON 永远不由缩略图后台直接覆盖。**

处理流程：

1. 真正执行操作时获取实时当前文件路径。
2. 如果目标是当前文件，在画布内存中按永久 ID 找 Shape。
3. 通过主程序命令修改，写入原有 undo 栈。
4. 画布设为 dirty，由用户正常保存。
5. 保存完成后再更新本地索引。

### 12.2 非当前文件

非当前文件走本地 JSON 事务：

1. 重新读取完整 JSON。
2. 按永久 ID 找到目标。
3. 只修改用户确认的字段。
4. 生成暂存 JSON并重新解析验证。
5. 备份原文件。
6. 原子替换原 JSON。
7. 记录逐文件结果。

### 12.3 用户切图

“是否当前文件”必须在实际写入前重新判断。不能使用打开缩略图窗口时缓存的当前文件路径。

这解决的是同一个应用内部的画布和后台写入协调，不是多人并发问题。

## 13. 事务、备份与恢复

### 13.1 复用现有事务底座

缩略图审核复用 `widgets/label_batch.py` 中的通用能力：

- `BatchWriteGate`：防止同一个应用同时运行两个批量写任务；
- `JsonTransactionEngine.stage_files()`：暂存并验证 JSON；
- `JsonTransactionEngine.commit()`：原子替换；
- manifest：记录每个文件状态；
- `restore()`：按备份恢复。

这里的 Gate 只约束当前程序内的批量功能，不承担三名标注员之间的协调。

### 13.2 原子性范围

- 一个 JSON 文件要么完整写入，要么保持旧文件；
- 整个批次不是全有或全无；
- 某个文件失败不回滚已经成功的其他文件；
- 汇总界面必须显示成功、跳过和失败数量；
- 用户可根据 manifest 恢复已成功文件。

### 13.3 备份范围

备份只存在当前分区工作区内，不写入公共目录，也不涉及另外两个分区。

最终剪切汇总前，应保留原分区工作目录或单独归档 `.xanylabeling/thumbnail_review/operations` 和备份，直到总体验收完成。

## 14. 审核进度

### 14.1 独立进度库

`review_progress.sqlite` 保存：

- 当前分区 ID；
- 当前处理到的标签；
- 每个标签的总数、已审核数和完成状态；
- 尚未提交的审核决定；
- 强制完成原因；
- 最近一次操作结果。

它不是 JSON 标注数据，但属于用户工作成果，因此不能随着索引重建一起删除。

### 14.2 恢复工作位置

重新打开文件夹时：

1. 验证分区配置仍一致。
2. 加载上次处理标签和审核进度。
3. 重建或增量更新数据索引。
4. 对已保存进度与当前 JSON 做一次数量核对。
5. 对不存在的对象显示“数据已变化”，不静默删除历史记录。

### 14.3 标签完成后

完成当前标签时写入一条完成记录，但不移动任何文件。随后按固定顺序进入下一个标签。

---

## 15. 从分区到最终汇总

缩略图功能不执行剪切，只提供汇总前的完成检查。

### 15.1 每个分区的完成检查

关闭并剪切之前确认：

- 分区内所有标签都已完成或有明确例外；
- 没有未提交决定；
- 当前画布没有待保存修改；
- 没有未处理的写入失败；
- 没有未确认的恢复事务；
- 标签全部属于本分区；
- 标签数量与分区配置一致。

检查通过后生成只读完成摘要，例如：

```json
{
  "partition_id": "A",
  "label_start": 1,
  "label_end": 1667,
  "label_count": 1667,
  "completed_labels": 1667,
  "pending_operations": 0,
  "failed_operations": 0
}
```

### 15.2 人工剪切汇总

三个标注员完成后：

1. 关闭三个分区中的 X-AnyLabeling。
2. 确认所有画布内容已保存。
3. 将三个分区中的标签数据剪切到最终汇总目录。
4. 剪切过程中出现同名标签时停止，不执行覆盖。
5. 汇总完成后重新扫描最终目录。
6. 验证标签并集符合预期，例如完整覆盖 `1～5000`，且没有重复。

### 15.3 汇总后处理

- 不复用三个分区的 `index.sqlite`；最终目录重新建索引。
- 不把三个分区的缓存拼接成一个缓存。
- 分区审核进度和操作日志作为历史归档保留。
- 汇总目录只用于最终检查或后续流程，不反向改变已经完成的分区归属。

## 16. 用户完整流程

```text
准备阶段
  → 按固定标签顺序划定三个不重复范围
  → 通过剪切把数据放入三个独立文件夹

标注阶段
  → 每名标注员只打开自己的文件夹
  → 后台建立当前文件夹索引
  → 按标签固定顺序查看缩略图
  → 数字键或按钮形成待提交决定
  → 确认后在当前文件夹内写回
  → 当前标签完成后进入下一个标签

汇总阶段
  → 三个文件夹分别通过完成检查
  → 关闭软件并保存画布
  → 通过剪切汇总到最终目录
  → 重新扫描并检查 1～5000 是否完整且不重复
```

## 17. 异常处理

| 场景 | 处理方式 |
|---|---|
| 当前目录出现其他分区标签 | 标记越界，禁止正常批量修改 |
| 标签缺失 | 显示缺失清单，不自动去其他文件夹查找 |
| 标签重复 | 阻止该标签完成，要求人工检查剪切结果 |
| JSON 损坏 | 隔离该文件，其他文件继续浏览 |
| Shape ID 缺失或重复 | 目标只读，禁止按数组位置写入 |
| 原图缺失 | 显示占位卡和路径错误 |
| 索引重建失败 | 保留旧索引，不影响已有页面 |
| 当前画布 dirty | 走画布命令，不后台覆盖 JSON |
| 非当前 JSON 写入失败 | 保留原文件和备份，记录失败原因 |
| 程序在提交时崩溃 | 启动后读取 manifest，提示恢复或检查 |
| 汇总剪切出现同名标签 | 停止并人工核对，禁止覆盖 |

## 18. 开发分期

| 阶段 | 内容 | 交付结果 |
|---|---|---|
| P1 工作区与顺序 | 单文件夹边界、分区配置、标签顺序、越界检查 | 可验证分区并按序浏览 |
| P2 本地索引 | staging/active 索引、标签统计、稳定分页 | 大数据量只读查询 |
| P3 缩略图 | 分桶解码、缓存、占位、任务取消 | 完整只读缩略图浏览 |
| P4 审核进度 | 选择、数字键、待提交决定、标签完成状态 | 可持续审核但暂不改盘 |
| P5 安全写回 | 永久 ID、当前画布路径、JSON 事务、备份恢复 | 当前分区批量修改可用 |
| P6 完成检查 | 分区完成摘要、汇总前检查、最终目录重扫 | 支持人工剪切汇总流程 |

## 19. 验收标准

### 19.1 分区边界

1. 当前工作区不能扫描或修改根目录外文件。
2. 当前分区不能把 Shape 改成其他分区的标签。
3. UI 中不存在跨文件夹移动或重新分配入口。
4. 三个分区可以完全独立使用，不依赖公共数据库或公共缓存。

### 19.2 标签顺序与进度

1. 标签始终按配置顺序显示。
2. 重启后恢复到上次处理标签。
3. 有未提交决定、待保存画布或失败项时，默认不能完成标签。
4. 索引重建不会删除审核进度。

### 19.3 Shape 与写回

1. JSON 中 Shape 数组重排后，仍按永久 ID 修改正确对象。
2. 当前画布文件不被后台直接覆盖。
3. 非当前文件写入失败后，原 JSON 仍可正常解析。
4. 每次批量写都有逐文件结果、备份和 manifest。
5. 根据 manifest 可以恢复已提交文件。

### 19.4 缩略图与性能

1. 同一原图在一批任务中只解码一次。
2. 原图、bbox 或标签变化后旧缓存失效。
3. 深页查询不会因 OFFSET 增大而持续变慢。
4. 快速切换标签时，旧任务结果不会显示到新页面。

### 19.5 汇总

1. 三个完成摘要中的标签集合互不重复。
2. 汇总后的标签并集完整覆盖预期范围。
3. 剪切遇到同名标签时不会自动覆盖。
4. 最终目录使用重新扫描生成的新索引。

## 20. 与五项安全机制的关系

原五项机制需要重新解释，不能继续建立在多人并发前提上：

| 机制 | 在新设计中的用途 |
|---|---|
| 永久 ID | 防止同一标注员编辑、删除或排序 Shape 后改错对象 |
| 文件变化检查 | 只处理当前程序内画布与后台索引的先后关系，不处理多人冲突 |
| staging 索引 | 防止扫描失败留下半成品页面 |
| JSON 事务 | 防止断电、崩溃或 I/O 失败损坏当前分区文件 |
| 游标分页 | 保证大数据量下翻页性能稳定 |

真正消除多人冲突的不是以上机制，而是：

> **提前剪切形成互不重叠的物理目录，并保证一个目录始终只有一个标注员处理。**

---

## 21. 最终结论

新方案的核心不是构建复杂的多人并发系统，而是尊重已经确定的生产流程：

```text
先剪切分区 → 单人独占处理 → 文件夹内完成闭环 → 再剪切汇总
```

缩略图审核工作区只对当前文件夹负责。它按固定标签顺序提供高效率审核，在文件夹内部用永久 ID、画布分流、原子写和备份恢复保证数据安全，但绝不跨文件夹搜索、修改、调度或搬运标签。
