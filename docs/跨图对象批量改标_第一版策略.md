# 跨图对象批量改标：第一版策略

> 文档状态：对象修改动作分离稿  
> 初稿日期：2026-08-25  
> 策略收敛：2026-08-26

## 1. 目标

允许用户在多张图片中标记具体对象，形成明确的会话集合，再把这些对象
统一修改为指定标签。

本方案新增“跨图对象标记”和“对象级批量改标动作”，不重复建设以下
既有能力：

- Shape 永久身份；
- 标签管理器中的全局标签重命名；
- 批量写盘所需的预检、备份、原子替换和恢复框架。

第一版需要满足：

- 可对已有跨图标记集合指定一个目标标签；
- 标记对象与执行改标是两个独立动作；
- 执行时冻结标记集合，后续标记变化不影响当前批次；
- 只修改明确标记的对象，不影响其他同标签对象；
- 标签、坐标、属性、`group_id` 和 Shape 数组顺序变化后仍能定位对象；
- 已删除对象跳过，身份冲突和写入失败明确报告；
- 提交前处理当前图片的未保存内容；
- 提供预检、备份、原子提交、部分失败报告和恢复信息。

该功能属于“对象实例批量改标”，不属于标签管理器的“全局标签
重命名”。

## 2. 已有能力与本方案边界

### 2.1 永久 Shape 身份已经就绪

项目已经使用 Shape 顶层字段：

```text
xanylabeling_shape_id
```

该字段承担 X-AnyLabeling JSON 生命周期内的永久对象身份。跨文件引用时
使用完整对象键：

```text
(project_id, image_id, xanylabeling_shape_id)
```

其中 `image_id` 使用项目内稳定且规范化的图片路径或标注 JSON 相对路径。

本方案不负责生成、迁移、修复或重新定义 Shape ID。对象改标只在预检时
防御性验证身份：

```text
唯一命中 → 可进入修改计划
对象不存在 → 视为已删除并跳过
ID 缺失、非法或重复 → 报告身份冲突
```

身份冲突不得使用数组下标、坐标、标签或几何相似度猜测。

### 2.2 对象标记属于本方案新增能力

项目当前没有跨图对象标记实现。本方案新增唯一的会话级标记仓库，负责：

- 加入、移除和清空标记；
- 跨图片维护标记集合；
- 在 Canvas 上表达标记状态；
- 对象删除后的标记清理；
- 提供标记数量、文件数量和对象引用快照。

标记仓库与 `canvas.selected_shapes` 相互独立，不把工作流状态写入标注 JSON。
它不负责选择目标标签或写盘，改标动作只消费其不可变快照。

### 2.3 安全批量事务框架已经就绪

现有标签批量迁移已经具备预检、暂存、备份、原子替换、结果统计和恢复
清单。本方案复用这些事务能力，但不能直接复用“按源标签匹配全部 Shape”
的转换语义。

对象级改标必须增加按完整对象键定位的变更计划，只修改计划中唯一命中的
Shape。

## 3. 核心决策：标记与修改动作分离

系统按三层能力组织：

```text
永久对象身份
    ↓
会话级对象标记集合
    ↓ 生成不可变快照
对象级批量改标命令
    ↓
预检 → 用户确认 → 安全提交 → 结果处理
```

三层的职责分别是：

| 层级 | 回答的问题 | 是否修改 JSON |
| --- | --- | --- |
| 对象身份 | 这是哪个对象 | 否 |
| 对象标记 | 用户准备处理哪些对象 | 否 |
| 改标命令 | 把这些对象修改成什么标签 | 是 |

以下行为必须成立：

- 标记对象不会自动修改标签；
- 关闭或暂停标记模式不会自动执行改标；
- 选择目标标签不会改变原标记集合；
- 取消预检不会清空标记；
- 只有用户确认后才能进入写盘事务；
- 所有 UI 入口最终调用同一个对象级改标命令。

## 4. 标记模块与改标命令的接口

### 4.1 不可变对象快照

启动一次改标请求时，从现有标记模块取得不可变快照。每个条目至少包含：

```text
project_id
image_id
xanylabeling_shape_id
```

可以附带以下只读摘要，用于预检界面显示：

```text
当前标签
shape_type
group_id
图片显示名称
```

摘要不参与身份匹配。运行时 `Shape` 引用可以作为当前图片的界面优化，
但不得成为跨图定位或写盘依据。

概念接口如下：

```text
marked_object_store.snapshot()
    → tuple[MarkedObjectRef, ...]
```

这里的接口名表达本方案要实现的会话仓库契约。LabelingWidget 只创建一份
仓库，Canvas 仅接收当前图片的标记 ID 用于绘制，不保存跨图集合。

### 4.2 为什么必须冻结快照

用户打开标签选择器、查看预检或等待后台扫描时，仍可能继续标记或取消
其他对象。当前批次必须使用启动时的对象集合：

```text
活动标记集合 ──snapshot──▶ 本次不可变对象集合
      │                         │
      └── 可以继续变化          └── 直到本次事务结束保持不变
```

这样可以保证预检数量与实际提交对象一致。

## 5. 对象级批量改标命令

第一版使用窄范围的显式命令，不提前抽象成可以任意修改所有 Shape 字段的
万能编辑器。

概念请求如下：

```text
request_object_relabel(
    targets=marked_object_store.snapshot(),
    target_label="writing",
)
```

命令输入只包括：

- 不可变对象快照；
- 一个目标标签；
- 当前项目和标注根目录上下文。

命令不读取 Canvas 普通选中集合，也不根据原标签扩大作用范围。

## 6. 执行状态模型

```text
空闲
  │
  ├── 无标记对象：拒绝启动并提示
  │
  └── 有标记对象
          ↓
      冻结对象快照
          ↓
      选择目标标签
          ↓
      预检
       ├── 取消：保留全部标记，返回空闲
       └── 确认
              ↓
          暂存与验证（可取消）
              ↓
          原子提交（不可取消）
              ↓
          同步结果与标记状态
              ↓
             空闲
```

对象标记模式有自己的生命周期，不并入该状态机。改标事务只在开始和结束
时通过快照与结果通知同标记模块交互。

## 7. 统一执行流程

### 7.1 请求校验

启动前检查：

- 目标标签非空且符合项目标签约束；
- 标记快照非空；
- 每个条目都有完整对象键；
- 所有条目属于当前项目；
- 当前没有其他数据集写事务；
- 当前不处于未完成绘制、拖动或其他不稳定编辑状态。

### 7.2 处理当前图片未保存内容

如果当前图片处于 dirty 状态：

```text
保存成功 → 继续
保存失败 → 中止并保留全部标记
用户取消 → 中止并保留全部标记
```

后台事务不得覆盖当前尚未保存的编辑。

### 7.3 按文件组织对象

快照按 `image_id` 分组：

```text
image_001.json：shape_id A、shape_id B
image_016.json：shape_id C
image_107.json：shape_id D、shape_id E
```

对象快照已经给出精确文件集合，因此无需按原标签扫描整个数据集，也不能
使用原标签作为候选文件来源。

### 7.4 严格定位

每个目标 JSON 都必须重新读取并验证真实内容：

```text
Shape ID 唯一命中 → 加入可修改集合
Shape ID 不存在   → 已删除，加入跳过集合
Shape ID 异常     → 该文件身份冲突，不生成替换文件
JSON 读取失败     → 该文件失败
```

即使 Dataset Index 中存在相同记录，也必须以提交前读取的 JSON 为最终
事实来源。

### 7.5 生成对象级变更计划

变更计划按文件保存目标 Shape ID 集合和目标标签：

```text
ObjectRelabelPlan
├── target_label
└── targets_by_file
    ├── image_001.json → {A, B}
    ├── image_016.json → {C}
    └── image_107.json → {D, E}
```

该计划与全局标签管理器的 `rename_map` 不同：

```text
全局标签重命名：所有 label == old 的对象 → new
对象级批量改标：只有 Shape ID 在计划中的对象 → target_label
```

两者可以共享事务基础设施，但不能共享对象匹配语义。

### 7.6 显示预检

预检至少显示：

```text
目标标签：writing
快照对象：18
涉及文件：7
可修改：16
已删除：1
身份冲突：1
读取失败：0
```

还应明确说明：

- 只修改列出的具体对象；
- 不修改其他同标签对象；
- 提交开始后不可取消；
- 失败文件中的对象会保留标记以便重试。

只有用户确认后才能进入暂存和写盘。

### 7.7 暂存、验证与提交

复用现有安全批量事务框架：

- 写入同卷临时文件；
- 重新解析新 JSON；
- 验证目标 Shape 的标签已改变；
- 验证 Shape 数量和非目标字段未意外变化；
- 备份原文件；
- 检查源文件自预检后是否变化；
- 使用原子替换提交；
- 保存事务 manifest 和恢复信息。

转换逻辑只能执行：

```text
唯一命中的 shape["label"] = target_label
```

必须保留：

- `xanylabeling_shape_id`；
- `points`；
- `shape_type`；
- `group_id`；
- `flags`、`attributes`、`description`；
- Shape 和根对象中的未知扩展字段；
- 非目标 Shape 的全部内容和顺序。

## 8. 修改结果与标记状态

标记模块根据结构化结果更新活动集合：

| 结果 | 文件状态 | 标记处理 |
| --- | --- | --- |
| 修改成功 | 已提交 | 移除对应标记 |
| 对象已删除 | 未修改 | 从活动集合移除 |
| 身份冲突 | 文件不变 | 保留标记 |
| 读取、验证或写入失败 | 文件不变或报告部分失败 | 保留标记 |
| 用户在提交前取消 | 文件不变 | 保留全部标记 |

如果一次事务部分成功，不得显示“全部成功”。结果至少包含：

```text
成功对象数
跳过对象数
失败对象数
成功文件数
失败文件数
恢复清单位置
```

完成后：

- 当前图片受影响时重新加载；
- 更新标签列表、过滤器和 Dataset Index；
- 恢复普通保存能力；
- 只清除成功或确认已删除对象的标记；
- 允许用户修复失败原因后直接重试剩余标记。

## 9. UI 与入口策略

第一版只要求一个明确的主入口：

```text
修改已标记对象的标签……
```

入口应显示当前对象数和文件数，例如：

```text
修改已标记对象的标签……（18 个对象 / 7 个文件）
```

可以从工具栏或菜单提供该入口。标签列表右键、Canvas 右键和数字快捷键
可以后续作为轻量适配入口，但不得各自实现写盘逻辑。

数字快捷键如在第一版接入，只能用于选择目标标签并打开统一预检，不能在
普通标记过程中无提示直接写盘。

本方案新增工具栏或菜单标记开关、清空动作和 Canvas 独立标记视觉，但不
新增 Inspector 页面，也不改变 Canvas 普通选中和编辑语义。

## 10. 并发与一致性

一次只允许一个数据集写事务。事务期间：

- 预检和暂存阶段允许取消；
- 提交阶段暂时禁止与目标文件竞争的保存；
- 提交阶段不可取消；
- 不冻结无关的只读浏览和界面重绘；
- 源文件在预检后被外部修改时，该文件失败而不是覆盖新内容；
- UI 必须以磁盘实际提交结果同步，不能提前应用预期状态。

## 11. 第一版明确不做

为了保持职责清晰，第一版不包含：

- 重新生成、修复或迁移 `xanylabeling_shape_id`；
- 把工作流标记状态写入标注 JSON；
- 重启后恢复标记集合，除非现有标记模块已经支持；
- 通过标签、坐标、数组下标或几何相似度猜测对象；
- 点击一个对象自动扩展到整个 `group_id`；
- 一个批次包含多个目标标签；
- 批量修改 `group_id`、属性、描述或几何；
- 自动修改所有同名标签；
- 多套对象级写盘实现；
- 云端或多人共享批次。

未来需要批量修改其他 Shape 字段时，应新增独立的对象操作类型，并复用
对象快照和事务协议，而不是把第一版改标命令提前扩展成万能命令。

## 12. 验收标准

第一版至少满足：

1. 会话标记仓库可以向改标命令提供跨图对象快照。
2. 创建快照后继续增加或取消标记，不改变本次预检和提交对象。
3. 未标记任何对象时不能启动改标。
4. 选择或取消目标标签不会修改标注 JSON，也不会清空标记。
5. 修改坐标、原标签、属性或 `group_id` 后，仍按 Shape ID 找到原对象。
6. 外部重排 `shapes` 数组后，仍能找到原对象。
7. 只修改对象计划中唯一命中的 Shape，其他同标签对象保持不变。
8. 对象不存在时跳过并从活动标记集合移除。
9. ID 缺失、非法或重复时明确报告身份冲突，不进行模糊匹配。
10. 当前图片 dirty 且保存失败或取消时，不启动批量写盘。
11. 预检显示目标标签、对象数、文件数、可修改、跳过和失败数量。
12. 用户取消预检或暂存时，保留全部标记且不修改文件。
13. 提交只改变目标 Shape 的 `label`，保留所有其他字段。
14. 成功对象清除标记，失败对象保留标记以便重试。
15. 部分失败显示准确结果并提供恢复信息。
16. 所有 UI 入口调用同一个对象级改标命令。
17. 全局标签重命名与对象级改标保持独立语义。

## 13. 用户流程

```text
开启跨图对象标记模式并跨图标记对象
    ↓
选择“修改已标记对象的标签……”
    ↓
系统冻结当前标记快照
    ↓
用户选择目标标签
    ↓
系统按文件和 Shape ID 严格预检
    ↓
显示可修改、已删除、冲突和失败数量
    ↓
用户确认
    ↓
暂存、验证、备份并原子提交
    ↓
成功对象清除标记
失败对象保留标记
    ↓
显示结果和恢复信息
```

第一版的交付中心是一个独立、可复用、对象级的批量改标动作：它消费
已有标记系统提供的不可变对象快照，以
`(project_id, image_id, xanylabeling_shape_id)` 严格定位对象，并复用现有
安全事务框架完成写盘。
