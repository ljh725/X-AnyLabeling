## 本轮问题

### R1 [P1] 把有效值当作持久基线，合法配置下普通保存误报冲突

代码：`anylabeling/views/labeling/settings/controller.py:146`、`:417`—`:421`；`anylabeling/user_config.py:814`—`:822`；主窗口同类调用为 `anylabeling/views/labeling/label_widget.py:8432` 起的 `update_user_preference`。

控制器用 `_config` 中的显示值建立 `_base_values`，并直接交给存储层作为磁盘 B 值。但有效配置已经合并模板默认值、内联 YAML 或 CLI 临时覆盖，不等于该字段的磁盘原值或缺失状态。存储层在锁内拿原始规范化磁盘 C 比较，因而在没有其他写入者时也会拒绝保存。

实测两个场景：

1. 文件型配置只有合法的 `{}`，打开设置将默认 `canvas.epsilon` 改为 `9.5`：返回 `ConfigConflict(['canvas.epsilon'])`，文件仍为 `{}`。
2. 完整配置的磁盘 epsilon 为 `10.0`，启动参数临时覆盖为 `9.9`，用户在设置中明确改为 `9.5`：仍返回 ConfigConflict，磁盘保持 `10.0`，草稿为 `9.5`。重新载入后临时覆盖仍为 `9.9`，不能解决这一基线混淆。

修正任务：2.3、3.2、4.1、5.1。草稿需要分别保留“持久字段原值/缺失”和“显示有效值”，显示/进程内草稿冲突检查与磁盘 B/C/P 不能混用；真实并发修改仍须拒绝。验收须同时覆盖稀疏配置、旧版本缺新增字段、显式修改被覆盖字段、无关保存不固化临时值。

### R2 [P2] 保存后重建完整草稿，却只推进保存字段的基线

代码：`anylabeling/views/labeling/settings/controller.py:528`—`:541`。

`_working_config` 在成功保存后整体从最新 `_config` 重建，`_base_values` 却只更新 saved_keys。已由别的入口修改、此次未编辑的字段会出现“界面已展示新值，冲突基线仍是旧值”。

实测：窗口 A 打开时字体为 8；另一个入口保存字体 20；A 保存 epsilon 成功后，其草稿字体为 20、基线仍为 8；A 再将字体改为 22，第二次保存误报 ConfigConflict，磁盘停留在 20。

现有 `test_untouched_field_can_be_edited_after_a_save` 没有插入“另一个入口先改字体”的步骤，所以通过并不验证该缺口。

修正任务：4.1、4.5。重建草稿时同步当前未修改字段的基线；仍处于未保存状态的字段继续保留原编辑基线。新增同进程与外部进程的上述交错场景。

### R3 [P2] 另一字段保存成功或重新打开设置，会丢失待应用失败状态

代码：`anylabeling/views/labeling/settings/controller.py:155`—`:156`、`:543`—`:549`；重载链为 `settings/dialog.py:2149`—`:2150`。

新增的 apply_failed/retry_apply 能处理单次失败，但 `_save_now` 只按本次 saved_keys 的结果重置整个 `_apply_failed_keys`；本次字段均成功时，会将之前尚未应用的其他字段一并清空。`begin_session` 也直接清空待应用集合，重载后尝试重试的入口已无失败记录可用。

实测：epsilon 写盘成功、runtime callback 持续抛异常，pending 为 `['canvas.epsilon']`；随后保存不相关 model_hub 成功，epsilon 从未成功应用，pending 却变成 `[]`。后续关闭不再能据此提示或重试。

修正任务：4.2、4.4、7.1。失败状态按字段累计，只清除本轮确实成功应用的字段；新建/重载草稿不得丢弃真实待应用状态，除非有明确的处理结果。补“失败 A→成功保存 B→重开/重载→重试 A”回归。

### R4 [P2] 重新载入只覆盖现存叶字段，未移除外部删除项

代码：`anylabeling/user_config.py:700`—`:722`、`:937`—`:955`。

`reload` 使用 `_sync_effective`，后者只遍历新文档中仍存在的叶字段，不清除旧 effective 中已被外部删除的条目。备份恢复专用的 `_replace_effective` 解决了恢复路径的问题，但普通重载/保存同步路径仍有旧 overlay 行为；整个文件被删除时也未重建有效配置。

实测：原数字映射有 1、2 两项；外部删除数字 1，保留数字 2 后 reload 返回 True。磁盘数字为 `[2]`，effective 仍为 `[1, 2]`。冲突对话框的“重新载入”依赖同一路径，所以删除项仍可能继续显示或被使用。

修正任务：3.2、4.1、4.4。按模板、完整规范化文档及明确启动覆盖策略构建最新有效视图，并同步删除；控制器仍须保留尚未明确放弃的草稿。补单项删除、嵌套父字段删除、目标文件删除与重载后再编辑。

### R5 [P2] 吸收外部配置变化后，没有把这些字段应用到实际动作

代码：`anylabeling/user_config.py:886`—`:887`；`anylabeling/views/labeling/settings/controller.py:543`；`settings/dialog.py:2149`—`:2154`；快捷键真正的应用分支在 `settings/runtime_applier.py:310`—`:312`。

存储层现在会把重读到的其他入口字段同步到 effective，但控制器仅给本次 saved_keys 调用 runtime callback。显式重载也只是刷新配置/草稿，没有按变化字段更新 QAction、画布运行参数等依赖对象。因此“设置界面已显示新值”不等于“当前窗口的实际行为已采用新值”。

实测：外部把 shortcuts.open 改成 `Ctrl+Alt+Shift+F12`，当前窗口仅保存 epsilon。保存成功后 effective 已显示新快捷键，runtime callback 记录却只有 `canvas.epsilon`，从未收到 `shortcuts.open`；现有 runtime applier 在 epsilon 分支只处理画布基本参数，不会补上快捷键分支。

本探针验证回调缺失及真实分支代码，未声称已启动完整 MainWindow 实测按键。下一步验收必须检查实际 QAction.shortcut()、数字模式及画布值，不能只断言 controller.get_value。

修正任务：4.1、4.2、4.4、4.5。保存吸收外部变化和显式重载时，识别真实生效的变化字段并通知依赖；保留临时覆盖和未保存草稿的语义，回调失败仍按 R3 处理。
