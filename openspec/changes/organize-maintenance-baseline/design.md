## Context

动机与范围见 [proposal.md](proposal.md)。2026-11-17 方案起点 `8d87a93b` 相对本地集成分支领先 36 个提交（0 behind）；此数字不是远端实时状态。工作树还存在其他任务的 `.gitignore`、`docs/development/` 和用户提供的审计报告，均未纳入本方案提交。

## Goals / Non-Goals

**Goals:**
- 从确定提交建立可维护候选基线，留下同一代码修订上的验证和限制说明。
- 让当前状态、历史事实和未来方案有明确入口；归档之后仍能定位证据。
- 以现有任务清单、CUSTOM 台账和版本操作记录交接，不新建长期维护的平行任务数据库。

**Non-Goals:**
- 本方案生成阶段不执行四步；不替用户宣布人工验收通过。
- 不启动关键点显示扩展，不恢复已终止的密集复核重设计计划。
- 不重写 Git 历史、不整体恢复旧文件、不移动版本入口、不删除备份和历史证据。

## Decisions

### 1. 一个执行 agent 顺序推进，一个可选审阅 agent 只读复核

唯一可勾选任务是 [tasks.md](tasks.md)。使用 OpenSpec apply 技能读取上下文后执行。阶段有依赖，多个 agent 同时修改 Git、索引或 tasks.md 容易覆盖成果，因此本轮不做并行写入。可让独立审阅 agent 只读检查提交、状态语义和证据；审阅意见由执行 agent 统一落实。

方案分支从 `8d87a93b` 建立；执行者沿用 `codex/4.2.1/maintenance-baseline-plan`，记录实际方案提交。若必须隔离工作区，将其放在仓库可写的 `.local/` 中，验证依赖和完整保存点后再操作，不移动或清理已有未提交文件。

### 2. 候选代码基线先固定，是否稳定由后续验证决定

在现有 `docs/version-management/` 下建立一份当期基线说明，包含提交号、相对集成分支的改动分类、保留实现、停止任务遗留、配置与数据兼容风险及已知失败。基线说明不是新的持续待办清单。

用户已接受整理四步，可以执行只读盘点、状态修正、测试、符合条件的既有变更归档及本地提交。推送、PR、合入、将部分实现整体撤销，仍不在授权范围。停止记录中的失败属于基线风险，不能据此重新开展已终止任务。

### 3. 当前状态前置，历史证据保留

`PENDING_TASKS.md` 只汇总并直链源 tasks.md，不复制第二套任务勾选。将旧快照明确放入历史区；CUSTOM 索引订正必须核对实际对应关系：CUSTOM-118 是数字键提示条，数字键矩形保存是 CUSTOM-011。CUSTOM-109 的 55/55 是用户决定关闭的任务状态，不自动等于新增人工验收证据。

任务全勾、证据缺口、行政关闭和归档状态分别表达。未实施的关键点方案注明暂停，保留 0/22；未完成验收的成本统计、原密集复核工作流保留真实未完成项。

### 4. 验证以同一生产代码修订为边界

使用 `C:\Users\20441\.conda\envs\x-anylabeling-cu12\python.exe`。按关键风险先跑保存/重开、导航、撤销重做、配置、矩形交互及 Inspector/密集复核交接，再覆盖受影响目录。用 `-vv -o faulthandler_timeout=30` 并以外层进程硬超时结束挂起运行；临时路径放 `.tmp/`，保留配置写入保护。

窗口测试在隔离 fixture 生效后 `get_config()` 再构造窗口。若卡在模态错误框，保留用例、原始错误和堆栈，不用跳过或屏蔽保存错误换取通过。原生异常按当前修订复现并区分历史问题、环境限制和新回归；旧的 0xC0000409 记录不能直接当作当前失败或已解决。

固定测试命令、环境、代码提交、通过/失败/跳过/未运行和退出码。源码、测试、资源或影响运行的配置更改后，补跑受影响范围；纯文档提交可引用相同生产代码修订的证据并说明对应关系。

证据集中放 `reports/maintenance_baseline_20261117/`，入口为 `REPORT.md`；性能原始数据仍按仓库约定放 `perf_reports/` 或 `benchmarks/`。Windows 不运行点云套件；工具栏布局属于 CI 排除项，选择执行或排除都说明。通过受影响测试后，评估并运行适用于 Windows 的完整回归；不能完成时记录明确缺口，不拼接各历史阶段数字冒充当前全绿。

### 5. 同步既有契约先预演再落地

在 `.tmp/` 的独立 OpenSpec 副本中检查依赖、delta 语义和链接迁移，不能在主目录试错。已完成变更按可独立验证的最小批次提交；每项归档决定注明来源提交、自动化及人工证据、未测限制和发布的契约范围。

`rectangle-point-fit` 按基础 ADDED → 锁角 ADDED → unify MODIFIED/REMOVED 的依赖顺序处理。场景改名必须写出旧/新对应及行为变化，不能只改标题骗过校验、另建重复规格或强行丢掉场景。

`migrate-canvas-controls-from-v430` 保留完整移交材料；restore 发布一次相同契约后，可用“已移交、无独立增量”的决定归档该历史脚手架，不表述为再次实施。只有核对确认重复契约已发布，才采用工具允许的零增量或跳过重复规格路径；不将此例推广到有独立产品契约的其他变更。

密集复核主规格不盲目补齐：对现有代码、原工作流三份 delta 和停止归档的五份草案建立对照。只在既有变更满足交付条件时发布；未满足则保留未发布并记录原因。已停止草案保留其历史身份，不无依据标为全部被取代，也不因存在部分代码而恢复原计划。

活动文档导航更新到新路径；历史报告和 inventory 快照保留原文，在当前入口提供旧路径→新路径映射。归档后运行 strict、链接核对与差异审阅。

## Risks / Trade-offs

- [人工与硬件验收不可自动完成] → 保留待验证状态，不以清零待办为交付条件。
- [未提交工作与审计输入混入提交] → 每批显式暂存文件，检查 staged diff；禁用 `git add .`。
- [报告中关联错误或过度结论] → 以任务、代码和实际证据核实；审计报告是线索，不是执行真值。
- [停止任务与当前维护边界交叉] → 允许观察和登记现有代码风险；触及重新开发或行为取舍时只暂停该项，继续其余整理。

## Migration Plan

四步逐批提交；首次实际执行时记录方案提交和候选代码提交。仓库操作追加现有操作记录，CUSTOM-124 只说明本轮工程配套成果。整理失败时保留原证据和可恢复提交；按具体文档/归档批次撤销，避免回退当前混合源码快照。最终分别报告本地、远端、合入和验证状态；已知失败未解决时可以交付“已整理但未达稳定基线”，不得标为“已验证稳定”。
