# 性能验收补充：匹配基线复测（8.3，2026-11-09）

> 本文关闭 2026-11-05 保留未完成的 8.3。此前的 `performance-before.json` 对照副本已包含五项恢复能力，且与当前代码存在其他既有差异，不能把差异归因于本变更。本轮改为三部分证据：**只差被测文件的匹配 A/B**、**同代码 A/A2 对照**、**恢复代码热路径微基准**。

## 1. 测前判据（写入驱动脚本，测试前固定）

- 每个条件（30/300 对象 × 拖框/切图）取多次运行的 p95 中位数；
- 通过条件：`|Δ| ≤ max(同代码 A/A 波动, 2%)` 或 `|Δ| ≤ 1.0 ms（拖框）/ 2.0 ms（切图）`；
- 另设同代码对照（A vs A 的另一份拷贝），用于界定环境噪声，避免把噪声当结论。
- 判据固定于 `run_ab.py`（脚本时间戳早于结果），不在拿到数据后修改。

## 2. 匹配基线定义

| 项 | 内容 |
| --- | --- |
| A | 当前工作区源码拷贝（HEAD `cd26f5f8`，含未提交的 label_widget 工作） |
| B | A 的**唯一差异**：反向应用 `484977f → a2e4282` 的 3 个产品文件（`label_widget.py`、`widgets/toolbar.py`、`settings/dialog.py`），其余逐字节相同 |
| A2 | A 的原样副本，仅用于同代码对照 |
| 环境 | Windows，12 逻辑核；Python 3.12.12，Qt 6.10.0 / PyQt 6.10.2；`QT_QPA_PLATFORM=offscreen`；每轮记录 psutil CPU 负载（实测 7%–25%） |
| 同一 harness | `.local/canvas-implementation-20261105/benchmark_controls.py`（sha256 `1fd6bca5…`），每轮独立 state 目录 |

A/B 差异由哈希清单核实：两树仅 3 个文件不同，`canvas.py`、`shape.py` 完全一致（见 `env.json` 的 `variant_hashes`）。

三个修复 hunk 的位置决定它们**不在**被测热路径上：

1. `group_selected_shapes` / `ungroup_selected_shapes` → 仅成组/解组动作；
2. `SettingsDialog` 字段定位定时器 → 仅设置窗口打开/跳转；
3. `ToolBarScrollArea.wheelEvent` 横向符号 → 仅工具栏上的滚轮事件。

拖框与切图路径不经过上述任何代码，因此 A/B 的拖框/切图差异只可能来自环境噪声。

| 条件 | A 中位 p95 | B 中位 p95 | Δ |
| --- | --- | --- | --- |
| 30 对象 拖框 | 16.99 ms | 22.30 ms | +31.2% |
| 30 对象 切图 | 47.61 ms | 49.85 ms | +4.7% |
| 300 对象 拖框 | 134.45 ms | 137.87 ms | +2.5% |
| 300 对象 切图 | 259.14 ms | 248.11 ms | −4.3% |

p50（更稳定）：A/B 分别为 14.59/15.48（+6.1%）、39.75/38.51（−3.1%）、83.22/84.97（+2.1%）、203.76/209.73（+2.9%），**符号不一致**；逐轮配对中位数为 +1.5%、−3.1%、+0.1%、+1.1%。

30 对象 p95 的 A/A 自身波动即达 24%–48%（离屏调度抖动），该尺度下 p95 不能作为判定指标。

| --- | --- | --- |
| 30 对象 拖框 | −3.3% | −5.4% |

## 6. 结果四：恢复代码自身成本（微基准，只关被测代码）

画布局部：E 树 = A 树仅把 `Shape.paint` 的填充透明度实现换回恢复前版本（`shape.py` 单文件差异），同一批图形直接绘制。

| 填充图形数 | A @100% | E（无恢复代码） | A @50% |
| --- | --- | --- | --- |
| 1 | 0.053 ms | 0.026 ms | 0.034 ms |
| 2 | 0.057 ms | 0.046 ms | 0.061 ms |
| 30 | 0.758 ms | 0.614 ms | 0.816 ms |
| 300 | 7.810 ms | 6.496 ms | 8.480 ms |

折算：恢复代码约 **+4.4 µs/填充图形**；透明度 <100% 时再 +2.2 µs/图形。但真实帧内并不会全量填充：`canvas.py` 每次重绘按 `_fill_drawing and (selected or hovered) and not moving` 决定填充（`_fill_drawing` 默认 `False`，拖动中 `moving_shape=True` 也不填充），**真实拖框帧填充数为 0**，静态多选时最多为选中数。因此拖框热路径的恢复成本为 0，最坏情况（300 个全选静态重绘）也只有一次约 1.3 ms 的开销。

切图局部（A 树实测每次调用）：`_flush_pending_brightness_contrast` 0.34 µs，`constrain_canvas_pan` 0.22 µs，`_apply_or_seed_shared_view` 75 µs（既有函数；本轮仅在其内部新增一次 constrain）。恢复新增的每次切图成本 **< 1 µs**，相对 40–250 ms 的切图耗时可忽略。

## 7. 结论

- 匹配 A/B：拖框/切图 p50 差异 −3.1%…+6.1%，与同代码对照噪声跨度（±5.4%）同量级，且三个修复 hunk 均不在被测路径上 → **不存在可归因于本变更的性能回退**。
- 恢复能力本身：拖框帧默认 0 次填充；切图新增调用 <1 µs/次；最坏静态全选重绘约 +1.3 ms 一次性开销。
- 8.3 判定：**无性能回退证据成立，予以勾选**。
- 限制：离屏相对测量，不代表真实 GPU/合成器绝对帧率；30 对象 p95 受离屏调度抖动影响大，故判定以 p50 + 同代码对照为准；未测量真实桌面合成与高 DPI 渲染开销（8.4 单独验收）。
