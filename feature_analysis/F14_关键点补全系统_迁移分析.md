# 功能14：关键点补全系统 — 迁移分析（4.0.0-beta.4 最终版）

- **难度**: ⭐⭐⭐ | **影响级别**: 🟢 label_widget 层局部改动
- **核心代码**: `widgets/keypoint_fill_mode.py` (~380行) + `widgets/keypoint_tool_window.py` (~430行)
- **集成代码**: `label_widget.py` (~100行)
- **依赖**: 无前置强依赖（不依赖 DigitLabelCycleManager / FilterController）
- **快捷键**: K (进入补全模式 / 打开工具窗口), Ctrl+K (切换工具窗口)

## 1. 旧分析文档的问题与 3.3.0 源码的问题

### 旧迁移分析文档（过度复杂化）
旧文档把 F14 分析成"5个独立模块、100KB、依赖F07、预计4-5小时"，原因：
1. **混淆了运行代码与注释代码**：`keypoint_fill_mode.py` 55KB 中，真正运行的 Build 1 仅 ~370行，其余 ~1100行是被注释掉的 Build 2/3。
2. **假设了未拆分的模块**：Build 3 的类被拆成了4个独立文件，但这些代码从未真正激活运行。
3. **虚构了 Canvas API 审查**：`KeypointFillMode` 不直接操作 Canvas。
4. **强加了不存在的前置依赖**：旧文档要求 F07(FilterController)必须先完成，但 F14 核心功能与 filter 无关。

### 3.3.0 源码的"重复构建"问题
`test_260105_2_X-AnyLabeling-3.3.0` 中的实现经历了 **3 次架构迭代**，且后 2 次被注释在同一文件内：

| 构建 | 类名 | 状态 | 问题 |
|------|------|------|------|
| Build 1 | `KeypointFillMode` | 运行 | 复用 `DigitLabelCycleManager`，仅核心引擎 |
| Build 2 | `KeypointDockWidget` | 注释掉 | Dock 面板，与主窗口深度耦合 |
| Build 3 | `KeypointToolWindow` + 4个分层类 | 注释但拆成4文件 | **过度分层**，每层仅100-200行，互相调用增加无意义复杂度 |

**核心问题**：Build 3 的 4 个文件形成"伪分层架构"——`KeypointDataView` 只是遍历 `label_list` 做统计，`KeypointDataOperation` 只是调用现有接口，`KeypointMessageManager` 只是包装 `status()`。将 3 个薄层拆成独立文件，反而增加了维护成本和认知负担。

## 2. 4.0.0 架构决策

### 2.1 内嵌 LabelCycle
3.3.0 的 `KeypointFillMode` 依赖外部 `DigitLabelCycleManager`（552行）。该管理器属于 F02-F04（数字快捷键多标签循环），若后续要移植那些功能可单独引入。

**F14 在 `KeypointFillMode` 内部内嵌 `_LabelCycle` 类**（~100行），覆盖：解析标签串、`activate/deactivate/advance/next/prev/jump`、信号发射。

### 2.2 合并工具窗口分层
将 Build 3 的 4 个文件合并为 **1 个文件 `keypoint_tool_window.py`**：
- `KeypointDockContent`：直接把 `data_view`（数据读取）和 `data_operation`（filter/激活/模式切换）的逻辑内联到内容组件中
- `KeypointToolWindow`：去除单例模式，改为普通实例由 `label_widget` 持有
- 删除 `keypoint_data_view.py`、`keypoint_data_operation.py`、`keypoint_message_manager.py`

### 2.3 去除 FilterController 依赖
4.0.0 中没有 `FilterController` 类。group_id 筛选通过直接操作 `gid_filter_combobox.gid_box` + 调用 `gid_selection_changed()` 实现。

## 3. 4.0.0 实现详情

### `widgets/keypoint_fill_mode.py`
- `KeypointFillMode`：核心补标引擎
  - `KEYPOINT_ORDER`：COCO 17 关键点标准顺序
  - `activate(group_id)`：计算缺失关键点，启动标签循环
  - `advance()`：创建点后推进到下一个标签，全部完成自动退出
  - `refresh()`：undo/redo 后重新计算缺失列表
  - `jump_to_label(label)`：跳转到指定关键点
  - 信号：`mode_activated`、`mode_deactivated`、`current_label_changed`
- `_LabelCycle`（内嵌）：轻量级标签循环器，替代 `DigitLabelCycleManager`

### `widgets/keypoint_tool_window.py`
- `KeypointDockContent`：内容组件
  - `_get_person_data()`：遍历 `label_list`，统计每个 group_id 的 person 框和已完成关键点数
  - `_get_keypoint_status()`：获取指定 group_id 已完成的关键点标签集合
  - `_sync_gid_filter(group_id)` / `_clear_gid_filter()`：直接操作 combobox
  - `switch_to_person(group_id)`：退出当前 fill mode → 设置 filter → 激活 fill mode → 切换到 point 模式
  - `refresh_all()`：刷新人员列表、统计信息、当前人员进度、关键点状态列表
  - `_update_keypoint_list()`：显示 ✅已完成 / ⏳待标注，当前待标注项高亮为蓝色
  - `_update_hint_label()`：提示栏显示下一个待标注点名称
  - `_on_keypoint_clicked()`：点击待标注关键点可跳转到该标签
- `KeypointToolWindow`：独立浮动窗口（`Qt.WindowType.Window`）
  - 持有 `KeypointDockContent`
  - `closeEvent` 仅隐藏不销毁

### `label_widget.py` 集成点

| 位置 | 改动 |
|------|------|
| `__init__` | 创建 `KeypointFillMode`；`self.keypoint_tool_window = None` |
| Action | `enter_keypoint_fill_mode` (K)；`toggle_keypoint_tool_window` (Ctrl+K) |
| `self.actions` / `on_load_active` / `addAction` / `menus.tool` | 注册两个 action |
| `new_shape()` | 开头拦截：若 fill mode 激活且新 shape 为 point，自动赋值 label+group_id，advance，跳过 label dialog |
| `toggle_draw_mode()` | 开头拦截：若 fill mode 激活且切换到非 point 模式，自动退出 |
| `undo_shape_edit()` | 末尾：若 fill mode 激活，调用 `refresh()` |
| `enter_keypoint_fill_mode()` | **智能模式**：选中 person 框 → single mode；未选中 → batch mode（打开工具窗口并选第一个未完成的人） |
| `exit_keypoint_fill_mode()` | 退出 fill mode，重置 filter，恢复选择模式 |
| `toggle_keypoint_tool_window()` | 创建/显示/隐藏工具窗口，连接 `canvas.new_shape` 信号实时刷新 |
| `switch_to_prev_person()` / `switch_to_next_person()` | 循环切换人员 |
| `load_file()` 末尾 | 图片切换时自动刷新工具窗口；调用 `_check_auto_activate_keypoint_fill()` |

### Auto-Activate 模式
- 工具窗口顶部有 `auto_activate_cb` 复选框："自动锁定目标 (Auto-Activate)"
- 勾选后，`_check_auto_activate_keypoint_fill()` 在每次图片加载后自动执行
- 若当前图片中**恰好只有一个** person 对象（按 group_id 统计），则自动激活 fill mode 并显示工具窗口
- 设置持久化到 `_config["auto_activate_keypoint_fill"]`

### 配置文件
- `widgets/__init__.py`：导出 `KeypointFillMode`、`KeypointToolWindow`
- `xanylabeling_config.yaml`：`enter_keypoint_fill_mode: K`，`toggle_keypoint_tool_window: Ctrl+K`

## 4. 弹框问题的处理

3.3.0 中报告的"开启后出现弹框"问题，在 4.0.0 中的防护措施：

1. **`new_shape()` 强制拦截**：方法开头检查 `keypoint_fill_mode.is_active`，若为 point 类型且获取到有效 label+group_id，立即 `return` 跳过 `label_dialog.pop_up()`。
2. **工具窗口 `switch_to_person()` 保证有效性**：激活 fill mode 前计算缺失列表，确保 `get_next_label_and_group_id()` 不会返回 None。
3. **单例模式去除**：3.3.0 的单例可能导致窗口状态残留，4.0.0 改为普通实例，生命周期由 `label_widget` 明确管理。

## 5. 与 3.3.0 的差异对比

| 项目 | 3.3.0 | 4.0.0-beta.4 |
|------|-------|-------------|
| 标签循环器 | 外部 `DigitLabelCycleManager` (552行) | 内嵌 `_LabelCycle` (~100行) |
| 工具窗口文件数 | 4 个文件 (`tool_window` + `data_view` + `data_operation` + `message_manager`) | 1 个文件 (`keypoint_tool_window.py`) |
| 工具窗口模式 | 单例 (`get_instance`) | 普通实例 (`label_widget` 持有) |
| group_id filter | `FilterController._sync_gid_visibility()` | 直接操作 `gid_filter_combobox.gid_box` |
| batch/single 切换 | `enter_keypoint_fill_mode(batch_mode=True/False)` 参数 | 智能判断：有选中 person → single；无 → batch |
| PyQt 版本 | PyQt5 | PyQt6（信号/枚举适配） |
| 注释代码 | Build 2/3 共 ~1100行注释代码残留在 `keypoint_fill_mode.py` | 全部去除，只保留运行代码 |
